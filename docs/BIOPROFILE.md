# BioProfile Engine: персональный профиль биомеханики мыши

Что здесь есть: конечный автомат классификации сценариев, структура `ProfileState` (98 байт, версия, magic, CRC), скользящие
медиана/сигма, измерение T_motor и усталости, безопасное хранение и интерфейс чтения для других модулей, симулятор «человека» с известной
истиной для проверки оценок. Код: `src/dataopen/bioprofile/`, CLI: `dataopen bioprofile ...`.

**Граница модуля.** Это **измерение**: движок читает движения мыши игрока и выход детектора (`KeypointArray`) и накапливает профиль. Он не
формирует ввод, не двигает курсор и не нажимает кнопки, и такого выхода в нём нет. Другие модули читают профиль только как данные.

## 0. Честный статус

| Что | Статус |
|---|---|
| Движок, профиль, хранение, интерфейс чтения, адаптер детектора, симулятор | **Реализовано и проверено тестами** (`tests/test_bioprofile.py`), в том числе против симулятора с известной истиной: T_motor по эпизодам: смещение ≈ −1.6 мс, разброс ≈ 2 мс, V_max ±1%, D_brake ±0.01, overshoot ±0.005, err_final: 90% эпизодов в пределах 0.08°, фазовая задержка ±1 мс, частота микро-поправок ±0.1 Гц, усталость ±15%. |
| Точность на **живых людях** | **Не проверено.** Симулятор моделирует *форму* движений (минимум-рывок, пауза, коррекция, слежение с задержкой и колебанием), а не записанную человеческую моторику. Реальная мышь, сенсор, частота опроса, реальные цели и паттерны фатига дадут другие числа; все пороги ниже **начальные значения для калибровки**, а не результат измерений на людях. |
| Единицы | `deg_per_count` (чувствительность мыши) **обязан быть правильным**: все скорости и расстояния в градусах считаются через него. `fov_h_deg` адаптера так же. |
| Что движок не знает | куда смотрит игрок (цель выбирается как ближайшая к перекрестию), сколько реально прошло от показа кадра до глаз (поправка `latency_comp_us` задаётся, по умолчанию полкадра 240 Гц). |

## 1. Вход

```python
eng = BioProfileEngine(EngineConfig(deg_per_count=0.02), profile=stored_or_None)
eng.on_mouse(t_us, dx, dy)          # сырые относительные счёты, по событиям (тишина = рука неподвижна), >= 1 кГц желательно
eng.on_target(t_us, TargetObs | None)   # кадр детектора; None = «никого не нашли», именно такие кадры двигают время, пока цели нет
eng.subscribe(fn)                   # fn(ProfileState) после каждого завершённого эпизода
```

`TargetObs(t_us, x_deg, y_deg, vis, degraded, radius_deg)`: цель в углах от перекрестия (вправо/вниз положительны), видимость 0..1, флаг
«дым/шум/низкий контраст», угловой радиус зоны прицеливания (допуск попадания). `DetectorAdapter` делает это из `KeypointArray`
рантайма: рectилинейная камера `atan(dx / f)`, `f = (W/2)/tan(fov/2)`, прицельная точка схемы (`head_center`), выбор цели, ближайшей к
перекрестию, развёртка 32-битного `timestamp_us` (оборот каждые 71.6 мин), `FLAG_EMPTY_ERROR` рантайма даёт «нет наблюдения».

Время движка это сетка 1 мс: счёты суммируются по миллисекундам; ошибки ввода (NaN, время назад больше 5 мс, абсурдные счёты) отбрасываются и
считаются (`dropped_samples`), а долгая тишина (> 2 с) не прокручивается по миллисекундам (3 часа молчания стоят меньше 0.5 с).

## 2. Конечный автомат сценариев

```
IDLE ──цель появилась, рука неподвижна──► ARMED ──первое движение──► MOVING ──скорость упала──► SETTLE ──тишина/таймаут──► TRACK | IDLE
  │                                          │                                                     │
  │                                          └─нет движения t_max──► lapse (miss)                  └─новое движение, до цели далеко──► MOVING (коррекция, не больше 1)
  ├─цель появилась, рука уже движется, цель далеко──► CENSORED (время реакции не измерить: ничего не учим)
  └─цель близко (< r_track), рука следует за ней──────────────────────────────────────────────────► TRACK ──цель исчезла/окно полно──► IDLE
```

Сценарий это **основная метка + модификаторы**, потому что «внезапное» и «плохая видимость» не исключают флик:

| Метка | Определение (пороги в `EngineConfig`, начальные) |
|---|---|
| `wide_flick` | расстояние до цели при старте ≥ `d_flick` (10°) и пик скорости ≥ `v_flick_min` (120°/с) |
| `micro_track` | цель ближе `r_track` (5°), рука следует ≥ `track_min_ms` (400 мс) |
| `surprise` (модификатор) | цель появилась, а 200 мс до этого средняя скорость руки ≤ `v_still` (8°/с) и максимум ≤ 3·`v_still` |
| `low_vis` (модификатор) | `vis < 0.5` или `degraded` в момент появления |

Сценарии ошибок (частоты в профиле, скользящее среднее по эпизодам с весом `rate_alpha` = 0.04):

| Ошибка | Определение | Начальный порог |
|---|---|---|
| `overshoot` | основное движение прошло цель на > 15% дистанции | `overshoot_err` |
| `undershoot` | основное движение остановилось, не дойдя на > 20% | `undershoot_err` |
| `direction` | первые 10% пути (≥ 1°) идут под углом > 35° к направлению на цель | `direction_err_deg` |
| `miss` | после движения (и одной коррекции) рука стоит дальше радиуса цели | `radius_deg` |
| `lapse` | цель на экране, а движения нет `t_max` (1200 мс) | `t_max_ms` |
| anticipation | «реакция» быстрее `t_min_ms` (100 мс): не реакция на цель; считается отдельно и **не попадает** в T_motor | `t_min_ms` |

Не больше одной коррекции приписывается флику; любое движение после неё это уже слежение. Пауза между подвижками одного флика
допускается до `still_final_ms` = 160 мс.

## 3. Метрики и их определения

| Метрика | Как считается |
|---|---|
| **T_motor** | от появления цели до начала движения. Появление = время захвата первого кадра с целью минус `latency_comp_us`. Начало движения: порог `max(v_on, μ_b + 5σ_b)` (μ_b, σ_b по 200 мс покоя до появления) должен держаться 6 мс подряд, затем откат назад по истории до последнего бина выше шумового пола `max(3°/с, μ_b + 2σ_b)`. |
| **V_max** | пик скорости (скользящее среднее 5 мс) основной подвижки флика, °/с |
| **D_brake** | оставшееся до цели расстояние в момент пика скорости (начало торможения) / дистанция флика: безразмерно, поэтому не зависит от расстояния |
| **overshoot** | `max(0, (макс. проекция смещения на направление к цели − D0) / D0)` за основную подвижку |
| **err_final** | расстояние до цели, когда рука остановилась (после основной подвижки или единственной коррекции), до того как цель поедет дальше |
| **phase lag** | задержка максимума взаимной корреляции скорости цели и скорости мыши в окне слежения, 0..300 мс шагом 5 мс с параболическим уточнением; считается только если скорость цели ≥ 4°/с и корреляция ≥ 0.5 (у неподвижной цели фазовой задержки нет, и движок не придумывает её) |
| **jitter** | остаток `путь мыши − путь цели(t − lag)` после вычитания полинома 2-й степени (сдвиг и медленный дрейф); спектр с окном Ханна в полосе 3–16 Гц. Частота = энергетический центр полосы, амплитуда = `√(2·P_полосы)` (пик синусоиды с такой мощностью) |

Целевой путь строится из наблюдений: `мир = e_наблюдения + вид(t_кадра)`, поэтому движение руки между кадрами не портит оценку цели; шум
детектора сглаживается (5 отсчётов, края дополняются, а не обнуляются: обнуление давало ложные выбросы в спектре).

**Точность T_motor и её смещение.** Разрешение 1 мс, кадры детектора 4.2 мс. Цель появляется между кадрами и детектор видит её на 0..4 мс
позже, чем её увидел человек (в среднем 2 мс; `latency_comp_us` это прибавляет). Начало движения ищется по порогу скорости, и порог
срабатывает позже настоящего начала на время разгона (≈ 6 мс при пороге 3°/с); поэтому момент начала уточняется экстраполяцией
`√скорость` (скорость растёт примерно квадратично) назад к нулю. На симуляторе остаётся смещение ≈ −2 мс при разбросе ≈ 2 мс.
При **плохой видимости** детектор видит цель ещё позже, и это **занижает** измеренное T_motor на эту задержку (в симуляторе
+80 мс настоящей медлительности превращаются в +35 мс измеренных): `t_motor_lowvis` хранится отдельно и его **нельзя сравнивать
напрямую** с нормальным; сравнивать надо динамику внутри одной корзины. Это ограничение измерения, не округления.

## 4. Скользящее окно

`RollingMedianSigma(window=32, min_n=8)`: точная медиана и σ = 1.4826·MAD по последним 32 значениям (отсортированный список + очередь,
вставка за O(log n + n), n ≤ 64). Медиана и MAD, а не среднее и std, потому что метрики тяжелохвостые (один провал 900 мс среди 220 мс
портит среднее и удваивает std). Значения дальше `6σ` от медианы **винсоризуются** (обрезаются и считаются), не отбрасываются: настоящий сдвиг
распределения всё равно подхватывается за несколько отсчётов (проверено тестом). Если больше половины значений совпадают (MAD = 0), σ берётся из IQR.

После перезапуска окно **засевается** из сохранённого (медиана, σ) квантильными точками нормального распределения (до 8) и счётчик `n`
наследуется, поэтому первый выброс после старта не ломает статистику, а свежие данные вытесняют засев за 32 эпизода.

## 5. Усталость

Эпизоды группируются в блоки по 2 минуты сессии; каждый блок это медиана (минимум 3 значения): T_motor (surprise, нормальная видимость) и
err_final (флики). Тренд по блокам это **Theil–Sen** (медиана попарных наклонов), поэтому один плохой блок не создаёт и не скрывает
тренд (тест). `z = наклон / SE`, SE приблизительная: робастный разброс остатков, формула МНК, ×1.2; это «сколько стандартных ошибок от нуля», а
не откалиброванное p-значение. Нужны ≥ 4 блока и ≥ 8 минут. `fatiguing` = оба наклона положительны с z ≥ 2: **флаг, а не диагноз**
(игрок мог поменять оружие). Пауза ≥ 5 минут (`rest_gap_s`) заканчивает сессию, усталость считается заново (тест).

## 6. Профиль (`BioProfileV1`, 98 байт, little endian, packed)

| Поле | Байт | Содержимое |
|---|---|---|
| заголовок | 16 | `magic` 'BIOP', `version`, `flags` (fatigue_valid, clean), `size`, `profile_id` (случайный, не личность), `generation` |
| калибровка | 6 | `deg_per_count` f32, `latency_comp_us` u16 |
| 9 метрик × 5 | 45 | медиана, σ, n (по метрике; n насыщается на 255): t_motor, t_motor_lowvis, v_max, d_brake, overshoot, phase_lag (знаковая), jitter_hz, jitter_amp, err_final; единицы и масштабы в `profile.STATS` |
| усталость | 12 | `session_s`, наклон T_motor (0.1 мс/ч), наклон ошибки (0.001°/ч), z (0.1), базовый T_motor |
| счётчики | 10 | flick, track, surprise, lowvis, anticipation (u16) |
| частоты ошибок | 5 | overshoot, undershoot, direction, miss, lapse, 0..255 = 0..1 |
| CRC32 | 4 | zlib CRC32 по первым 94 байтам |

Читатель сначала проверяет размер, magic, CRC и версию: версия новее своей это `ProfileVersionError` (данные целые, но не его), всё
остальное `ProfileError`. Тест переворачивает **каждый** бит по одному байту и требует отказа. Заголовок для C (`dataopen bioprofile header`)
генерируется из той же структуры, тест сверяет смещения всех полей с компилятором.

## 7. Хранение и интерфейс чтения

* `ProfileStore(path)`: два файла-слота `.a` и `.b`, пишутся поочерёдно (во временный файл, `fsync`, атомарное переименование, `fsync`
  каталога). Порванная запись или битый бит портят только записываемый слот; `load()` возвращает новейший слот, прошедший проверку,
  иначе `None`. Слот, записанный **более новой версией**, никогда не перезаписывается (`save()` бросает исключение).
* `ProfilePublisher(name)` / `ProfileReader(name)`: профиль в shared memory (seqlock + CRC32 почтового ящика рантайма). `read()` возвращает
  проверенный `ProfileView` с возрастом, либо `None`; на мусор не бросает.
* `ProfileView` (только чтение): `stat(name)` → `Stat(median, sigma, n)`; `confident(name, min_n=12)`; `percentile(name, p)` (нормальное
  приближение: время реакции скошено вправо, это приближение); `fatigue`, `counts`, `error_rates`, `as_dict()`.

```python
eng.subscribe(publisher.publish)               # процесс-измеритель
view = ProfileReader("bioprofile").read()      # любой другой модуль
if view and view.confident("t_motor") and view.age_ms < 5000:
    p05 = view.percentile("t_motor", 0.05)     # типичная нижняя граница времени реакции этого игрока
```

Потребитель обязан смотреть на `n`/`confident`/`age_ms`: у нового игрока профиль пуст (`Stat.valid == False`), и это надо отличать от «0».

`bioprofile/progress.py` даёт для телефона простое «сколько собрано»: `profile_progress(view)` → `fill` (среднее `min(1, n/30)` по шести статистикам, нужным помощи и подавителю дрожи) и готовность слоёв. Это счётчик наблюдений, не статистическая сходимость и не оценка качества ([PWA.md](PWA.md)).

## 8. Команды

```
dataopen bioprofile simulate --minutes 60 --fatigue-ms-per-h 40 --out me.prof   # симулятор -> движок -> профиль + сравнение с истиной
dataopen bioprofile show me.prof                                                # прочитать профиль (A/B-слоты, CRC)
dataopen bioprofile header --out bioprofile.h                                   # заголовок для C
```

## 9. Ограничения

* Это модель по описанию задачи, пороги начальные. Любой серьёзный запуск начинается с калибровки на записях реальных людей: `v_still`,
  `v_on`, `d_flick`, `r_track`, `t_min_ms`, пороги ошибок (у профессионала недолёт 20% это норма, у человека с тремором нет).
* Выбор цели «ближайшая к перекрестию» это эвристика; при нескольких целях в кадре движок может следить не за той, за которой следит игрок.
* Метрики слежения требуют, чтобы цель двигалась (≥ 4°/с); для неподвижных целей phase lag отсутствует, и это нормально.
* Цели, которые двигались во время флика, считаются неподвижными в пределах флика (динамика цели учитывается после него, в слежении).
* Не измеряется: нажатия кнопок, время выстрела, отдача, асимметрия осей, влияние DPI/частоты опроса на сглаживание; расширение
  идёт добавлением метрики в `STATS` (поле, масштаб) и версии структуры.
* Профиль хранит поведение конкретного человека: его нужно хранить локально и показывать этому человеку (`profile_id` случайный, но
  статистика моторики сама по себе чувствительные данные).
