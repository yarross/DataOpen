# Заводской провижининг, идентичность устройства, восстановление и четыре уровня сброса

Устройство в поле не должно стать «бомбой замедленного действия»: на заводе каждый экземпляр сам получает уникальные ключи, серийный номер и проверенный fail-safe без ручной магии, а когда в поле что-то ломается, человек не остаётся без мыши и экрана, а устройство возвращается в рабочее состояние без пайки. Этот документ фиксирует **логику и потоки**; загрузчика, OTP/eFuse, secure element и оснастки стенда нет, они смоделированы правилами и проверены тестами. Код: `src/dataopen/provisioning/`, команды `dataopen prov …` и `dataopen recover …`.

## 0. Честный статус и границы

| Что | Статус |
|---|---|
| Записи устройства (серийный номер с контрольным символом, аттестация производителя, сертификат DAK, служебный токен), цепочка доверия производитель → DAK → карточка владельца, стадии жизненного цикла, карта хранения, матрица четырёх уровней сброса | **Реализовано как формат, логика и тесты**, есть эталонный вектор аттестации (`tests/data/attestation_v1.json`) |
| Заводская процедура целиком: прошивка, проверки стенда, рождение ключей, аттестация, запись один раз, блокировка, наклейка, отчёт, карантин при отказе | **Реализовано как симуляция** (HSM это ключ в памяти, база серийников это счётчик) |
| Проверки стенда для мыши, Panic (короткого и длинного, с прошивкой и без неё), watchdog, режима MODE, пропадания питания | **Выполняются на настоящем C-ядре моста** (`ctl.sim.World`); неисправности внедряются, стенд их ловит |
| Проверки питания, видео, BLE, светодиодов и secure element | **Параметрические модели с внедрением отказов**: измерять сигналы здесь нечем |
| Цепочка восстановления: цепочка загрузки как модель, система восстановления, золотой образ, загрузка через ROM, перепрошивка MCU со стороны SoM, полный возврат (L4) с токеном | **Реализовано как модель и тесты** (`provisioning/recovery.py`, `service.py`) |
| Показ серийного номера и цепочки в приложении, политика «файлы только для подтверждённых карточек» в шлюзе | **Реализовано** (`device.serial`, `Card.device`, `require_attested`) |
| Загрузчик, secure boot, реальные OTP/eFuse/RPMB, secure element, маскром SoM, ISP-линия MCU, сервисные линии данных на порту питания, кнопка RECOVERY, система восстановления как образ | **Не сделано** (только правила и модель; в спецификации железа добавлены детали, `docs/HARDWARE.md`) |
| Оснастка стенда (pogo-площадки, экранированный бокс, эмуляторы мыши и монитора, оптические датчики), база серийников, настоящий HSM, подпись отчёта станцией | **Не сделано** |
| Служебный BLE-сервис в режиме восстановления (запустить восстановление с телефона) | **Не сделано**: описан, в протокол CtlLink не добавлен |
| Аудит, пентест, сертификация, процесс жизненного цикла ПО для медицинских изделий | **Не проводились** |

## 1. Принципы

1. **Секреты рождаются в устройстве и никуда не уходят.** Станция и производитель получают только открытые ключи и доказательство владения; ни ключа устройства, ни ключа владельца у них нет.
2. **Серийный номер, ключ подлинности (DAK) и аттестация неизменяемы** никаким пользовательским и сервисным сбросом; ключи владельца (Device Public ID) меняются заводским сбросом.
3. **Необратимое делается последним.** Блокировка OTP, ключевого слота, отладки и secure boot идёт после всех проверок и проверки цепочки.
4. **Любое сомнение значит карантин:** плата, не прошедшая шаг, не получает наклейку, не попадает в базу выпущенных, уже выданная аттестация отзывается.
5. **Аппаратный bypass важнее любого восстановления.** Что бы ни было сломано, мышь и экран идут напрямую; восстановление может требовать кнопок и компьютера, но не подключения устройства «в разрыв» навсегда.
6. **Каждый шаг назад к заводскому состоянию требует присутствия:** кнопка на устройстве, а для L4 ещё и подписанный токен на конкретный серийник.
7. **Откат запрещён.** Ни один уровень не снижает порог анти-отката; золотой образ старше порога не используется.

## 2. Factory Provisioning: пошаговый процесс

Станция ведёт одну плату от «пустой» до «готова к упаковке». Участвуют: устройство (`DeviceAgent`), стенд (`Jig`), HSM производителя (`VendorHsm`), база серийников (`SerialDb`).

```
станция                         устройство                         HSM производителя
  │ 1 flash: образы (подписаны) ─►│                                    │
  │ 2 selftest: стенд ───────────►│ mark_tested → DEV_TESTED           │
  │ 3 ◄──────── begin(): DAK рождён в secure element, ключи владельца, доказательство владения (подпись DAK)
  │ 4 серийник из базы ────────────────────────────────────────────────►│ проверка доказательства, уникальность
  │                                                                     │ серийник↔DAK↔плата, подпись аттестации
  │ 5 ◄────────────────────────────────────────────── аттестация ───────┤
  │ 5 accept(): проверка подписи, DAK и платы ─► запись один раз, PROVISIONED
  │ 6 verify: цепочка производитель → DAK → карточка владельца, быстрый тест bypass
  │ 7 finalize(хэш отчёта) ──────►│ OTP, ключевой слот, отладка, secure boot заблокированы, SHIPPED
  │ 8 наклейка: серийник + QR      │                                    │ 9 mark_shipped
```

<!-- fp:steps -->
| № | шаг | что происходит |
| --- | --- | --- |
| 1 | `flash` | Прошить MCU моста (оба банка), SoM (оба банка) и золотой образ; каждый образ проверяется подписью производителя |
| 2 | `selftest` | Стенд проверяет питание, реле, мышь, Panic, watchdog, пропадание питания, видео, BLE, светодиоды; всё прошло → DEV_TESTED |
| 3 | `keygen` | Устройство само рождает DAK внутри secure element и ключи владельца; наружу идут только открытые ключи и доказательство владения |
| 4 | `attest` | HSM проверяет доказательство, выдаёт серийный номер из базы и подписывает аттестацию (серийник, hw_id, DAK, плата) |
| 5 | `record` | Устройство проверяет аттестацию и пишет запись один раз в OTP / заблокированный слот; → PROVISIONED |
| 6 | `verify` | Станция читает запись обратно, проверяет цепочку производитель → DAK → карточка владельца и повторяет быстрый тест bypass |
| 7 | `lock` | Хэш отчёта в OTP; OTP, слот ключей, отладочный порт и secure boot блокируются (необратимо); → SHIPPED |
| 8 | `label` | Печать наклейки: серийный номер и QR (карточка рождения с цепочкой) |
| 9 | `release` | HSM отмечает серийник выпущенным; отчёт сохраняется в базе станции |
<!-- /fp:steps -->

**Проверки стенда** (один экземпляр платы, питание от пружинных контактов, экранированный бокс):

<!-- fp:checks -->
| проверка стенда | что измеряется | допуск |
| --- | --- | --- |
| `rails` | питание D0..D4: VEXT, 3V3_AON, 3V3, 1V8, 1V2 | ±5 % |
| `secure_element` | secure element отвечает | отвечает |
| `mouse_through_bridge` | мышь (эмулятор) проходит через мост: 20 отчётов | 20 из 20 |
| `panic_soft` | короткое Panic: помощь выключена, указатель не пропал | PASSTHRU, причина PANIC, маршрут через мост |
| `panic_long` | удержание Panic: контакты отпускаются | ≈ 2,9-3,4 с |
| `panic_loop_hardware` | то же, но прошивка о нажатии не знает: работает только аппаратная RC-петля | ≈ 2,9-3,4 с |
| `watchdog_hang` | стенд останавливает кики: контакты отпускаются | ≤ 130 мс |
| `mode_switch` | ползунок MODE на BYPASS | ≤ 20 мс |
| `power_cut_bypass` | стенд отключает VEXT: мышь работает напрямую | ≤ 20 мс и мышь работает |
| `video_direct` | без питания видео напрямую, захват сигнала монитором | ≤ 3 с, EDID не изменён |
| `ble_visible` | BLE-реклама видна в экранированном боксе | ≥ -75 дБм |
| `indication` | RGB, светодиоды слотов, BYPASS и зуммер отвечают | все рисунки видны |
<!-- /fp:checks -->

Первые шесть строк электрических проверок исполняются на настоящем ядре моста; допуски взяты из `hw/failsafe.py` (окно watchdog 100 мс, RC петли Panic 3 с, время отпускания реле 8 мс как допущение). Проверка `panic_loop_hardware` намеренно не сообщает прошивке о нажатии: так проверяется **вторая линия обороны**, аппаратная петля, независимо от кода.

**Что записывается куда** (в железе это зависит от выбранных микросхем; здесь правило, не раскладка адресов):

- **secure element:** DAK (рождается внутри), ключи владельца (в изделии тоже в нём; в симуляции файл `FileKeyStore`), заблокированный слот с записью устройства.
- **OTP / eFuse:** хэш ключа производителя (корень доверия для загрузки, токенов, образов и аттестации), журнал стадий жизненного цикла (только добавление), порог анти-отката, биты блокировки отладки и secure boot.
- **eMMC boot-раздел (аппаратная защита записи):** загрузчик и золотой образ (система восстановления + заводская прошивка); **eMMC данных:** профили, настройки, список доверенных (зашифрованы ключами слотов), банки A/B.
- **QSPI-флеш моста:** два банка прошивки MCU и загрузчик.
- **Не записывается нигде на плате, только в базе производителя:** копия аттестации, журнал выпуска, отзывы, хэш отчёта (его копия в OTP).

Формат записей (`provisioning/records.py`):

- **Серийный номер** `DOn-yyww-sssss-c`: цифра SKU, год и неделя выпуска, пять цифр порядкового номера и один контрольный символ по простому модулю 31, который ловит любую одиночную опечатку в цифре (проверено перебором). Ввод с наклейки терпим к регистру, пробелам и похожим символам.
- **Аттестация** (подпись производителя, домен `DOATT1`): `{серийник, hw_id, DAK, хэш платы, дата, идентификатор производителя}`; канонический JSON.
- **Сертификат устройства** (подпись DAK, домен `DODEV1`): `серийник ‖ дайджест карточки владельца`; лежит в карточке в необязательном блоке `device` и **не входит в самоподпись карточки**, поэтому старые карточки остаются действительными.
- **Доказательство владения** (подпись DAK, домен `DOPOP1`): над одноразовым числом, DAK, платой и hw_id. Домены разделены: secure element подписывает только `DODEV1` и `DOPOP1`, а подписи в доменах `DOATT1` и `DOSVC1` ставит только производитель.
- **Токен сервиса** (подпись производителя, домен `DOSVC1`): `серийник | действие | nonce`; nonce выдаёт само устройство (часов нет), токен одноразовый.

## 3. Идентичность устройства

<!-- fp:identity -->
| что | для чего | где хранится | можно ли сбросить |
| --- | --- | --- | --- |
| серийный номер и запись | пишется на заводе один раз; наклейка | OTP / заблокированный слот secure element | **неизменяема** никаким сбросом |
| DAK, ключ подлинности | рождается в secure element; подписывает карточку владельца и доказательство владения | secure element, наружу не выходит | **неизменяем** никаким сбросом |
| аттестация производителя | подпись производителя над (серийник, hw_id, DAK, плата) | в записи устройства; копия в базе производителя | **неизменяема** |
| ключи владельца = Device Public ID | привязка пакетов `DOBS`, подпись карточки | secure element / хранилище ключей | **меняются** заводским сбросом (L3) и возвратом (L4) |
| DAK-сертификат карточки | связывает серийник с текущей карточкой владельца | в карточке; подписывается заново при смене ключей | пересоздаётся при L3 |
<!-- /fp:identity -->

**Цепочка доверия:** ключ производителя (в OTP только хэш) → аттестация `(серийник, hw_id, DAK, плата)` → сертификат DAK над текущей карточкой владельца. Получатель, знающий открытый ключ производителя, отличает настоящее устройство серийника S от страницы или скрипта, выдумавшего карточку: это закрывает оговорку «подмена карточки получателя» из `SECURITY.md`. Проверка `verify_chain` отвергает чужого производителя, чужое оборудование, карточку без блока, сертификат от чужого DAK и **настоящий сертификат на чужих ключах**.

**На наклейке серийный номер** (он не меняется) и QR с карточкой рождения и цепочкой. Номер владельца (Device Public ID) после заводского сброса другой, поэтому он показывается в приложении отдельной строкой «Номер владельца».

**Жизненный цикл** (только вперёд, лог добавляется даже после блокировки OTP):

<!-- fp:lifecycle -->
| стадия | смысл | дальше |
| --- | --- | --- |
| `BLANK` | плата прошита, ничего не записано | `DEV_TESTED` |
| `DEV_TESTED` | стенд проверил плату | `PROVISIONED` |
| `PROVISIONED` | запись устройства сделана, OTP ещё открыт | `SHIPPED` |
| `SHIPPED` | OTP и ключи заблокированы, готово к упаковке | `IN_FIELD`, `RMA` |
| `IN_FIELD` | первое включение у владельца | `RMA` |
| `RMA` | на сервисе: возврат к заводскому состоянию | `PROVISIONED` (только по токену производителя) |
<!-- /fp:lifecycle -->

## 4. Сценарии Recovery / Unbrick

**Слои, от никогда не отказывающего к требующему компьютера:**

0. **Аппаратный bypass** ([HARDWARE.md](HARDWARE.md)): мышь и монитор напрямую, что бы ни было сломано, без питания, при зависшей прошивке и при мёртвой системе. Единственное, что слой 0 не покрывает, это залипшие контакты реле.
1. **MCU моста:** два банка и загрузчик с пробой; если оба плохи, его ROM (последовательный загрузчик) ждёт, а SoM сам пишет подписанный образ по линии BOOT / RESET / UART (ISP). Компьютер не нужен.
2. **SoM:** банки A/B с пробой (см. [SLOTS.md](SLOTS.md) раздел 8); если оба банка плохи или человек удерживает **SLOT + CONFIRM при подаче питания ≥ 5 с**, загружается **система восстановления** из золотого образа (подписана, только чтение), светодиод RECOVERY, мышь и экран напрямую. Нажатие CONFIRM пишет оба банка заново. Раздел данных не трогается, профили целы. Компьютер не нужен.
3. **Загрузка через ROM SoM** (его нельзя стереть): если повреждены загрузчик или золотой образ, ROM ждёт утилиту поддержки. Нужны компьютер на **порту питания** (его линии данных ведут на USB OTG SoM, в обычной работе не используются; питание от компьютера в этом режиме подаётся только на D0..D2) и **утопленная кнопка RECOVERY** (скрепка). Утилита пишет загрузчик, золотой образ и банки; раздел данных остаётся.
4. **Возврат производителю:** умерли secure element или eMMC, SoM мёртв. Мышь и экран работают напрямую; профили теряются (ключи были в элементе).

| событие | что видит человек сразу | как вернуть | компьютер | профили |
| --- | --- | --- | --- | --- |

(Таблица считается моделью `recovery.run`: поведение при сбое, шаги, нужен ли компьютер и что с профилями получены из логики, а не написаны вручную; тест перебирает все сочетания повреждений.)

Дополнительно:

- **Неудачное OTA.** Обновление ложится в неработающий банк и не запускается само (нужны два шага и кнопка); новая версия подтверждает себя только при здоровом мосте, иначе после трёх загрузок автоматически возвращается прежний банк. Обрыв питания во время записи оставляет работающий банк нетронутым (проверено в `tests/test_ctl_update.py`).
- **Золотой образ старше порога анти-отката.** Система восстановления отказывает (откат запрещён), а не нарушает порог; поддержка загружает новый золотой образ (подписанный, не ниже порога). Это известное неудобство схемы: золотой образ надо обновлять вместе с каждым обновлением безопасности. Как именно (подписанная служебная операция) не реализовано.
- **Профили.** Живут в разделе данных под ключами из secure element. При переустановке образов они сохраняются; при потере раздела возвращаются из резервной копии `.dobundle` **на том же устройстве** (копия «для себя» открывается только его ключами). При смерти secure element копия бесполезна; страховка на такой случай — файл «для другого устройства», сделанный заранее для запасного.
- **Потерян телефон.** Удержание CONFIRM 3-10 с открывает окно сопряжения на 120 секунд; заводской сброс (L3) забывает все телефоны.
- **Светодиод** состояния RECOVERY отличим по рисунку:

| --- | --- | --- | --- |
| **RECOVERY** | magenta | вкл 600, выкл 150, вкл 100, выкл 150, вкл 100, выкл 900 мс | пурпурный, одна длинная и две короткие вспышки: система восстановления, мышь и экран напрямую, нажмите CONFIRM, чтобы восстановить прошивку |

## 5. Factory Reset / Clear Profile / полный возврат к заводскому состоянию

Четыре уровня, у каждого своё имя, способ вызова и граница. Что каждый стирает или оставляет, написано в таблице карты хранения выше (колонки L1-L4) и проверено на настоящем шлюзе (`tests/test_prov_levels.py`).

<!-- fp:levels -->
| уровень | название | как вызывается | что затрагивает |
| --- | --- | --- | --- |
| **L1** | Очистить слот | приложение (два шага + кнопка) · `slot.clear` | активный слот |
| **L2** | Очистить все профили | приложение · `erase.profile`; удержание CONFIRM 10 с | все слоты, список доверенных, ключ диска |
| **L3** | Заводской сброс | приложение · `factory.reset`; удержание CONFIRM 20 с | всё личное + новые ключи владельца + забыть телефоны |
| **L4** | Полный возврат к заводскому состоянию | только режим восстановления: токен производителя + присутствие | L3 + образы обоих банков SoM и MCU из золотого образа |
<!-- /fp:levels -->

- **L1, очистить слот.** Профиль, уровни, имя и манифест активного слота; ключ слота заменяется, остальные слоты побайтно целы. Помощь выключается. Это «очистить профиль» в самом узком смысле.
- **L2, очистить все профили** (команда `erase.profile`, в приложении «Стереть личные данные (все слоты)»): все слоты, настройки, список доверенных и ключ диска. Владелец, сопряжённые телефоны и прошивка остаются; собственная резервная копия по-прежнему открывается.
- **L3, заводской сброс** (`factory.reset`): всё личное плюс **новые ключи владельца и новый Device Public ID** (старые файлы и копии перестают открываться), забываются все телефоны (обратный вызов `on_forget`). **Серийный номер, DAK, аттестация, прошивка, золотой образ, порог анти-отката не меняются**; Device Public ID получает свежий сертификат от того же DAK. Подходит при передаче устройства другому человеку.
- **L4, полный возврат** (`dataopen recover full-return`): L3 плюс оба банка SoM и оба банка MCU переписываются из золотого образа. Только из режима восстановления: подписанный токен производителя на этот серийник и nonce этого устройства плюс присутствие (кнопка). Токен одноразовый; неудачная попытка (нет руки, не тот серийник, золотой образ старше порога) его не тратит; журнал стадий получает `RMA → PROVISIONED → SHIPPED`. Порог анти-отката и серийник не сбрасываются.

L1-L3 вызываются из приложения двумя шагами плюс кнопка на устройстве; L2 и L3 также удержанием CONFIRM 10 и 20 секунд (само удержание является подтверждением). **L4 из приложения и кнопками недоступен.**

## 6. Инструменты

<!-- fp:tools -->
| кто | инструмент | что делает |
| --- | --- | --- |
| завод | `dataopen prov provision` | станция: прошивка, стенд, ключи, аттестация, запись, блокировка, наклейка, отчёт |
| завод | `dataopen prov verify` | проверка цепочки производитель → DAK → карточка по каталогу устройства |
| завод | HSM / база серийников | подпись аттестаций и токенов, уникальность серийник ↔ DAK ↔ плата, отзыв (в симуляции: ключ в памяти) |
| поддержка | `dataopen recover simulate` | разбор сценария: что видит человек, что делать, нужен ли компьютер |
| поддержка | `dataopen recover full-return` | L4: токен + присутствие, банки из золотого образа, личное стёрто |
| человек | кнопки SLOT + CONFIRM при подаче питания | система восстановления без компьютера |
| человек | приложение (PWA) | L1/L2/L3 (два шага + кнопка), серийный номер, резервные копии |
<!-- /fp:tools -->

**Заводской набор:** станция (`prov provision`: один вызов ведёт плату по девяти шагам и печатает проверки, либо карантин с причиной), стенд с оснасткой (в симуляции `Jig`, на настоящем ядре моста), HSM и база серийников. `prov verify` проверяет цепочку готового устройства. Неисправности можно внедрить опцией `--fault` (`relay_stuck`, `watchdog_dead`, `panic_stuck`, `ble_silent`, …), чтобы убедиться, что стенд их ловит.

**У конечного пользователя и поддержки:** никакой установки. Человек пользуется кнопками (аккорд восстановления, окно сопряжения, удержание) и приложением (сброс L1-L3, резервные копии, серийный номер). Поддержка пользуется утилитой `recover` (в симуляции `dataopen recover simulate | scenarios | full-return`; на изделии это был бы такой же скрипт, говорящий с ROM через порт питания).

**Что можно симулировать уже сейчас:** весь заводской поток на настоящем ядре моста, все сценарии восстановления и их исходы, L1-L4 на настоящем шлюзе, токены и их отказы, отзыв и дубликаты в HSM.

## 7. Стыковка с существующим

| Часть | Как ложится |
|---|---|
| **Слоты** | L1 очищает слот (замена эпохи ключа слота); L2/L3 стирают все слоты; система восстановления не трогает раздел данных, поэтому слоты переживают переустановку образов. `slot.clear`, `erase.profile`, `factory.reset` остались теми же командами |
| **Защищённые пакеты** | ключи владельца теперь подписаны DAK: `GET identity` отдаёт карточку с цепочкой; при `require_attested` файл «для другого устройства» делается только для карточки с действительной цепочкой (отказ `card_unattested`, нажатие кнопки не тратится); копия «для себя» после L3 не открывается (проверено) |
| **Dual-bank** | банки SoM и MCU пишутся из золотого образа при L4 и при восстановлении; самоподтверждение, пробные загрузки, анти-откат работают как раньше; золотой образ не может быть старше порога |
| **PWA** | строки «Серийный номер (как на наклейке)» и «Номер владельца» на странице «Ещё»; подсказки к L2/L3; текст отказа `card_unattested`; страница по-прежнему ничего не расшифровывает |
| **Аппаратный bypass** | не зависит ни от одного из этих механизмов; стенд проверяет его на каждой плате (в том числе без ведома прошивки) |
| **Secure element** | место для DAK, ключей владельца и записи устройства; интерфейс `KeyStore` и `SecureElementSim` (подписывает только два домена, секрет не отдаёт) |
| **Светодиод и панель** | новое состояние RECOVERY; аккорд SLOT + CONFIRM при подаче питания входит в режим восстановления (в модели `Unit.chord`) |

## 8. Что сознательно не сделано и ограничения

- Нет загрузчика, secure boot, OTP/eFuse, RPMB, настоящего secure element и маскрома; нет оснастки стенда, настоящего HSM, базы серийников, подписи отчёта станцией (в OTP хранится только его хэш).
- Проверки видео, BLE, питания и светодиодов параметрические; электрические проверки идут на модели, а не на плате: допуски (±5 %, 8 мс на реле) это допущения.
- Часов на устройстве нет: токены защищены одноразовым nonce, срока действия у них нет.
- Золотой образ нужно будет обновлять; процесс не реализован.
- Служебный BLE-сервис режима восстановления, сервисный порт на линиях данных порта питания и утопленная кнопка RECOVERY это предложения, не проверенные на плате (требуется ESD и защита порта, и аккуратная работа с питанием от компьютера).
- Резервная копия «для себя» не помогает при смерти secure element; страховка — заранее сделанный файл для запасного устройства.
- Не проводились аудит, пентест, сертификация; процесс обращения с ключом производителя (офлайн-HSM, ротация, отзыв ключа) только назван.
- Один производитель в хэше OTP: смена или ротация корня доверия не продумана.
