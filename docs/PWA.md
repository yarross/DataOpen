# Пульт управления с телефона: PWA, Web Bluetooth и шлюз на модуле

Клиент для людей с тремором, последствиями инсульта и ДЦП, которым трудно ставить программы и возиться с драйверами: страница в браузере, которая после первого открытия
**работает без интернета**, без аккаунтов и без трекеров, и по Bluetooth управляет устройством. Всё критичное (профиль, калибровка, настройки, ключи связи) живёт на устройстве.
Код: `pwa/` (клиент, чистый JS без сборки), `src/dataopen/ctl/` (шлюз и протокол на модуле), `src/dataopen/bioprofile/progress.py`; CLI: `dataopen ctl ...`.

## 1. Принципы

1. **Телефон только пульт.** Устройство работает само; потеря связи, закрытая вкладка, сели батарея и сломанный телефон ничего не меняют.
2. **Оболочка безопасности фиксирована, тело динамическое.** Статус, «Выключить помощь», «Железный bypass» строятся из 20 байт `status` и не зависят от манифеста: они работают с любой прошивкой, которая говорит на этом статусе.
3. **Понизить бесплатно, повысить пробно.** Всё, что уменьшает помощь, действует сразу и навсегда. Всё, что увеличивает, действует сразу, но возвращается само, если человек не нажал «Оставить».
4. **Устройство единственный авторитет.** Оно проверяет каждое значение по тому же манифесту, который отдало телефону.
5. **Телефон не присылает параметры, только смысл** («уровень 7 из 10»). Сырые блобы для моста строит шлюз, потому что только он знает профиль.
6. **Ни одного жеста.** Только нажатия на большие кнопки: ни перетаскивания, ни долгого нажатия, ни свайпов, ни двойных тапов, ни зависимости от скорости.

## 2. Архитектура

```
 телефон (Chrome, PWA, офлайн)             устройство
 ┌────────────────────────────┐   BLE GATT   ┌─────────────────── модуль (Linux) ───────────────────┐
 │ оболочка безопасности      │◄────────────►│ транспорт (BlueZ, вне объёма) ─► ctl.Gateway          │
 │   (из status, 20 байт)     │  CtlLink v1  │   сессия · состояние · манифест · файл настроек        │
 │ рисовальщик манифеста      │              │   Tuning (уровни→параметры) · калибровка · таймер отката│
 │ ru/en · кэш IndexedDB      │              │   ▼ BridgeLink (SPI): CMD, PARAMS_ASC/TREMOR, STATUS  │
 └────────────────────────────┘              │ ProfileStore (A/B) · BioProfile                       │
                                             └──────────────► мост (MCU): fail-safe, зажим, Panic ◄──┘
```

BLE-радио есть только у модуля (у моста его нет, связь с ним только SPI), поэтому пульт говорит с шлюзом на модуле, а шлюз с мостом. Если модуль умер, мост сам уходит в `PASSTHRU` по `STALE_LINK` через 0.5 с,
а телефон видит «нет связи». Мост остаётся единственным, кто решает, что реально происходит с указателем, и он умеет только вычитать (`|out| ≤ |in|`).

## 4. Протокол CtlLink v1 (`ctl/protocol.py`, `pwa/js/link.js`)

**GATT.** Свой сервис, четыре характеристики, все требуют шифрованного (спаренного) соединения. UUID-ы случайные и частные (в Bluetooth SIG ничего не регистрировалось): их надо сменить на свои перед выпуском.

| характеристика | свойства | что |
|---|---|---|
| `info` | read | 16 байт: версия, возможности, id устройства (4 байта), хэш манифеста (4), ревизия манифеста, подсказка размера чанка |
| `status` | read, notify | **ровно 20 байт**: помещается в ATT-пакет при MTU 23, значит читается без какого-либо согласования |
| `ctl_in` | write, write without response | чанки сообщений телефон → устройство |
| `ctl_out` | notify | чанки сообщений устройство → телефон |

**Статус (20 байт, little endian):** версия, мост слышен (0/1), режим моста (`HW_BYPASS`/`PROBE`/`PASSTHRU`/`ASSIST`), причина (индекс в таблице причин моста),
флаги (латч Panic, латч bypass, помощь хочет, калибровка, параметры живы, пробное включение, ПК видит мышь, связь по SPI, моста здоровье, мост слышен), готовность профиля 0..100,
биты готовности слоёв (помощь при движении, подавление дрожи, «дрожь слишком мала, не нужно»), ревизия состояния, ревизия манифеста, время работы **в минутах**, секунд до отката пробы, оба уровня,
**активный слот и маска слотов с профилем** ([SLOTS.md](SLOTS.md)).
Если мост не слышен 1.5 с, режим сообщается как «неизвестен», а не угадывается.

**Сообщение:** `версия u8 | тип u8 | req u16 | длина u16 | флаги u16 | тело | CRC32 u32` (zlib, по всему перед ним). Тело ≤ 16 КБ. Разбор строгий: любая ошибка размера, версии, длины или CRC даёт «не сообщение».
**Чанк:** 1 байт заголовка (0x80 первый, 0x40 последний, младшие 6 бит номер) и до `размер − 1` байт сообщения. Размер чанка согласуется в HELLO: телефон предлагает, **устройство выбирает не больше того, что оно
само может доставить** (для BLE это ATT MTU − 3; пока MTU неизвестен, 20). Телефон при ошибке записи откатывается на 20 и шлёт сообщение заново. Сборщик ограничен 16 КБ и 5 секундами между чанками: потерянный
чанк роняет одно сообщение, а не канал.

| тип | |
|---|---|
| HELLO / HELLO_R | версия, размер чанка, язык; ответ: id, прошивка, хэш манифеста, срок пробы |
| GET / DATA | `manifest`, `state`, `identity` (открытая карточка), `bundle` (с параметрами `for`: `self` или карточка получателя, и `scope`: `active` или `all`), `slots`, `firmware` |
| SET / ACT / CONFIRM / BUNDLE_PUT | значение; действие (двухшаговые требуют `confirmed`); оставить/вернуть; файл настроек |
| **STOP, HARD_BYPASS** | **пустое тело, одно сообщение, влезает в один 20-байтный чанк, принимаются до HELLO** |
| FW_BEGIN / FW_CHUNK / FW_END | образ прошивки по частям в неработающий банк ([SLOTS.md](SLOTS.md) раздел 8): канал A, система |
| PKG_BEGIN / PKG_CHUNK / PKG_END | пакет для слотов по частям (профиль, уровни, раскладка, веса модели) в каталог ожидания; заголовок и подпись проверяются с первым куском: канал B, [UPDATES.md](UPDATES.md) |
| ACK / ERR / EVENT / PING | `ERR` несёт код и ключ текста (`err.physical`, `err.bad_bundle.damaged` ...); `EVENT` несёт изменение состояния |

Изменение состояния уходит **до** ответа: когда `set()` завершился, состояние на телефоне уже новое. Если ревизия в `status` не совпала с известной, клиент сам перечитывает всё состояние (событие потерялось).
Очередь записи у клиента с приоритетом на уровне чанка: STOP встаёт перед следующим чанком, а недоотправленное сообщение отменяется с понятной причиной.

Общие числа и текстовые константы клиент не пишет руками: `dataopen ctl constants` создаёт `pwa/js/constants.js`, `dataopen ctl golden` создаёт `pwa/tests/golden.json` (байты, которые обе стороны обязаны
давать и принимать одинаково). Оба файла сверяются с генераторами тестом.

## 5. Манифест: органы управления приходят с устройства

JSON ≤ 16 КБ: `schema`, `rev`, `title`, страницы, контролы. Восемь типов, клиент не знает ни одного экрана по имени.

| тип | что рисуется |
|---|---|
| `toggle` | большой выключатель с **иконкой и словом** «Включено»/«Выключено» |
| `stepper` | значение прописью сверху, под ним две большие кнопки «−» и «+» (вместо ползунка: его нельзя перетаскивать); подписи на размеченных уровнях («Как рекомендует профиль») |
| `meter` | полоса и число, `role=progressbar` |
| `status` | значение с подписью из словаря устройства |
| `action` | кнопка; `confirm: two-step` — подтверждение второй большой кнопкой |
| `file` | `bundle_put`: выбор файла и зона для перетаскивания (на компьютере); `bundle_get`: сохранить копию для этого устройства; `bundle_for_card`: выбрать карточку получателя и сохранить файл для него; `card_get`: сохранить карточку устройства |
| `note`, `group` | текст; вложенный список |

У каждого контрола `id`, `key` (в дереве состояния), `label`/`help` как `{ru, en}`, ограничения (`min`, `max`, метки), `confirm` (`none`, `revert`, `two-step`), `danger`. Устройство проверяет
каждый `SET` и `ACT` по этому же манифесту (`Manifest.check_set`/`check_act`), а при запуске проверяет сам манифест (`validate_manifest`: размеры, глубина, уникальность `id`, языки, диапазоны).

Клиент снисходителен: неизвестный тип становится нейтральной плашкой «обновите приложение», лишние поля игнорируются, строки попадают в страницу только через `textContent`, из манифеста нельзя получить
ни скрипт, ни адрес. Манифест кэшируется в IndexedDB по хэшу: при повторном подключении клиент читает 16 байт `info` и скачивает манифест только если хэш изменился. Страницы манифеста с `id: "more"` сливаются с
фиксированной страницей «Ещё» (там сначала аппаратный bypass, затем то, что принесло устройство, затем настройки самого приложения).

## 6. Стыковка с мостом и модулем (`ctl/gateway.py`)

Шлюз принимает и отдаёт чанки и ничего не знает о транспорте. К мосту он ходит кадрами BridgeLink: HELLO каждые 10 мс (он же опрос), `CMD` по изменению и раз в секунду, блобы параметров раз в секунду.

**Кнопки.**
- **«Выключить помощь»** (всегда на экране, один тап, без подтверждения, не проходит через защиту от повторных нажатий): `assist_wanted = false` записывается на диск, `CMD PASSTHRU` уходит немедленно, без ожидания тика.
  Мышь идёт байт в байт, ПК её не перечисляет заново. Включить обратно с телефона можно.
- **«Железный bypass»** (во вторичном месте, два шага, с текстом про 1–2 секунды без мыши): `CMD BYPASS`. Это жёсткая защёлка моста: телефон её **не снимает**, снимает только удержание физической кнопки Panic 2 секунды.
  Шлюз повторяет команду, пока мост не подтвердит защёлку (или 1 секунду), и больше не посылает её: иначе он бы заново защёлкивал мост после возврата рукой.
- **«Включить помощь»** — просьба. Мост её выполняет, только если нет защёлки, ошибки и устаревших параметров. Иначе экран показывает причину простыми словами и что делать (латч Panic: «удержите кнопку 2 секунды»).
- Перезапуск шлюза **не** включает помощь сам: он читает сохранённое желание (по умолчанию выключено). Перезапуск посреди пробы — это «нет»: возвращается сохранённое состояние.

**Ручки (`ctl/tuning.py`).** Уровни 0..10, по умолчанию 5 = ровно то, что рекомендует профиль. Множитель: 0 → слой выключен, 5 → ×1.0, 10 → ×1.5.
Сила помощи: `s_brake × f`, `k_floor' = 1 − f·(1 − k_floor)` (не ниже 0.1), `hold_scale' = min(1, hold_scale × f)`. Подавление дрожи: `s_max` ниже рекомендации масштабируется, выше рекомендации идёт к потолку 0.95 (чтобы верхние
ступени всегда что-то значили), `trim_cap × f` (≤ 64). Затем пересчёт `overlap_hold` (иначе два слоя демпфируют один и тот же сигнал дважды) и обычная фиксированная арифметика. Слой, который выключен, отправляется мосту **нейтральным,
но допустимым блобом** (нулевой блоб мост отклонил бы: `v_on` обязан быть ≥ 1).

Проверено на настоящем C-ядре моста: все пары уровней {0, 1, 5, 9, 10}² для трёх профилей (дрожь, без дрожи, без профиля) принимаются таблицами диапазонов (`params_rejected == 0`); сила по уровню монотонна;
на сетке уровней через весь мост (с большими движениями руки) мост никогда не прибавляет движения и ни разу не срабатывает защита от нарушения.

**Что делают уровни на симулированном человеке** (тот же «человек» и те же случайные числа, 10 попыток; `tests/test_ctl_manifest.py`, и для справки на 30 попытках при отладке):
у персонажа с тремором дрожание при удержании цели падает с ≈24 px (без помощи) до ≈4.8 px (уровень 5) и ≈4.3 px (уровень 10); доля попыток с перелётом 100 % → 27 %; **цена**: время захвата цели растёт с ≈530 мс до ≈650 мс (уровень 5) и ≈750 мс (уровень 10).
У персонажа, склонного к перелётам, время захвата падает с ≈370 до ≈240 мс. Это ответ симулятора на вопрос «безопасно ли и в какую сторону», а не на вопрос, как это ощущается: **шкала уровней не проверена на людях.**

**Пробное включение.** Повышение (включить помощь, поднять любой уровень при включённой помощи, импорт файла или новый профиль при включённой помощи) применяется сразу; прежнее состояние запоминается, запускается таймер (20 с по умолчанию), экран
показывает «Стало лучше?» с кнопками «Оставить» и «Вернуть как было» и честным отсчётом. Если ничего не нажать или связь пропала, всё возвращается. Новое повышение продлевает таймер, возврат к уровню не выше сохранённого
снимает пробу. Понижение пробы не требует. Если до пробы профиля не было, безопасный возврат — «помощь выключена» (профиль остаётся).

## 7. Калибровка и статус профиля

В движке BioProfile нет ни режима калибровки, ни метрики «сошёлся»: он учится пассивно, у каждой статистики есть число наблюдений `n`. Поэтому добавлено два минимальных механизма.

**Статус профиля** (`bioprofile/progress.py`): `fill` = среднее `min(1, n/30)` по шести статистикам, которые нужны слоям (`d_brake`, `v_max`, `overshoot`, `t_motor`, `jitter_amp`, `jitter_hz`). Это «собрано достаточно наблюдений», а **не** статистическая
сходимость, и в интерфейсе подписано как «сколько наблюдений уже накоплено, не оценка качества». Отдельно: готов ли слой помощи при движении и дрожь (`ready`, `not_needed`, `collecting`).

**Калибровка** (`CalibrationController` в шлюзе): пока она идёт, помощь **принудительно выключена** (профиль должен учиться на собственных движениях человека, а не на движениях под помощью), прежнее желание сохраняется и после остановки возвращается; повторно включить помощь
во время калибровки нельзя (`err.busy`). Профиль записывается по окончании; он идёт как новый профиль, то есть при включённой помощи это проба. Источник событий подключаемый (`Learner`: `start/stop/poll/snapshot`);
в симуляторе это `SimLearner` (симулированный человек в настоящем движке BioProfile). **Живого источника нет:** нужна связка «телеметрия моста (сырые X/Y) + объекты UI-детектора → `on_mouse`/`on_target`», а адаптера «UI-детектор → `TargetObs`» в проекте нет
(pose-связка с помощью запрещена, [UIDET.md](UIDET.md)). Пока этого нет, калибровка на железе не запустится. DPI мыши шлюзу тоже неоткуда узнать: `deg_per_count` приходит от источника.

## 8. Файл настроек `.dobundle`: теперь привязан к одному устройству

Файл больше не открытый. Это `DOBS` v2: профиль, два уровня (и, при желании, UI-манифест) **зашифрованы под одно конкретное устройство**, подписаны отправителем, защищены от повтора; открыть его может только то устройство, для которого он сделан
(формат, ключи, потоки и границы в [SECURITY.md](SECURITY.md)). Страница остаётся «глупой»: она только переносит байты и **не умеет их расшифровать**.

| Кнопка в приложении | Что происходит |
|---|---|
| «Загрузить файл настроек» (или перетащить файл) | байты уходят на устройство; оно само расшифровывает, проверяет и применяет; чужой, повреждённый, повторный и старый открытый файл отвергаются понятной причиной |
| «Сохранить копию для этого устройства» | файл, который откроется только на этом же устройстве (резервная копия); кнопка на устройстве не нужна |
| «Сохранить для другого устройства» | выбрать карточку получателя (`.docard`), сверить его номер с наклейкой; **нужна кнопка на этом устройстве** |
| «Сохранить карточку устройства» | открытая карточка с номером устройства: её можно передавать, по ней нельзя ничего прочитать, только подготовить файл для этого устройства |
| получение файла от нового отправителя | **нужна кнопка на устройстве-получателе** (сообщение называет номер отправителя); дальше отправитель запомнен |

Если устройство просит кнопку на себе, сообщение так и говорит и несёт кнопку «Повторить». Профиль по-прежнему ложится через `ProfileStore.save()` (A/B-слоты), остаётся для «Вернуть прежний профиль», а при включённой помощи идёт пробой.

## 9. Безопасность и приватность

| Угроза | Что сделано |
|---|---|
| Сосед в радиусе Bluetooth что-то настраивает | Все характеристики требуют шифрованного соединения. **Задумано (не реализовано):** окно сопряжения открывается **физическим действием на устройстве** (отдельная кнопка, светодиод), до 4 телефонов, «забыть все телефоны» тоже физически (шлюз уже требует нажатия кнопки: `err.physical`, срок жизни нажатия 30 с, одно нажатие — одно действие) |
| Телефон присылает опасные параметры | Он не присылает параметры. Блобы строит шлюз и проверяет мост (таблицы диапазонов, зажим `|out| ≤ |in|`) |
| Файл с профилем попал не туда | Файл зашифрован под одно устройство и подписан ([SECURITY.md](SECURITY.md)); данные на самом устройстве зашифрованы, их можно стереть |
| Злая страница/манифест | CSP `default-src 'none'`, скрипты и стили только свои, без `unsafe-inline`; текст только через `textContent`; из манифеста нельзя получить код или адрес (тест на исходниках) |
| Слежка | Нет аккаунтов, нет аналитики, нет сторонних шрифтов и скриптов; у страницы нет ни одного вызова `fetch`; в браузерном тесте за всё время контактировался только собственный origin |
| Мусор на канале | Фаззинг приёма (3000 случайных, побитых и поддельных сообщений и чанков): шлюз остаётся рабочим |
| Крах посреди пробы | Проба не становится постоянной от падения (в тесте) |
| Подмена файла | шифр с проверкой целостности и подпись: изменённый бит отвергает файл; ограничения моста |

Честно: Web Bluetooth не даёт странице управлять сопряжением; как именно покажет себя «Just Works» с окном по кнопке на разных телефонах, **не проверено**.

## 10. Клиент: экраны, доступность, испытания с людьми

**Экраны.** Подключение (одна большая кнопка и три коротких шага; если Bluetooth недоступен, прямо сказано, что делать, на iPhone — что он не поддерживается). Состояние устройства закреплено вверху и всегда словами, иконкой и цветом
(«Помощь работает», «Помощь на паузе: нет связи с модулем», «Остановлено кнопкой Panic. Чтобы вернуть, удержите кнопку 2 секунды»). Внизу всегда «■ Выключить помощь». Страницы: «Помощь», «Профиль», «Ещё».

**Что проверяется автоматически** (`pwa/tests/a11y.test.mjs` по исходникам и `browser.mjs` в настоящем Chromium по отрисованному):
- шесть палитр (светлая, тёмная, максимальный контраст — по умолчанию по настройкам телефона и по выбору человека): контраст текста **не ниже 7:1** (WCAG AAA) для всех пар и **не ниже 3:1** у границ, колец фокуса и залитых кнопок; в браузере то же измерено по настоящим стилям на каждой теме;
- базовый шрифт 20 px при стандартных настройках браузера, всё в `rem` (системный размер текста масштабирует всё); цели касания **не меньше 64×64**, кнопка выключения не ниже 90 px; зазор между кнопками не меньше 12 px; горизонтальной прокрутки на 360 px нет;
- ни одного обработчика жестов (`touchstart`/`pointer*`/`dblclick`/`contextmenu`/`wheel`/`keydown`...), нет стилей только для наведения, нет ограничений по времени, кроме отката в безопасную сторону (который можно подтвердить);
- фокус всегда виден; `prefers-reduced-motion`, `prefers-contrast`, `prefers-color-scheme` учитываются;
- **защита от случайных повторных нажатий** (0 / 0,4 / 0,8 с; по умолчанию 0,4): второе нажатие на ту же кнопку сразу после первого не засчитывается; кнопка выключения помощи не защищается никогда;
- все элементы нативные (`button`, `role=switch` с `aria-checked`, `role=progressbar` с `aria-valuetext`, `aria-live` у состояния и значения шагов), у каждого есть имя на обоих языках; ключи обоих языков совпадают, у всех причин моста и кодов ошибок есть текст.

**Что автоматически проверить нельзя и что надо проверить на людях.** Это главная часть. Предлагаемый протокол (без него продукт для этой группы остаётся непроверенным):
1. Участники: люди с тремором, последствиями инсульта, ДЦП, разные степени; отдельно сопровождающие. Свой телефон, а не наш.
2. Задачи с секундомером: подключить устройство; увидеть, включена ли помощь; выключить помощь; включить; поменять силу на «чуть больше»; запустить и остановить калибровку; загрузить файл; перейти в bypass и вернуться. Цель: подключение и первая настройка за **2–3 минуты** без помощи.
3. Измерять: время и число ошибочных нажатий на задачу (промахи, двойные нажатия), долю задач без подсказки, непреднамеренные включения «bypass» (должно быть ноль), сколько раз «Вернуть как было» нажимали осознанно и сколько раз проба истекала сама, понятность текстов (вопрос «что сейчас с устройством?»), нагрузку (шкала по желанию участника).
4. Отдельно: TalkBack, Switch Access, Voice Access на Android; увеличение текста до 200 %; одна рука; планшет, горизонтальная ориентация.
5. Ничего не подгонять под сумму цифр: хорошие задачи оставить, плохие переписать (макет, подписи, размер кнопок, ступени шкалы), снова измерить. Особенно проверить, **что значит для человека «уровень 7 из 10»** и не слишком ли мелкая шкала для дрожащей руки.

## 11. Транспорты и платформы

| | Статус |
|---|---|
| Android, Chrome (и совместимые браузеры) | v1. Web Bluetooth; страница из кэша работает без интернета |
| Компьютер, Chrome и Edge | то же |
| **iPhone / iPad** | **не поддерживается.** В Safari и в любом браузере на iOS нет Web Bluetooth (все они на WebKit). Сторонние приложения-обёртки есть, но это установка, которой хотят избежать |
| Wi-Fi (точка доступа устройства) | не делалось. Протокол не зависит от транспорта: те же чанки идут по WebSocket (`pwa/js/transport/ws.js` уже есть и используется симулятором и тестами). Для iPhone нужна **страница, которую отдаёт само устройство** по HTTP на своей сети: с HTTPS-страницы обращаться к адресу из локальной сети нельзя (смешанное содержимое), и офлайн-кэш у такой страницы не работает (service worker требует защищённого контекста) |

Размер чанка согласуется (раздел 4); Chrome сам согласует MTU, страница его не видит, поэтому устройство само ограничивает свои уведомления тем, что может доставить.

## 12. Хостинг и обновления

Страница — статические файлы (`pwa/`), их нужно отдать по HTTPS (Web Bluetooth и service worker требуют защищённого контекста; `localhost` подходит для разработки). **Первое открытие требует интернета один раз**; после этого всё берётся из кэша.
Устройство или его коробка может нести ссылку/QR-код, а установка на экран «Домой» необязательна (кэш работает и без неё). Деплой я не настраивал: публикация вовне — решение владельца продукта.
Service worker кэширует файлы из списка (список и версия кэша записываются командой `dataopen ctl pwa-build`, версия = хэш содержимого, тест сверяет). Новая версия скачивается в фоне, но **не вступает в силу, пока человек не нажмёт «Обновить»**
(и страница не перезагружается посреди работы); самая первая установка перезагрузки не вызывает.

## 13. CLI и тесты

```
dataopen ctl simulate [--profile tremor|steady|overshooter|none] [--trial-s N] [--json]   # сценарий «телефона» против шлюза и настоящего ядра моста
dataopen ctl manifest [--out F]            # манифест устройства
dataopen ctl constants [--out pwa/js/constants.js]   # константы протокола для клиента
dataopen ctl golden [--out pwa/tests/golden.json]    # общие тестовые векторы
dataopen ctl pwa-build [--check]           # список файлов и версия service worker
dataopen ctl serve-sim [--port N] [--trial-s N]      # PWA и симулированное устройство на localhost (разработка и тесты)
```

Тесты: Python (`tests/test_ctl_protocol.py`, `test_ctl_manifest.py`, `test_ctl_gateway.py`, `test_ctl_slots.py`, `test_ctl_panel.py`, `test_ctl_update.py`, `test_pwa.py`), Node (`pwa/tests/*.test.mjs`, запускаются из `test_pwa.py`; в CI Node ставится шагом `setup-node`),
Chromium (`pwa/tests/browser.mjs`: `python -m pytest tests/test_pwa.py -k chromium`, если установлен Playwright; переменная `PLAYWRIGHT_NODE_MODULES` указывает на каталог с его модулями).

## 14. Допущения и открытые вопросы

- Окно сопряжения по физической кнопке, число телефонов, «забыть все» — решения проекта, которых ещё нет в железе; шлюз уже требует физического подтверждения для «забыть все телефоны».
- Таймер пробы 20 секунд и шкала уровней 0..10 выбраны разумно, но не проверены на людях; срок пробы настраивается (`trial_s`), шкала — формулами в `ctl/tuning.py`.
- Слоты, панель, обновление прошивки: допущения и пороги в [SLOTS.md](SLOTS.md) (раздел 11).
- Шлюз держит одну сессию (как и обычный BLE-периферийный режим); два телефона одновременно не предусмотрены.
- Профиль, собранный одной мышью, не знает про смену DPI: шлюзу неоткуда его узнать (то же ограничение, что у моста, [BRIDGE.md](BRIDGE.md)).
- Приём файла через системное «Поделиться» не делался. Подпись производителя на карточках устройств и подпись/передача весов моделей тоже ([SECURITY.md](SECURITY.md), раздел 7).
