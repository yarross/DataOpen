# Runtime инференса на целевом SoC

Что здесь есть: главный цикл (`src/dataopen/runtime/loop.py`), политика буфера кадров, backend'ы моделей (ONNX Runtime CPU/CUDA/TensorRT,
RKNN, mock, любой `IModelEvaluator` замкнутого цикла), IPC-канал для `KeypointArray`, DMA-подобное кольцо кадров, метрики и CLI
`dataopen runtime ...`. Код работает сегодня на ONNX Runtime (CPU/CUDA); на плате меняется один backend (`--backend rknn`).

## 0. Честный статус

| Что | Статус |
|---|---|
| Цикл, политики, метрики, канал, кольцо кадров, C-постобработка, ORT-backend, mock, fallback, `RuntimeEvaluator` | **Реализовано и проверено тестами** (`tests/test_runtime.py`, `tests/test_detector_torch.py`), включая реальную ONNX-модель и обученную модель замкнутого цикла. |
| `RknnLiteBackend` | **Написан по документированному API `rknnlite`, не запускался**: здесь нет платы и `rknn-toolkit-lite2`. Тест проверяет только понятную ошибку без тулкита. |
| Настоящий dma-buf от захвата видео | **Не проверено.** Кольцо передаёт дескрипторы по SCM_RIGHTS на `memfd` (то же, что делается с dma-buf fd); на плате продюсер передаёт fd буферов RGA/V4L2. Режим `dmabuf=True` включает `DMA_BUF_IOCTL_SYNC` вокруг чтения CPU, без железа не запускался. |
| Realtime-гарантии (ядра, приоритеты) | Есть `--cpus` и `--rt-priority`, это обычный Linux, **не RTOS**: жёсткий дедлайн Python не даёт, см. раздел 8. |
| Задержки/FPS на NPU | **Не измерены.** Цифры раздела 7 это хост-CPU и накладные расходы самого цикла. |

## 1. Как это устроено

```
 захват ──► RingProducer ─(fd кадров один раз; дальше "слот k = кадр f")─► RingConsumer ─┐   FrameSource
 (RGA/V4L2)   memfd/dma-buf, 4 слота, продюсер НЕ блокируется                           │
                                                                                         ▼
                                              reader-поток ──► BufferPolicy (latest | queue:N) ──► worker-поток(и)
                                              O(1), не ждёт модель      drop + причина                 │
                                                                                                       ▼
                                  ModelBackend.infer(frame): ORT / RKNN / EvaluatorBackend / Scripted / Fallback
                                  модель ─► сырые выходы по уровням ─► C-постобработка (ctypes, без GIL) ─► KeypointArray
                                                                                                       │
                          заголовок: frame_id, время захвата, яркость, flags, letterbox ◄──────────────┘
                                                                                                       ▼
                       ResultChannel:  UDS SEQPACKET (каждый результат по порядку, каждому подписчику)
                                       + ShmLatest (последний результат в shared memory, seqlock + CRC32)
```

Принципы:

* **Не блокирует остальную систему.** Читатель только кладёт ссылку на кадр в политику (O(1)); медленная модель стоит кадров
  (с учётом причины), но не стоит остановки захвата и не задерживает публикацию. Продюсер кольца, `QueueSource.push` и публикация
  в канал не ждут никого и никогда.
* **Каждый буфер возвращается продюсеру ровно один раз**, что бы с кадром ни случилось (посчитан, вытеснен, устарел, ошибка,
  остановка): тест `test_slow_model_with_latest_only...` проверяет это на потоке с потерями.
* **Ошибка модели не выглядит как «никого нет».** При исключении backend'а в канал уходит результат с `FLAG_EMPTY_ERROR`
  и нулём детекций; потребитель, который не умеет читать флаги, всё равно не получит старого ответа под видом нового.
* **Один цикл на всё.** `RuntimeEvaluator` оборачивает тот же цикл в `IModelEvaluator`, поэтому замкнутый цикл может оценивать
  модель именно тем путём, которым она поедет (раздел 3).

## 2. Главный цикл

Реальный код: `InferenceRuntime._read` / `_work`. Псевдокод рабочего потока:

```python
while running:
    frame = policy.get()                                  # блокирует только этого воркера
    if max_age and frame.age > max_age:                   # ответ, который уже никому не нужен, только задержал бы следующий
        drop(frame, "stale"); continue
    try:
        arr = backend.infer(frame)                        # модель + постобработка, детекции в пикселях 640x640
        metrics.ok()
    except Exception as e:
        metrics.error(e); arr = empty(flag=EMPTY_ERROR)   # потребитель обязан узнать, что ответа нет
    if a_newer_frame_was_already_published:               # несколько воркеров заканчивают не по порядку
        drop(frame, "late"); continue
    fill_header(arr, frame_id, capture_ts, brightness, flags, letterbox)
    publisher.publish(bytes(arr))                         # UDS + shm, не блокирует
    metrics.record(infer, publish, e2e); frame.release()  # буфер назад продюсеру
```

Запуск:

```python
rt = InferenceRuntime(RingConsumer("/run/apollo/frames.sock"),
                      OrtBackend("apollo_n_u8.onnx", provider="cuda"),            # на плате: RknnLiteBackend("apollo_n.rknn", core="all")
                      ResultChannel(uds_path="/run/apollo/kp.sock", shm_name="apollo_kp"),
                      policy="latest", max_age_ms=12, stale_flag_ms=8, log_every_s=5).start()
...
rt.stop()
```

или `dataopen runtime run --source ring --input /run/apollo/frames.sock --backend ort --model m.onnx --provider cuda --uds /run/apollo/kp.sock --shm apollo_kp --policy latest --max-age-ms 12`.

Поля заголовка `KeypointArray` (формат v2 из `docs/DETECTOR.md`, 1516 байт): `frame_id` и `timestamp_us` берутся из кадра (время захвата, монотонные
микросекунды, 32 бита, оборот ~71 минута: потребитель сравнивает разности), `avg_scene_brightness` считается по 400 отсчётам кадра,
`flags`:

| Бит | Значение |
|---|---|
| 1 `DEGRADED` | результат дал запасной backend (NPU → CPU) |
| 2 `STALE` | на момент публикации кадр был старше `stale_flag_ms` |
| 4 `DROPPED_BEFORE` | между предыдущим результатом и этим кадры были пропущены |
| 8 `EMPTY_ERROR` | инференс не удался: детекций нет, и это не значит «никого нет» |

## 3. Интеграция с `IModelEvaluator`

Мост в обе стороны, ничего в замкнутом цикле не меняется.

**Вход: любой evaluator замкнутого цикла как backend runtime** (`EvaluatorBackend`). Mock-модель замкнутого цикла
(`SimulatedEvaluator`, `CallableEvaluator`, `OnnxEvaluator`, `TorchEvaluator`) становится моделью production-цикла: тесты runtime
и стенд без модели работают на том же коде, что плата. Доверенные метки для `SimulatedEvaluator` едут в `frame.meta["hints"]`.

**Выход: runtime как `IModelEvaluator`** (`RuntimeEvaluator`): кадры замкнутого цикла проходят reader → политика → backend →
C-постобработка → упаковка Q12.4 → обратно в `Prediction`. Так замкнутый цикл судит модель тем путём, которым она поедет:
регрессия постобработки или квантования результата проявится как падение OKS в цикле, а не в поле.

```
dataopen collect --game mock_shooter --quality-model apollo_n_u8.onnx --quality-format apollo --quality-runtime ...
dataopen collect --game mock_shooter --quality-sim --quality-runtime ...        # mock-модель через тот же production-путь
```

Отличия `RuntimeEvaluator` от живого пути сделаны намеренно: кадры подаются с обратным давлением и очередью, в которой ничего не
теряется (оценка обязана учесть каждый кадр), сбой backend'а **поднимает исключение** (не «ноль детекций»), кадры произвольного
размера вписываются (letterbox) и координаты возвращаются в исходные пиксели. Проверено тестом: вердикты замкнутого цикла через runtime
совпадают с прямым путём (расхождение только из-за квантования результата 1/16 px и 1/255), а обученная модель
через runtime даёт ту же метрику, что через PyTorch.

Backend'ы:

| Backend | Где | Заметки |
|---|---|---|
| `OrtBackend` | ONNX Runtime: `cpu`, `cuda`, `tensorrt` (через EP), `directml` | раскладка берётся из метаданных ONNX; uint8 NHWC читается без копии; если провайдера нет, **предупреждение и CPU** |
| `RknnLiteBackend` | плата Rockchip (`rknnlite`) | **не запускался здесь**; раскладка из `<model>.layout.json` рядом с файлом (его пишет `detector export`); ядро NPU `--core auto\|0\|1\|2\|0_1\|all` |
| `EvaluatorBackend` | любой `IModelEvaluator` | сериализует вызовы; `warmup` без фиктивных кадров |
| `ScriptedBackend` | тесты | задержка/джиттер/сбой каждые N/однократное зависание |
| `FallbackBackend` | основной + запасной | после `max_errors` подряд сбоев переключается (флаг `DEGRADED`), раз в `retry_s` пробует основной снова |

Постобработка: C99 (`apollo_post.c`, собирается `dataopen runtime build-post` или автоматически, вызывается через ctypes с освобождением GIL)
или numpy-эталон; тест проверяет, что оба дают **одинаковые байты**.

## 4. Новый кадр пришёл, предыдущий ещё не досчитан

Политика задаётся `--policy`; каждое вытеснение учитывается с причиной.

| Политика | Поведение | Когда |
|---|---|---|
| **`latest`** (по умолчанию) | держим один ожидающий кадр; новый заменяет старый (`superseded`) | всё, что действует по результату (прицел): старый ответ ценится меньше, чем никакого; задержка ограничена одним кадром |
| `queue:N[:oldest]` | очередь N; при переполнении выбрасывается самый старый | нужно сгладить всплеск, но свежесть важнее полноты; рядом `--max-age-ms` |
| `queue:N:newest` | при переполнении отбрасывается новый | офлайн-анализ, где важна непрерывность backlog'а, а память ограничена |

Неограниченной очереди нет намеренно: медленная модель превратилась бы в растущую задержку и затем в OOM. `--max-age-ms` отбрасывает
кадр, который к моменту взятия в работу уже старше порога (`stale`): считать его значит задерживать следующий. Если несколько воркеров
заканчивают не по порядку, более старый результат не публикуется (`late`), чтобы потребитель никогда не видел время назад.

Выбор `latest` по умолчанию: при частоте кадров выше пропускной способности модели любая очередь рано или поздно сводится к «выбрасываем
самое старое», только с лишней задержкой по дороге; `latest` делает это сразу и без накладных расходов. Очередь оправдана при **нескольких
воркерах** (по одному на ядро NPU: `--workers 3` с `--core 0/1/2`) или когда нужны все кадры.

## 5. IPC-канал

`ResultChannel` это два транспорта за одним `publish` (можно любой из них):

* **UDS SEQPACKET** (`--uds`): каждый результат, по порядку, каждому подписчику; границы сообщений сохраняются. У каждого подписчика
  **маленький буфер отправки**: подписчик, который не успевает, **пропускает сообщения** (считается для него), не замедляя runtime и других.
  `UdsSubscriber.latest()` берёт только самое новое.
* **`ShmLatest`** (`--shm`): последний результат в shared memory для модулей, которые читают в своём темпе (контур прицеливания на 1 кГц).
  Один писатель, много читателей; чтение подтверждается счётчиком последовательности **и** CRC32 полезной нагрузки, поэтому разорванное чтение
  обнаруживается независимо от порядка памяти CPU (тест с писателем, который молотит без остановки).

Потребитель сначала проверяет `structs.validate(buf, keypoints, classes)`: размер, magic, версию и **хеш схемы**: массив, произведённый для другого
набора точек, отвергается. Минимальный потребитель: `dataopen runtime tail --uds PATH | --shm NAME`.

## 6. Метрики

Логируются раз в `--log-every` секунд одной строкой, полный снимок дописывается в JSONL (`--metrics-jsonl`), Prometheus-текст
(`metrics.prometheus()`) для сбора снаружи:

```
fps in/out 119.5/119.9  e2e p50/p99 5.7/14.3 ms  infer p50/p99 5.6/7.6 ms  queue 0/2  dropped 1 (0.4%)  errors 0
```

Минимум, который надо смотреть:

| Метрика | Что показывает |
|---|---|
| `latency_ms.e2e` (p50/p95/p99/max) | от времени захвата кадра до публикации; то, что чувствует потребитель |
| `latency_ms.infer` | только `backend.infer` (модель + постобработка) |
| `latency_ms.queue_wait`, `frame_age` | сколько кадр ждал; рост = модель не успевает |
| `latency_ms.publish` | цена IPC (десятки микросекунд) |
| `fps_in`, `fps_out` | вход и выход за скользящее окно 2 с |
| `queue.depth/max/capacity` | глубина очереди сейчас и максимум |
| `dropped` по причинам | `superseded`, `queue_full_oldest/newest`, `stale`, `late`, `shutdown`, `error`, `producer` (продюсер кольца не нашёл свободного слота) |
| `errors.total/consecutive/last`, `degraded` | сбои и переключение на запасной backend |

`rt.health()` возвращает `ok=False`, если воркер завис дольше `hang_ms` или идут подряд сбои: для сторожевого процесса.

## 7. Измерения

Все числа с хоста (4 ядра CPU контейнера, ONNX Runtime CPU, FP32, **не NPU**); вход 60 кадров/с, политика `latest`, 6 секунд, `dataopen runtime bench`.
Веса случайные (измеряется скорость, не качество), `conf_thr` 0.25.

| Конфигурация | e2e p50 / p99, мс | infer p50 / p99, мс | выход, FPS | потеряно |
|---|---|---|---|---|
| ApolloNet **n** @640 | 10.1 / 24.5 | 10.0 / 22.0 | 58.4 | 0.6% |
| ApolloNet **s** @640 | 26.4 / 40.4 | 18.5 / 29.9 | 53.3 | 11.9% (модель медленнее входа: 43 кадра вытеснены, `superseded`) |

Что из этого следует:

* **Накладные расходы самого цикла малы.** `ScriptedBackend` с нулевой задержкой при 240 кадрах/с: e2e p50 0.69 мс (из них публикация 0.04 мс, ожидание
  в очереди 0.1 мс), p99 2.8 мс, ни одного пропуска. Остальное в `infer` у этого стенда это упаковка одной детекции на Python.
* **Постобработка.** На реальном выходе n@640 (20 детекций, порог 0.01): **C 0.12 мс против numpy 11.8 мс** на кадр. Эталон на numpy сам съедает
  больше, чем вся модель n на NPU по арифметической оценке, поэтому в runtime по умолчанию C (`--post auto`), а numpy остаётся запасным путём.
* **Политика `latest` при перегрузе ведёт себя как задумано:** у модели `s` задержка кадра остаётся ограниченной (кадр ждёт ≈ 8 мс, не растёт),
  лишние кадры вытесняются и посчитаны.
* Это **хост-CPU**: на RK3588 цифры другие, и именно их надо снять (`dataopen runtime bench --backend rknn ...` на плате). Цели ТЗ (< 4 мс, > 240 FPS)
  здесь **не проверяются**: CPU медленнее NPU на порядок. Проверено только то, что цикл вокруг модели добавляет доли миллисекунды и не рушится
  при перегрузе.

## 8. Развёртывание на SoC и ограничения

1. **Модель.** `dataopen detector export` (uint8 или float 0..255) → `quantize` → `rknn_convert` (скрипт сгенерирован, запускается на x86 с
   `rknn-toolkit2`) → `<model>.rknn` + `<model>.layout.json` на плату. `dataopen runtime run --backend rknn --model m.rknn --core all`.
2. **Кадры.** Продюсер захвата вместо `submit()` вызывает `acquire()` / `commit()` и передаёт fd своих буферов (RGA/V4L2 dma-buf): пиксели не копируются.
   Нужен RGB 640×640 uint8; конвертацию цвета и масштаб делает RGA.
3. **Ядра и приоритет.** Три ядра NPU RK3588: либо один воркер на `--core all`, либо три воркера (`--workers 3`) на отдельных ядрах с `--policy queue:3`
   (пропускная способность выше, задержка кадра та же). Процесс прижмите `--cpus` к ядрам, свободным от драйвера захвата, и по возможности
   `--rt-priority`. Это **soft real-time**: GIL и сборщик мусора Python дают джиттер; если p99 не устраивает, горячий путь
   (reader + worker + публикация) переносится на C/C++ с теми же структурами и тем же протоколом кольца/канала: формат не меняется.
4. **Деградация.** `FallbackBackend(rknn, ort_cpu)` переключает на CPU после сбоев; потребитель видит флаг `DEGRADED` и решает, насколько доверять.
5. **Что не сделано:** трекинг (`track_id` всегда 0); общая очередь нескольких потребителей с подтверждениями; перезапуск драйвера NPU
   (процесс-хранитель снаружи: `health()` для него); проверка на реальном dma-buf и RKNN.
