# DataOpen Assist: архитектура ассистивного USB/видео-адаптера с персональной моторной коррекцией ввода

## 1. Название, статус, цель документа

| | |
|---|---|
| **Изделие** | Ассистивный адаптер между мышью человека, компьютером и монитором. Рабочее название кода: **DataOpen** (пакет `dataopen`), линейка железа **DO-1 Base, DO-2 DP, DO-3 Type-C, DO-4 Pro** ([HARDWARE.md](HARDWARE.md)). |
| **Что делает** | Прозрачно проксирует USB-мышь и, при необходимости, видеосигнал. Из движения мыши **только вычитает** (подавляет дрожь, притормаживает у цели), ориентируясь на персональный моторный профиль человека и на то, что находится на экране. При любой неисправности человек получает мышь и экран напрямую. |
| **Для кого** | Людей с тремором, последствиями инсульта, ДЦП, перелётами при наведении. Управляется с телефона (PWA), не требует установки программ на компьютер. |
| **Ветка / состояние** | Ветка `claude/optimistic-lamport-wrhq2l` репозитория `yarross/DataOpen`. Документ описывает состояние кода и тестов этой ветки. |
| **Статус изделия** | **Спецификация и работающая симуляция. Железа нет. С людьми не испытывалось.** Готовность к пилоту по собственной проверке репозитория: **НЕТ** (выполнено 8 из 33 критериев, проверено на железе 0, с людьми 0; `dataopen release status`, [V1.md](V1.md)). |
| **Тип документа** | Главный обзорный документ системы. Подробности по подсистемам вынесены в профильные `docs/*.md`; здесь они сведены в одну картину и привязаны к коду. |

### 1.1. Цель документа

Документ нужен, чтобы:

1. **Понять систему целиком**: из чего она состоит, кто с кем говорит, на каком процессоре что исполняется, где проходят границы доверия.
2. **Увидеть, что уже реализовано**: какие куски работают, на чём именно проверены (хост, симуляция, ни на чём) и чем подтверждены.
3. **Увидеть, что осталось только архитектурным заделом**: каждый такой блок помечен прямо в тексте.
4. **Продолжать разработку**: раздел 16 даёт порядок работ, а приложение A карту файлов и правил, чтобы не наступить на найденные грабли.

### 1.2. Условные обозначения статуса

Эти же четыре статуса использует реестр готовности `src/dataopen/release/registry.py`; `dataopen release check` сверяет его с репозиторием.

| Метка | Значение | Что это гарантирует |
|---|---|---|
| **[I] Implemented** | Код готов, его корректность решается тестами на хосте: форматы, протоколы, криптография, автоматы состояний, алгоритмы, C-ядра, совпадающие с эталоном бит в бит. | Логика верна **на хосте**. Годность для реального мира отдельный вопрос и записан как «не проверено». |
| **[S] Simulated** | Код готов, но «работает» только против смоделированного железа, радио, USB-хоста, людей или синтетических данных. | Механизм ведёт себя как задумано **в модели**. Модель может ошибаться. |
| **[A] Architecture-only** | Есть описание, схема, данные, правила, но нет кода самой вещи. | Только замысел. Нельзя считать работающим. |
| **[D] Deferred** | Сознательно вне v1. | Ничего. |

Метки источника цифр в тексте (из [LATENCY.md](LATENCY.md)): `calc` расчёт из констант кода, `sim` измерено в симуляции, `host` замер на хосте, `estimate` оценка, `unmeasured` не измерено.

### 1.3. Принцип честности документа

* Везде, где написано «работает», подразумевается «в симуляции», если рядом не указано иное.
* **Ни одна цифра не получена на железе.** Времена реле, watchdog, перенумерации USB, тепло, ток, целостность сигнала, задержки на SoC это допущения или расчёты.
* **Ни один человек не пользовался устройством.** Всё про пользу, шкалу уровней, пороги кнопок, понятность текстов проверено на смоделированных людях.
* Если документ расходится с кодом, права код. Таблицы, помеченные `<!-- fp:… -->`, `<!-- hw:… -->`, генерируются из кода в профильных документах, а их актуальность проверяют тесты.

## 3. Именование и карта подсистем

### 3.1. Слои системы

Система делится по тому, **на каком процессоре и в каком домене питания** что исполняется, и по тому, **что может сломаться без последствий для человека**.

| Слой | Где исполняется | Что в нём | Что будет, если слой умрёт |
|---|---|---|---|
| **L0. Безопасный домен** | Дискретная логика и нормально-замкнутые реле, **без процессора** | Супервизор питания, окно watchdog, петля Panic (RC ≈ 3 с), ползунок MODE, вентили, драйверы катушек, жёлтый светодиод BYPASS | Мышь и экран напрямую, как без устройства |
| **L1. Мост** | MCU моста (класс Cortex-M7), C99-ядро без кучи | Прокси USB-мыши, правка X/Y, ASC и подавитель дрожи, автомат fail-safe, граница доверия к модулю | Если завис: L0 отпускает реле за ≈100 мс. Если мёртв модуль выше: мост сам идёт в PASSTHRU |
| **L2. Модуль** | SoM (класс RK3588), Linux | Шлюз CtlLink, BioProfile, слоты, ключи, пакеты, обновления, видеопуть, UI-детектор, (демон сборки, не написан) | Мост через 0,5 с перестаёт применять помощь; мышь идёт без помощи |
| **L3. Телефон** | Chrome на Android, PWA | Пульт: статус, «Выключить помощь», слоты, уровни, файлы | Ничего не меняется: устройство работает само |
| **L4. Завод и сервис** | Станция, HSM, утилита поддержки (всё в симуляции) | Провижининг, аттестация, токены L4, восстановление | Устройства в поле продолжают работать |

### 3.3. Поток данных (обзор)

```
        ┌───────────────────────────── L0: безопасный домен, без процессора [A: схема; S: модель логики] ─────────────────────────────┐
        │  VEXT_OK · WDG_OK · PANIC_LOOP_OK · MODE_ASSIST ──► катушки K1/K2 (мышь), KV (видео); иначе всё напрямую                     │
        └───────────────────────────────────────────────────────▲───────────────────────────────────────────────────────────────────────┘
                                                                │ ENGAGE / VIDEO_EN: только «просьба»
  мышь ──USB HS──► [BRG: host-порт] ─ образ мыши ─► [device-порт] ──USB──► ПК         L1: MCU моста (C99)
                        │ bridge_mouse_in: ASC ► TRM ► зажим |out|≤|in|  ▲
                        │ TELEM (10 Гц STATUS, выборки 16 байт)          │ PARAMS_ASC/TREMOR, SCENE, CMD, HELLO
                        ▼                                                │
                    ═══════════ BridgeLink v1: SPI, кадр 128 байт, CRC32 (BLK) ═══════════════════════════════
                        │                                                │
  экран ─ HDMI/DP ─► [CAP: сплиттер + захват] [A] ─► [VID: подготовка 640×640] ─► [UID: UiNet + трекер] ─► сцена ─┘  L2: SoM (Linux)
                                                              [GWY: шлюз] ◄─ [BIO: профиль] ◄─ [LRN: живой Learner] [A]
                                                              [SLT] [SEC] [UPA] [UPB] [PRV/RCV]         [MOD: демон, склейка] [A]
                                                                   ▲  CtlLink v1 (BLE GATT [GAT: A] / WebSocket в симуляции)
                                                              телефон: [PWA]                                   L3
```

Важное свойство, из которого вытекает всё остальное: **горячий путь мыши (отчёт в мост, отчёт в ПК) не зависит ни от SPI, ни от модуля, ни от телефона**. Мост ничего не ждёт: если параметры или сцена устарели, помощь молча исчезает, а отчёты идут как есть.

## 4. Философия и принципы

Принципы ниже не декларации: каждый привязан к месту, где он проверяется кодом или тестом.

### 4.1. Центральное инженерное обязательство

**P1. Только вычитание.** Цепочка помощи по каждой оси и на каждом отчёте обязана давать `|out| ≤ |in|`, тот же знак или ноль, а нулевой ввод даёт нулевой вывод (остаток дробных счётов «на потом» не копится). Устройство не добавляет движения, не подмешивает шум или джиттер, не создаёт и не склеивает отчёты.
*Где держится:* ядра ASC и TRM (инвариант в тестах на случайных входах для всех реализаций); **финальный зажим в мосте** (3 нарушения подряд дают PASSTHRU на 5 с); `tests/test_assist.py`, `test_tremor.py`, `test_bridge.py`, фаззинг под ASan/UBSan; сквозной тест в приёмке (`ACC-03`).

**P2. Выход из помощи лёгкий и быстрый, вход намеренный.** Ни один путь в безопасное состояние не требует работающего модуля. Мягкий выход (PASSTHRU) ≤ 1 мс без повторного перечисления USB; жёсткий (аппаратный bypass) работает без прошивки, но ПК перенумерует мышь. Защёлки (Panic, bypass) снимает только намеренное действие человека; телефон и модуль могут помощь **только понижать**.

**P3. Отказ всегда в сторону «как без устройства».** Нормально-замкнутые контакты: нет питания, зависла прошивка, оборвался кабель кнопки, MODE=BYPASS → мышь и экран напрямую. Видео по умолчанию идёт напрямую; через сплиттер экран идёт только пока детектор нужен и все условия выполнены.

### 4.2. Принципы управления и доверия

**P4. Телефон только пульт; устройство единственный авторитет.** Потеря связи, закрытая вкладка, севший телефон ничего не меняют. Телефон не присылает параметры, только смысл («уровень 7 из 10»); сырые блобы строит шлюз и проверяет мост.

**P5. Оболочка безопасности фиксирована, тело динамическое.** Статус, «Выключить помощь», «Железный bypass», выбор слота строятся из 20-байтного `status` и не зависят от манифеста. Слот, пакет или манифест не могут убрать путь к безопасному состоянию.

**P6. Понизить бесплатно, повысить пробно.** Всё, что уменьшает помощь, действует сразу и навсегда. Всё, что увеличивает, применяется сразу, но возвращается само через 20 с, если человек не нажал «Оставить».

**P7. Модуль, параметры и мышь недоверенные для моста.** Мост валидирует каждое поле блобов (границы, CRC, поколение), держит TTL (параметры 5 с, сцена 100 мс, связь 0,5 с) и независимый детектор «запирания».

**P8. Ни одного жеста.** Клиент: только нажатия на большие кнопки (цели ≥ 64×64 px), ни перетаскиваний, долгих нажатий, свайпов, двойных тапов; контраст текста ≥ 7:1.

### 4.3. Принципы данных и обновлений

**P9. Данные человека принадлежат человеку.** Профиль моторики биометрия: привязан к одному устройству (ключи + подпись), зашифрован на диске, стирается заменой ключа, не уходит в облако; нет аккаунтов и аналитики; у страницы ноль сетевых запросов после первого открытия.

**P10. Два канала обновлений не смешиваются.** Система исполняется и может «убить» устройство (подпись производителя, два банка, анти-откат). Пакет это данные человека (подпись отправителя, запечатан для одного устройства, ничего не исполняется). Ни ключей, ни формата, ни сообщений, ни хранилища общего нет.

**P11. Необратимое делается последним, откат запрещён.** OTP, secure boot и отладочный порт блокируются после всех проверок. Ни один сброс не снижает порог анти-отката; золотой образ старше порога не используется.

**P12. Любое сомнение на заводе значит карантин.** Плата без наклейки, аттестация отзывается.

### 4.4. Принципы построения и честности

**P13. Sans-IO ядра.** Ядро моста не касается железа и не блокирует, без кучи, libm и глобалей; единственные внешние символы `memcpy/memset/memmove`. Один код работает и в симуляторе, и на плате.

**P14. Детерминизм.** Fixed-point Q16.16 даёт бит-в-бит одинаковый результат на хосте и МК; C-ядра сверяются с Python-golden на сотнях тысяч тиков.

**P15. Нет часов на устройстве.** Срок годности токенов и файлов заменён одноразовыми nonce и растущими счётчиками (`seq`, анти-откат).

**P16. Каждая цифра имеет источник; симуляция не выдаётся за измерение.** Бюджет задержки, реестр готовности и приёмка устроены так, что утверждение «проверено на железе» нельзя получить правкой флага: нужен файл-запись о приёмке.

### 4.5. Границы применения (сознательные отказы)

| Чего нет и не будет | Почему |
|---|---|
| Подключения pose/people-детектора (DET) к цепочке помощи, адаптера «враги из онлайн-игры» | Это была бы помощь в прицеливании по другим игрокам, а не accessibility. ## 5. Аппаратная архитектура

**Статус раздела: [A] спецификация и расчёты.** Реальной PCB, схемы, трассировки, замеров, сертификации нет. В коде (`src/dataopen/hw/`) лежат проверяемые данные и логика: линейка SKU, группы DNP, BOM, домены питания, оценка тепла, таблица истинности fail-safe (перебрана по всем 128 сочетаниям входов и сверена с `HwModel` симулятора моста), таблица индикации. Названия микросхем (`*` в BOM) это кандидаты по памяти и требуют сверки с даташитами.

### 5.3. Питание

Питание **только от отдельного USB-C** (5 В, источник не слабее 5 В / 3 А, без PD; блок и два кабеля в коробке). Электроника адаптера не берёт ток с порта ПК. VBUS ПК измеряется делителем (< 10 мкА) и проходит к мыши **только через нормально-замкнутый контакт K2**, как при прямом кабеле.

| Домен | Что в нём | Когда питается |
|---|---|---|
| **D0** | Безопасный домен: супервизор, окно watchdog, петля Panic, MODE, вентили, драйверы катушек, BYPASS-светодиод | Всегда, от VEXT, **без программ** |
| **D1** | MCU моста и его flash; ключ VBUS мыши (500 мА) | После D0; мост работает без SoM |
| **D2** | SoM, BLE, (Wi-Fi), eMMC | От VEXT; загрузка 20–40 с (допущение), пока мышь идёт через мост без помощи |
| **D3** | Видео: сплиттер/повторитель, захват, катушки KV | Ключом, **только пока нужен детектор** |
| **D4** | RGB, светодиоды слотов, зуммер | От VEXT |

Порядок включения: VEXT в допуске → D0 → D1 → D2 → D3 (по запросу) → D4.

| SKU | Мышь, Вт | Видео, Вт | Пик, Вт | Предел (80 % от 5 В / 3 А), Вт | Запас на пике, Вт |
|---|---|---|---|---|---|
| DO-1 | 3,94 | 8,71 | 10,65 | 12,0 | 1,35 |
| DO-2 | 3,94 | 9,00 | 10,94 | 12,0 | 1,06 |
| DO-3 | 3,94 | 8,71 | 10,71 | 12,0 | 1,29 |
| DO-4 | 3,94 | 9,24 | 11,65 | 12,0 | 0,35 |

Нагрузки в Вт это **оценки по общим представлениям, не измерения**. Тепловой вывод (честный): корпус 100×75×26 мм (площадь 241 см², h = 10 Вт/(м²·К), 4,15 К/Вт) при пределе касания +22 К рассеивает **5,3 Вт** длительно. «Мышь с помощью без видео» помещается с запасом (перегрев 16 К), **непрерывный UI-детектор в этот корпус по теплу не помещается** (перегрев около 36–38 К). Варианты, между которыми выбирать после замеров: корпус в 1,5–2 раза больше, пониженная частота детектора (UI не требует 240 FPS), более слабый SoM (RK3566 на Base — открытый вопрос), принять горячую поверхность с предупреждением. Пока записано как ограничение: **мощность SoM на пике ограничивается 4,5 Вт программным регулятором**.

**Сервисный порт.** Линии данных USB-C питания проведены на USB OTG SoM (ESD и резисторы) и в обычной работе не используются. При зажатой утопленной кнопке RECOVERY и подключённом компьютере SoM входит в загрузку через ROM; в этом режиме питаются только D0–D2.

### 5.4. Fail-safe

Логика безопасного домена (`hw/failsafe.py`), только аппаратура, без процессора:

```
gate        = VEXT_OK · WDG_OK · PANIC_LOOP_OK · MODE_ASSIST
мышь через мост (K1, K2 включены)   = gate · MCU_ENGAGE
видео через сплиттер (KV включены)  = gate · VIDEO_EN · VIDEO_PWR_OK
иначе катушки обесточены, контакты нормально замкнуты: мышь и экран напрямую
```

Мост и SoM лишь **просят** (`ENGAGE`, `VIDEO_EN`); катушки включить может только вентиль. Аналоговые USB-мультиплексоры без питания не обязаны соединять каналы, поэтому в пути стоят реле, а не мультиплексоры.

| Событие | Что делает аппаратура | Время до «напрямую» | Нужна ли живая прошивка |
|---|---|---|---|
| Внешнее питание пропало | Катушки обесточены, K1/K2/KV отпускаются | ≈ 8 мс (допущение) | нет |
| Короткое нажатие Panic | Контакты не двигаются; мост сам выключает помощь (мягкая защёлка) | указатель не прерывается | да |
| Удержание Panic ≈ 3 с | Петля Panic размыкается, RC роняет `PANIC_LOOP_OK` | ≈ 3008 мс | **нет** |
| Зависание прошивки моста | Нет киков, `WDG_OK` падает за окно 100 мс | ≈ 108 мс | **нет** |
| Зависание SoM / потеря BridgeLink | Аппаратура не меняется; мост через 0,5 с перестаёт применять помощь и снимает `VIDEO_EN` | контакты не двигаются | да |
| Ползунок MODE → BYPASS | `MODE_ASSIST` падает | ≈ 8 мс | **нет** |
| Обрыв кабеля внешней кнопки | Петля разомкнута как при удержании | ≈ 3008 мс | **нет** |

Цена жёсткого bypass: ПК заново перечисляет мышь (0,3–2 с, в симуляции принято 300 мс), монитор перезахватывает сигнал (0,5–3 с). Это записано в руководство, а не скрыто.

**Что проверено:** таблица истинности по всем сочетаниям входов; совпадение с `HwModel` (watchdog ≤ 100 мс, потеря питания, MODE, обрыв кнопки, RC при кнопке, которую прошивка «не видит»); стенд на каждой плате проверяет вторую линию обороны (`panic_loop_hardware`) без ведома прошивки.
**Что не проверено:** времена реле, дребезг, разброс RC (`RELEASE_MS = 8`, `WDG_MS = 100`, `PANIC_RC_MS ≈ 3000` допущения), целостность HS-сигнала через K1, ток катушек, нагрев.

### 5.5. Видеотракт

Реле KV **отпущены** = видеокарта напрямую к монитору с теми же EDID/HPD/DDC; **включены** = видеокарта через сплиттер, ветвь на монитор и ветвь на захват (MIPI CSI-2). Принцип: **путь монитора не проходит через захват**, это аналоговая цепь без буфера кадра. ВЧ-реле рассчитаны на HDMI до ~3,4 Гбит/с на линию и DP до HBR; выше — только напрямую. HDMI 2.1 FRL, DSC, HBR3/UHBR, HDR устройство обязано объявлять как «не отслеживается» (`tap_ok=false`). DP — сложнее HDMI: пассивного сплиттера нет, нужен репитер с cut-through (кандидат не выбран).

### 6.1. BIO: BioProfile Engine **[S]**

**Что делает.** Измеряет, а не управляет: читает движения мыши (`on_mouse(t_us, dx, dy)`) и наблюдения цели (`on_target`) и накапливает профиль моторики. Выхода «двигать курсор» в нём нет.

**Устройство.** Конечный автомат сценариев `IDLE → ARMED → MOVING → SETTLE → TRACK`, с метками `wide_flick`, `micro_track` и модификаторами `surprise`, `low_vis`; частоты ошибок `overshoot`, `undershoot`, `direction`, `miss`, `lapse`; отдельный счётчик упреждения (не попадает в T_motor). Метрики: **T_motor** (время от появления цели до начала движения), **V_max**, **D_brake** (доля дистанции, где человек сам начинает тормозить), **overshoot**, **err_final**, **phase lag** (взаимная корреляция скоростей), **jitter** (частота и амплитуда в полосе 3–16 Гц). Скользящие медиана и σ = 1,4826·MAD по 32 значениям с винсоризацией на 6σ. Усталость: тренд по двухминутным блокам методом Тейла–Сена, флаг, не диагноз.

**Профиль** `BioProfileV1`: 98 байт, little endian, `magic 'BIOP'`, версия, CRC32; 9 метрик × (медиана, σ, n); заголовок для C генерируется из той же структуры и сверяется с компилятором.

**Хранение:** `ProfileStore` — два файла-слота `.a/.b`, запись во временный файл + `fsync` + атомарное переименование; слот новой версии не перезаписывается. Для других модулей: `ProfilePublisher/ProfileReader` (shared memory, seqlock + CRC32).

**Проверено [S]:** `tests/test_bioprofile.py` против симулятора человека с известной истиной (T_motor: смещение ≈ −1,6 мс, разброс ≈ 2 мс; V_max ±1 %; err_final: 90 % эпизодов в пределах 0,08°; фазовая задержка ±1 мс; частота микро-поправок ±0,1 Гц; усталость ±15 %); переворот **каждого** бита профиля даёт отказ.
**Не проверено:** точность на живых людях (симулятор моделирует форму движений, а не записанную моторику); пороги начальные. `deg_per_count` обязан быть правильным; смену DPI в ПО производителя мышь-мост не видит.

### 6.2. ASC: Adaptive Sensitivity Correction **[I]**

**Что делает.** Снижает эффективную чувствительность `K ∈ [0,1; 1,0]` по мере приближения к объекту. **Строго `K = 1,0`, пока человек сам не начал двигаться.**

**Модель.** Расстояние до границы объекта `d`; плавный вход `g(x) = x³(6x² − 15x + 10)` (ровно 0 вне зоны); сопротивление `S = S_slope + S_well`, `K_tgt = 1/(1+S)`. Склон торможения привязан к **личной дистанции начала торможения** (`R` из `d_brake` и частоты перелётов), лунка удержания гасит дрожь у самой цели «ровно настолько, чтобы» дрожь стала не больше трети радиуса. Человек, которому помощь не нужна, получает `K ≡ 1,0`. Усталость ослабляет помощь (`φ = 0,5`), а не усиливает (ручка политики).

**Защита до реакции (Pre-reaction Guard).** Автомат `LOCKED → WAIT → OPEN`: помощь открывается, только если движение началось не раньше `t_appear + T_lo`, где `T_lo = max(100 мс; T_motor − 2σ)`. Помощь не бывает «впереди реакции» человека. После открытия нарастает за `τ_ramp = clamp(σ_T; 20; 80) мс`.

**Взгляд вперёд.** Кривая считается там, где курсор окажется через `25 мс + 120 мс·overshoot_med`. **Уход и перелёт:** зона позади объекта расширяется; быстрый осознанный уход снимает гашение; через 3 с гашение снимается полностью: человека нельзя «запереть».

**Сглаживание.** Критически демпфированный фильтр 2-го порядка (14 Гц на усиление, 7 Гц на отпускание), ограничитель `|dK/dt| ≤ 6 с⁻¹` (`slew_per_s`).

**Реализации.** Float (спецификация формул), Python fixed-point Q16.16 (golden), C99 `asc_core.c` (без libm и кучи, `asc_params_t` 152 байта, `asc_state_t` 104 байта). C **бит-в-бит** равен golden на 11 тыс. реальных и 6 тыс. враждебных тиков; fixed против float в пределах `|ΔK| < 0,0005`. Хост: ≈ 44 нс/тик.

**Проверено [I/S]:** `tests/test_assist.py` (36 тестов), инварианты на случайных входах для всех трёх реализаций. Симуляция «человека в контуре» (тот же человек, те же случайные числа): у персонажа с перелётами доля перелётов 1,00 → 0,53, время захвата 370 → 247 мс.
**Не проверено:** польза для людей; такт на Cortex-M (оценка единицы мкс); константы подобраны на том же симуляторе (числа оптимистичны). Источник объектов (`ObjectProvider`) снаружи модуля.

### 6.3. TRM: Tremor suppression **[I]**

**Что делает.** Односторонне убирает физиологический тремор 3–16 Гц из собственного движения человека. Не добавляет движения.

**Почему не линейный фильтр.** Жёсткая граница `|out| ≤ |in|` несовместима с линейным: после остановки руки он «звенел» бы. Поэтому: НЧ-каскад (намеренное движение) → ВЧ-остаток → полоса 3–16 Гц → отношение `r = E[band]/(E[band] + w·E[lp] + ε)` («насколько это тремор») → сила `s` → `y = clamp(x − s·hp)` с ограничителем `trim_cap` счётов на отчёт.

**Параметры из профиля:** `f_tremor = jitter_hz`, `s_max = 0,9·smoothstep((A − 0,08°)/(0,40° − 0,08°))` — при амплитуде < ≈ 0,09° фильтр **выключен** (тождественно `out = in`). Доверие: `n ≥ 12`.

**Порядок в цепочке: сначала ASC, потом TRM.** Guard и направление ASC обязаны видеть неискажённое движение; границы перемножаются. Лунка ASC в цепочке ослабляется на `0,75·s_max/0,9` (иначе перегашивают один и тот же сигнал).

**Проверено [I/S]:** `tests/test_tremor.py` (25 тестов): на хвате с тремором 6/8/12 Гц мощность в полосе падает ≥ 15 дБ; флик проходит на 100 %; C бит-в-бит равен golden на 120 тыс. тиков.
**Цена (честно):** **отставание на намеренном движении типично 20,5 мс (7,6–46,2 мс), снимается ~13 % пути** (синтетический пользователь, `sim`). При дрейфе медленнее скорости дрожи часть движения убирается (никогда не добавляется). Для людей без заметного тремора фильтр выключен, результат побитово равен «без помощи». Не проверено на людях.

### 6.4. BRG: HID Bridge **[S]**

**Что делает.** Между мышью (USB host) и ПК (USB device). ПК видит **ту же мышь**: все дескрипторы, строки на всех языках, интерфейсы, кнопки, запросы. В отчётах движения мост меняет **только биты X и Y и только вычитанием**; кнопки, колесо, Report ID, вендорные поля, длина остаются прежними; отчётов ровно столько же.

**Прозрачность.** При включении мост читает Device descriptor, **единственную** Configuration и report-дескриптор каждого HID-интерфейса, строит образ. Запросы ПК: `GET_DESCRIPTOR` из образа; `SET_ADDRESS` локально; **всё остальное пересылается мыши вживую** (строки, MS OS, BOS, HID `GET/SET_REPORT`, idle/protocol, вендорные запросы). Интерфейс получает роль `MOUSE_MOTION`, если в его report-дескрипторе есть относительные знаковые X/Y ≤ 16 бит.

**Когда мост не включается** (остаётся аппаратный bypass): isochronous/bulk, больше одной конфигурации, альтернативные настройки, образ > лимитов, нет распознаваемого относительного X/Y (абсолютные указатели, всё вендорное), мышь не отвечает. Режим `mouse_only` дополнительно отказывается от устройств с клавиатурой/digitizer.

**Режимы тайминга** (по `bInterval` мыши): **DIRECT** (1 кГц; тик цепочки на отчёт, пропущенные миллисекунды догоняются нулевыми тиками, результат бит-в-бит как у `AssistChain(impl="c")` 25 из 25 прогонов), **SPLIT** (HS 2–8 кГц; ядра тикают по сетке 1 мс на сумме окна, каждому отчёту `round(in·g + carry)`; частота отчётов не падает), **SLOW** (> 4 мс, мышь 125 Гц: помощи нет, `PASSTHRU/SLOW_MOUSE`). Арифметика ядер точна для `|dx|,|dy| ≤ 511` счётов за тик; больше — мимо цепочки.

**Состояния** (раздел 7.4 и [BRIDGE.md](BRIDGE.md) §5): `HW_BYPASS`, `PROBE`, `PASSTHRU`, `ASSIST`.

**Граница доверия.** Финальный зажим по осям; валидация блобов (размер, CRC32, `generation`, диапазон **каждого** из 38+15 полей, проверено экстремумами int32 в каждое поле); TTL параметров 5 с, сцены 100 мс, связи 500 мс; детектор «запирания» (≥ 250 счётов чистого входа и выход < 4 % за 500 мс → помощь выключена на 500 мс; защита от дефектов, не настройка); бюджет такта (3 подряд > 300 мкс → `PASSTHRU/OVERRUN`); крэш-луп (3 перезагрузки по watchdog без 60 с чистой работы → `HW_BYPASS/CRASHLOOP`).

**Проверено [S]:** 80 тестов (`test_bridge.py` 52, `test_bridge_failsafe.py` 28); перечисление ПК через мост против прямого на 5 мышах (включая композит с HID++-подобным каналом и клавиатурой, мышь HS и 8 кГц) — транскрипты (30–64 запроса) **идентичны**; XOR входа и выхода затрагивает только маски X/Y; фаззинг под ASan+UBSan; `-std=c99 -pedantic -Wall -Wextra -Wconversion -Wshadow -Werror`; кросс-сборка под Cortex-M7. Хост: отчёт ≈ 618 нс (ASSIST, DIRECT), 33 нс (PASSTHRU).
**Не проверено:** реальные мыши, драйверы ПК и ПО производителей (G HUB и т. п.), HS-сигнал через коммутатор, время такта на M7, время перенумерации ПК (принято 300 мс). Добавляется задержка control-запросов (пересылка ≈ 1–3 мс на запрос).

### 6.5. VID: Video path **[I алгоритмы / A железо]**

**Что делает.** Устройство стоит между видеокартой и монитором, **монитору отдаёт тот же сигнал без добавленной задержки**, а параллельно снимает кадр и готовит `640×640 RGB` для детектора.

**Правила passthrough (модель `EdidProxy`).** EDID читается **ровно тот, что у монитора** (база и расширения); DDC/CI, SCDC, HDCP пересылаются; монитор заменили → импульс HPD ≥ 100 мс; монитора нет → HPD низкий, **ничего не выдумывается**. HDCP не обходится: при защите tap получает чёрный кадр и сообщает об этом.

**Тайминги.** CTA-861 и CVT-RB (оценка), достижимость tap: HDMI 2.0 TMDS ≤ 600 МГц (1080p144 — да; 1080p240 и 1440p144 — нет), DP HBR2. Время, к которому нужные строки уже пришли (центральный ROI 640×640): 1080p60 → 12,7 мс, 1080p144 → 5,2 мс. **Это физический нижний предел.**

**Подготовка кадра.** Потоковое C99-ядро `video_prep.c` (RGB/BGR/UYVY/YUYV, BT.709/601, limited/full, кроп, **area-даунскейл**, letterbox как у детектора, фон 114). Совпадает с float-эталоном до 2 LSB; постоянная картинка остаётся ровно постоянной; код под Cortex-M7 1 938 байт. После последней нужной строки остаётся работа одной строки (10–35 мкс на хосте).

**Геометрия.** `Geometry.to_screen/to_input` переводят координаты детектора в пиксели экрана и обратно (проверено на 4 конфигурациях).

**Доставка.** `VideoPath.push` кладёт готовые кадры в `FrameSource` (кольцо dma-buf, политика `latest`; необработанные кадры отбрасываются на стороне производителя). В `Frame` два времени: `ts_us` — момент, когда середина ROI была на проводе, и `meta["ready_us"]`.

**Проверено [I]:** `tests/test_video.py` (35 тестов), фаззинг под ASan+UBSan.
**Не сделано [A]:** чипы и плата, демон V4L2/RGA/ISP/dma-buf, `hdcp_active` и `VIDEO_EN` в BridgeLink, публикация геометрии рядом с кольцом, DSC/HDMI 2.1/HDR. Цифры `unmeasured`: ни одного реального сигнала.

### 6.6. UID: Assistive UI detector **[S]**

**Что делает.** **Единственный** источник объектов интереса для ASC. Смотрит на кадр экрана и находит элементы интерфейса и сам указатель.

**Таксономия v1 (8 классов):** `button`, `icon`, `text_field`, `menu_item`, `toggle`, `tab`, `window_control`, `cursor`. **Жёсткая стена**: `require_ui_layout` отклоняет любую модель с ключевыми точками или классом вне таксономии (вызывается в `UiSceneBuilder`, экспортёре и `OrtUiDetector`, а в канале B — при установке весов).

**Модель `UiNet`.** Малая безъякорная сеть (0,48 М параметров, ≈ 1,0 GMAC на 640, ONNX 1,9 МБ), операции только `Conv, Relu, Add, Resize, Concat` (+ `Cast, Transpose, Mul, Constant, Identity`), три масштаба. Потеря: focal BCE (вес `cursor` ×3) + GIoU. **Хост ONNX Runtime CPU: p50 11 мс, p95 16 мс (`host`).** Числа для NPU — цели, не замеры.

**Данные.** Синтетические экраны (`ui/synth.py`): окна, диалоги, игровое меню, рабочий стол, настройки; пять семейств тем для обучения и две **отложенные** (ретро, стекло); экран готовится через **то же C-ядро video-пути**, что и в проде.

**Сцена для ASC и моста.** Трекер (жадное сопоставление по IoU, стабильные `id`, цель считается целью после `confirm_hits = 2` кадров, трек живёт 6 пропущенных кадров); время появления нужно guard ASC; объект ASC — точка бокса, ближайшая к указателю, радиус `0,35 × меньшая сторона`; сцена задаётся **относительно указателя на момент захвата**, мост сам вычитает дальнейший путь.

**Результаты на синтетике (`dataopen ui eval`):** mAP50 0,78 на обучающих темах, 0,76 на отложенных; указатель найден в пределах 6 px входа в 70 % (обучающие) и 63 % (отложенные) при пороге 0,4; в оставшихся ≈ 30 % кадров сцена не публикуется (безопасное направление отказа: помощь пропадает). Компромисс «сильнее искать указатель против меньше ложных элементов» (порог цели 0,6, указателя 0,4) предстоит переиграть на реальных данных.
**Не проверено:** ни одного размеченного реального скриншота; INT8/RKNN/NPU не запускались; польза для людей; связь «счёты → пиксели» линейна лишь без ускорения указателя ОС (калибровка `px_per_count` не сделана).
**Режим работы в играх:** где нет указателя на экране (сырой 3D-ввод), сцена не публикуется, помощи нет.

### 6.7. GWY: шлюз управления **[I]**

**Что делает.** Единственное, с чем говорит телефон. Принимает чанки CtlLink и ходит к мосту кадрами BridgeLink: HELLO каждые 10 мс (он же опрос), `CMD` по изменению и раз в секунду, блобы параметров раз в секунду. Хранит состояние, слоты, ключи; проверяет **каждое** значение по тому же манифесту, который отдал телефону.

**Органы управления.**
* **«Выключить помощь»**: всегда на экране, один тап, `assist_wanted = false` на диск, `CMD PASSTHRU` сразу.
* **«Железный bypass»**: два шага, `CMD BYPASS` — жёсткая защёлка, **телефон её не снимает**, снимает только удержание Panic 2 с.
* **«Включить помощь»**: просьба, мост выполняет только без защёлок, ошибок и устаревших параметров; иначе экран объясняет причину.
* Перезапуск шлюза помощь **не** включает (читает сохранённое желание, по умолчанию выключено); перезапуск посреди пробы — «нет».

**Уровни** (`ctl/tuning.py`). Две ручки 0..10, 5 = ровно рекомендация профиля, множитель 0 → слой выключен, 5 → ×1,0, 10 → ×1,5. Сила помощи: `s_brake × f`, `k_floor' = 1 − f·(1 − k_floor)` (≥ 0,1). Подавление дрожи: выше рекомендации идёт к потолку 0,95. Выключенный слой отправляется мосту нейтральным, но допустимым блобом. Проверено на настоящем ядре моста: все пары {0,1,5,9,10}² для трёх профилей принимаются (`params_rejected == 0`), сила монотонна.

**Проба.** Повышение (включение помощи, подъём уровня при включённой помощи, импорт нового профиля) применяется сразу, запоминается прежнее состояние, запускается таймер 20 с, экран показывает «Оставить / Вернуть». Нет нажатия или пропала связь → возврат. Крэш посреди пробы не делает её постоянной.

**Калибровка** (`Gateway.calibrating`, источник `Learner`). Пока идёт, помощь принудительно выключена (профиль должен учиться на движениях без помощи), включить нельзя (`err.busy`); профиль идёт как новый (при включённой помощи → проба). Источник подключаемый: `Learner` (`start/stop/poll/snapshot`, при наличии `on_telem`); шлюз уже пересылает ему выборки `TELEM` моста, пока идёт калибровка; в симуляторе `SimLearner`. **Живого `Learner` нет [A]** (см. LRN): нет того, что превратило бы телеметрию и сцену в `on_mouse`/`on_target`.

**Физическое подтверждение.** Нажатие кнопки CONFIRM — одно действие, 30 с, одно использование; сообщение об ошибке называет, для чего оно нужно (`err.physical`).

**Проверено [I]:** `test_ctl_protocol.py`, `test_ctl_manifest.py`, `test_ctl_gateway.py` против **настоящего C-ядра моста**; фаззинг приёма (3000 случайных и подделанных сообщений).
**Не проверено:** сопряжение BLE, смысл шкалы «7 из 10» для человека.

### 6.8. PWA: клиент на телефоне **[S]**

**Что делает.** Страница без установки и аккаунтов, **после первого открытия работает офлайн**, по Bluetooth управляет устройством. Всё критичное живёт на устройстве; телефон хранит только язык, оформление, настройки защиты от повторных нажатий и кэш манифеста по хэшу.

**Устройство клиента.** Оболочка безопасности (статус, «Выключить помощь», «Железный bypass», выбор слота) строится из 20 байт `status`; рисовальщик манифеста (8 типов: `toggle`, `stepper`, `meter`, `status`, `action`, `file`, `note`, `group` + `text`; неизвестный тип → нейтральная плашка, строки только через `textContent`); очередь записи с приоритетом на уровне чанка (STOP встаёт перед следующим чанком); ru/en. **Клиент не содержит криптографии** (тест по исходникам): он носит байты и показывает причины.

**Безопасность страницы.** CSP `default-src 'none'`, только свои скрипты и стили, из манифеста нельзя получить код или адрес, у страницы нет ни одного `fetch`.

**Доступность (проверяется автоматически).** Контраст ≥ 7:1 (AAA) на шести палитрах, границы и кольца фокуса ≥ 3:1; базовый шрифт 20 px, всё в `rem`; цели ≥ 64×64 (кнопка выключения ≥ 90 px); зазор ≥ 12 px; нет обработчиков жестов; `prefers-reduced-motion/-contrast/-color-scheme`; защита от случайных повторных нажатий 0/0,4/0,8 с (кнопка выключения помощи не защищается никогда).

**Транспорты.** Android Chrome (Web Bluetooth), компьютер Chrome/Edge. **iPhone не поддерживается [D]** (нет Web Bluetooth); путь через Wi-Fi SoftAP описан, не сделан.

**Проверено [S]:** Node-тесты (109 в 12 файлах) против настоящих шлюза и ядра моста, байты сверены с Python на общих эталонных векторах; Chromium 360×800 локально (15 проверок, в CI не запускается). BLE подставной.
**Не проверено:** настоящий Web Bluetooth, MTU, фон/сворачивание; TalkBack/Switch Access с людьми.

### 7.2. BridgeLink v1: мост ↔ модуль

Модуль — SPI master, мост — SPI slave с двойной DMA-буферизацией и линией `DRDY`. **Горячий путь не зависит от SPI**: при несвежем TX-буфере порт повторяет предыдущий кадр с тем же `seq`.

```
0 sync 0xB7 | 1 ver=1 | 2 kind | 3 flags (мл. 4 бита: серийный номер блоба) | 4-5 seq | 6-7 ack | 8-9 len (≤112) | 10 frag_idx | 11 frag_cnt
12..123 payload (112) | 124..127 crc32 (zlib) по байтам 0..123        (little-endian)
```

| kind | Направление | Содержимое |
|---|---|---|
| `0x01 TELEM` | мост → модуль | До 6 выборок по 16 байт: `t_us u32, raw_dx, raw_dy, out_dx, out_dy i16, K Q15, buttons, flags` + счётчик потерь; кольцо 2048, самая старая выборка после переполнения помечена флагом 0x80; идёт в BIO (сырые счёты нужны даже в PASSTHRU) |
| `0x02 STATUS` | мост → модуль | 10 Гц: состояние, причина, режим, защёлки, `generation`, счётчики (отчёты, отклонённые блобы, нарушения инварианта, срабатывания детектора запирания, потери телеметрии), время обработки макс/среднее, возраст сцены, VID/PID образа |
| `0x03 TSYNC_REPLY` | мост → модуль | `(m_t, bridge_rx, bridge_tx)` |
| `0x10 HELLO/NOP` | модуль → мост | heartbeat (связь жива) |
| `0x11 PARAMS_ASC` | модуль → мост | Блоб 172 байта: `generation, profile_id, px_per_count Q16, 152 байта asc_params_t, crc32`; 2 фрагмента |
| `0x12 PARAMS_TREMOR` | модуль → мост | Блоб 80 байт: тот же заголовок + 60 байт `tremor_params_t`; 1 фрагмент |
| `0x13 SCENE` | модуль → мост | `t_capture_us` (часы моста), `n ≤ 5`, объекты по 20 байт: `id u16, flags (bit0 = появился), x, y, radius Q16.16 px` **относительно курсора на момент захвата**, `t_appear u32` |
| `0x14 CMD` | модуль → мост | `0` PASSTHRU, `1` ASSIST (запрос), `2` BYPASS |
| `0x15 TSYNC` | модуль → мост | `m_t u64` |

**Компенсация задержки сцены.** Мост хранит кольцо накопленного вывода (256 записей) и пересчитывает положение объекта на «сейчас»: `rel_now = rel_capture − (cum_out_now − cum_out_capture) · px_per_count`. Детектор с задержкой 20 мс и частотой 30 Гц даёт почти ту же помощь, что идеальный (среднее `|ΔK|` 0,0014), без компенсации в 38 раз хуже. Сцена старше 100 мс **от захвата** не используется вовсе (помощь пропадает, а не «оживает по устаревшему положению»).

**Время жизни данных (граница доверия):** параметры 5 с, сцена 100 мс, связь 500 мс. Просроченное = помощи нет, возобновляется само при свежих данных.

**Чего в протоколе нет:** определённой частоты SPI и линии DRDY в коде; `ClockSync` (`bridge/clocksync.py`) не подключён к живому циклу (шлюз не шлёт TSYNC); сообщения `VIDEO_EN` и `hdcp_active`.

### 7.3. CtlLink v1: телефон ↔ шлюз

#### 7.3.1. GATT и чанки

| Характеристика | Свойства | Что |
|---|---|---|
| `info` | read | 16 байт: версия, возможности, id устройства (4 байта), хэш манифеста (4), ревизия манифеста, подсказка размера чанка |
| `status` | read, notify | **Ровно 20 байт**: помещается в ATT при MTU 23, читается без согласования |
| `ctl_in` | write, write-without-response | Чанки телефон → устройство |
| `ctl_out` | notify | Чанки устройство → телефон |

Все характеристики требуют шифрованного (спаренного) соединения. UUID случайные, частные, перед выпуском их надо сменить. **GATT-сервер на BlueZ не написан [A].**

**Сообщение:** `версия u8 | тип u8 | req u16 | длина u16 | флаги u16 | тело | CRC32 u32`, тело ≤ 16 КБ; любая ошибка размера, версии, длины или CRC даёт «не сообщение». **Чанк:** 1 байт заголовка (0x80 первый, 0x40 последний, младшие 6 бит номер) + до `размер − 1` байт; размер согласуется в HELLO (устройство выбирает не больше, чем может доставить; при MTU неизвестном — 20); сборщик ограничен 16 КБ и 5 с между чанками.

#### 7.3.2. Статус (20 байт)

Версия; мост слышен; режим моста (`HW_BYPASS/PROBE/PASSTHRU/ASSIST`); причина (индекс в таблице из 23 причин); флаги (латч Panic, латч bypass, помощь хочет, калибровка, параметры живы, пробное включение, ПК видит мышь, связь по SPI, мост здоров); готовность профиля 0..100; биты готовности слоёв; ревизия состояния и манифеста; время работы в **минутах**; секунд до отката пробы; оба уровня; **активный слот и маска слотов с профилем**. Если мост не слышен 1,5 с, режим «неизвестен», а не угадывается.

#### 7.3.3. Типы сообщений и ошибки

| Тип | Назначение |
|---|---|
| `HELLO / HELLO_R` | Версия, размер чанка, язык; ответ: id, прошивка, хэш манифеста, срок пробы |
| `GET / DATA` | закрытый список: `manifest`, `state`, `identity`, `slots`, `firmware`, `packages`; запрос профиля или модели под любым именем получает `ERR RESIDENT` (19) |
| `SET / ACT / CONFIRM / BUNDLE_PUT` | Значение; действие (двухшаговые требуют `confirmed`); оставить/вернуть; файл настроек |
| **`STOP`, `HARD_BYPASS`** | **Пустое тело, одно сообщение, один чанк, принимаются до `HELLO`** |
| `FW_BEGIN/CHUNK/END` | Канал A: образ системы по частям |
| `PKG_BEGIN/CHUNK/END` | Канал B: пакет по частям |
| `ACK / ERR / EVENT / PING` | `ERR` несёт код и ключ текста; `EVENT` несёт изменение состояния **до** ответа |

Коды ошибок включают (добавочно): `WRONG_DEVICE` 13, `BAD_SIGNATURE` 14, `REPLAY` 15, `PLAIN_REFUSED` 16, `FW_REJECTED` 17, `PKG_REJECTED` 18 и `RESIDENT` 19; `detail` называет причину (`signature`, `hardware`, `rollback`, `trust:<ID>`, `erase`, `slot:<n>`…; кода `export` больше нет). Общие числа и тексты клиент не пишет руками: `dataopen ctl constants` генерирует `pwa/js/constants.js`, `dataopen ctl golden` — `pwa/tests/golden.json` (байты, которые обе стороны обязаны давать и принимать одинаково).

**Манифест** (JSON ≤ 16 КБ): `schema`, `rev`, страницы, контролы; у контролов `id`, `key`, `label/help` как `{ru,en}`, ограничения, `confirm` (`none | revert | two-step`), `danger`. Устройство проверяет каждый `SET`/`ACT` через `Manifest.check_set/check_act`, а при запуске — сам манифест (`validate_manifest`: размеры, глубина, уникальность `id`, языки, диапазоны). Клиент кэширует манифест по хэшу.

### 7.4. Состояния моста

| Состояние | Что происходит | Как попадаем | Как выходим |
|---|---|---|---|
| `HW_BYPASS` | Мышь напрямую, аналоговый коммутатор | Питание/старт; watchdog; фатальная ошибка; мышь не поддерживается; серия USB-ошибок; ПК не настроил клон; 3 краша; Panic ≥ 3 с; `CMD BYPASS`; отключение мыши | Сам — только после старта или ошибки без защёлки (2 с стабильной мыши, образ валиден, ПК настроил клон); после защёлки — намеренно |
| `PROBE` | Мышь на host-порту, device-порт ПК ещё не подключён | Автомат решил включаться | Образ построен → `ENGAGED`; не построен за 3 с → bypass (до 3 попыток, затем `ENGAGE_FAILED`) |
| `PASSTHRU` | Мост работает, X/Y не трогается, **бит в бит** | Короткий Panic (в том же вызове); аккорд кнопок мыши (по умолчанию Back+Forward 3 с); `CMD PASSTHRU`; устаревшие параметры/связь; мышь 125 Гц; нарушение инварианта; превышение бюджета | Таймер для автоматических причин; намеренное действие для Panic |
| `ASSIST` | Цепочка включена | Проверки пройдены, параметры свежие | Любое из вышесказанного |

Латчи не снимаются ничем, кроме намеренного действия (повторное удержание Panic ≥ 2 с снимает мягкую; жёсткие аккорд не снимает). Модуль может только **понижать** помощь. Тест случайных последовательностей событий проверяет: при любой защёлке состояние не `ASSIST`, жёсткая защёлка значит bypass.

## 8. Безопасность, идентичность, пакеты

**Статус: формат, поведение и протоколы [I/S] (с тестами); хранилище ключей, secure boot, HSM, аудит [A].** Криптография только из пакета `cryptography` (X25519, Ed25519, ChaCha20-Poly1305, HKDF-SHA256); **собственных примитивов нет**, формат и протокол собственные и проверены только нашими тестами. Независимого аудита, пентеста и соответствия требованиям к медицинским изделиям **нет**.

### 8.1. Что защищаем и от кого

Моторный профиль человека — биометрическая характеристика.

| Кто | Что может | Что сделано |
|---|---|---|
| Тот, кому достался файл (утечка, пересылка) | Прочитать профиль, применить на другом устройстве | Файл зашифрован под **одно** устройство; на другом `wrong_device` |
| Тот, кто изменил файл по дороге | Подменить профиль, уровни, манифест | AEAD + подпись отправителя; **каждый** изменённый бит отвергает файл (проверено перебором) |
| Украденный **спаренный телефон** | Выгрузить, стереть, подсунуть свой файл | Всё это требует **нажатия кнопки на самом устройстве**; выключить помощь он может — это безопасное направление |
| Вредоносная страница PWA | Подсунуть чужую карточку, уронить передачу | Страница не видит ключей и содержимого; сверка номера получателя глазами, кнопка на источнике, цепочка производителя на карточке |
| Сосед по Bluetooth | Писать в устройство | Шифрованное соединение; всё опасное требует физической кнопки |
| Физический доступ к flash | Прочитать профиль | Данные зашифрованы ключом диска; стирание = замена ключа (в симуляции ключ в файле — граница) |
| Злонамеренный модуль/мышь | Подать опасные параметры мосту | Граница доверия моста (6.4) |
| Старая подписанная прошивка с дырой | Вернуть известную дыру | Анти-откат |
| **root на модуле** | Всё | **Не защищаемся в симуляции**; нужен аппаратный хранитель ключей **[A]** |

### 8.2. Идентичность устройства

Три секрета рождаются один раз и не покидают устройство: `ed` (Ed25519, подпись карточки и файлов), `x` (X25519, расшифровка файлов), `storage` (32 байта, ключ диска). Хранилище — интерфейс `KeyStore`; `FileKeyStore` (файл `0600` в каталоге `0700`) — **симуляция**, `SecureElementSim` — модель (подписывает только два домена, секрет не отдаёт); реальный secure element **[A]**.

**Device Public ID** = `SHA-256("DOID1" ‖ ed_pub ‖ x_pub)`; человеку показываются первые 80 бит в Crockford base32 `XXXX-XXXX-XXXX-XXXX` (без I, L, O, U); в ключ шифрования идёт весь 32-байтный дайджест. **Карточка** `.docard`: `{v, ed, x, id, label, created, sig}` — открытая; подпись Ed25519 доказывает владение ключом; разбор строгий (неверная подпись или `id`, не выводимый из ключей, отвергаются). Блок `device` с цепочкой производителя не входит в самоподпись, поэтому старые карточки остаются действительными.

**Цепочка доверия:** ключ производителя (в OTP только хэш) → аттестация `(серийник, hw_id, DAK, плата)` → сертификат DAK над текущей карточкой владельца. Домены подписей разделены (`DOATT1`, `DODEV1`, `DOPOP1`, `DOSVC1`): secure element подписывает только `DODEV1` и `DOPOP1`, а `DOATT1` и `DOSVC1` ставит только производитель. `verify_chain` отвергает чужого производителя, чужое оборудование, карточку без блока, сертификат от чужого DAK и **настоящий сертификат на чужих ключах**. Политика шлюза `require_attested`: файл «для другого устройства» делается только для карточки с действительной цепочкой.

Серийник, DAK и аттестация **неизменяемы** никаким сбросом; ключи владельца (Device Public ID) меняются заводским сбросом.

### 8.3. Файл `DOBS` v2 (малый защищённый файл)

Двоичный, little endian. Открытая часть (160 байт) защищена как AAD и входит в подпись: `'DOBS'`, версия 2, suite 1, флаги (бит 0 «копия для себя»: формат его знает, устройство такой файл не производит и отвергает), `bundle_id` (16), `recipient_fp` (8), `sender_fp` (8), `seq` (8), `sender_ed_pub`, `sender_x_pub`, `eph_x_pub` (по 32), `nonce` (12), `ct_len`. Далее шифртекст и подпись Ed25519 отправителя (64 байта) над `"DOBS-v2-sig" ‖ заголовок ‖ шифртекст`.

**Ключ:** `HKDF-SHA256(ikm = X25519(eph_priv, recipient_x), salt = eph_pub ‖ recipient_x, info = "DOBS v2 key" ‖ digest_отправителя ‖ digest_получателя ‖ bundle_id)`, шифр ChaCha20-Poly1305. Внутри TLV-секции, дополненные нулями до кратного 256 байт: `1 profile`, `2 tuning`, `3 manifest`, `4 meta`, `5 model` (зарезервирована, в `DOBS` отвергается — веса идут в `DOPK`), `6 slot`.

**Свойства (все проверены):** привязка к устройству (полный дайджест получателя в ключе и подписанном заголовке); целостность (каждый бит файла); подлинность отправителя; защита от повтора (`seq` строго растёт; файл, сделанный самим этим устройством, отвергается: `own_file`); размер файла с профилем, уровнями и именем 496 байт, потолок 16 000 байт; эталонные векторы `tests/data/dobs_v2.hex` и `dobs_v2_slots.hex` фиксируют формат (добавление секции слотов не изменило ни байта старого вектора). Постороннему видно: что это `DOBS`, версию, короткие номера, открытые ключи, размер с шагом 256.

Старый открытый `.dobundle` v1 **не принимается** (`plain_refused`).

### 8.4. Пакет `DOPK` v1 (канал B)

Запечатан для **одного** устройства, подписан **отправителем**, принимается **по частям**. Заголовок 272 байта: `'DOPK'`, версия, suite, флаги, `pkg_id` (16, входит в ключ), `recipient_fp`, `sender_fp`, `seq`, `schema`, `kinds` (маска: профиль, уровни, раскладка, имя, модель), `min_fw`, `sender_ed/x`, `eph_x`, `nonce_base`, `chunk_size`, `ct_len`, **`ct_sha256` всего шифртекста**, подпись Ed25519 над `'DOPK-v1-sig' ‖ заголовок`. Каждая часть шифруется отдельно: nonce = `nonce_base ⊕ номер`, связанные данные = `SHA-256(заголовок без хэша) ‖ номер ‖ признак «последняя»` (ловит перестановку, пропуск, обрезку).

**Подпись стоит до данных.** По первым 272 байтам устройство проверяет «магию», версию, подпись, получателя, повтор, схему, версию системы, виды содержимого и размер — **до** того, как передан хоть мегабайт. Остальное — повторно по частям и целиком (`ct_sha256`).

**Веса модели — данные, не код** (`updates/models.py`): карточка совпадает с байтами; классы в интерфейсной таксономии, указатель отдельный класс, ключевых точек нет (модель позы отвергается `not_ui_model`); граф ONNX разобран без запуска: только `Conv, Relu, Add, Resize, Concat, Constant, Cast, Transpose, Mul, Identity`, ни пользовательских доменов, ни подграфов, ни внешних файлов, opset ≤ 20, один вход, размер ≤ 16 МиБ; без пакета `onnx` устройство **не принимает** веса (отказ закрывается). Проверяется, что это допустимый вид модели, **не что она хороша**, и **не исполняется в песочнице [A/D]**.

### 8.5. Данные на диске и стирание

Файлы общие (`settings`, `trust`) — под ключом диска; файлы слота — под **ключом слота** `HKDF-SHA256(ключ диска, salt = "DOSLOT1", info = "DataOpen slot key" ‖ k ‖ эпоха_слота)`. Очистка слота увеличивает эпоху: старый шифртекст не читается, остальные слоты байт в байт целы (проверено). «Стереть личные данные» заменяет ключ диска; заводской сброс — ещё и ключи владельца. Проверено: после стирания старый шифртекст не открывается новым ключом, перезапуск данных не возвращает, в файлах нет известных байтов профиля.

### 8.6. Физическое подтверждение (кнопка на устройстве)

Одно нажатие, 30 с, одно использование; приём ничего не меняет, пока не пройдены все проверки; повреждённый или чужой файл **не тратит** нажатие.

| Действие | Кнопка на устройстве |
|---|---|
| Файл от нового отправителя | на **получателе** (после нажатия отправитель запоминается, до 16) |
| Пакет с весами модели | на получателе, **каждый раз** |
| Стереть личные данные / заводской сброс / очистить слот | нужна + два шага в приложении; либо удержание CONFIRM 10 с / 20 с |
| Применить обновление системы / вернуть версию | нужна + два шага |
| Забыть все телефоны | нужна + два шага |
| Выключить помощь, включить, уровни, переключить слот | не нужна (повышение идёт пробой) |

### 8.7. Что только задел **[A]**

Secure element / TPM / OP-TEE; secure boot с корнем доверия в eFuse/OTP; аппаратный монотонный счётчик анти-отката; настоящий HSM и процесс ключа производителя (ротация, отзыв); неизменяемый журнал событий безопасности; песочница для присланных моделей; независимая проверка. Допущения: модель «первое знакомство подтверждается кнопкой» не защищает от человека, стоящего у устройства (физический доступ вне модели); часов нет, срока действия у файлов нет; быстродействие Ed25519/X25519 на SoM не измерялось (разовые операции, не горячий путь); квантовые атаки не рассматривались; метаданные файла открыты.

### 8.8. Резидентность: профиль и веса не покидают устройство **[I в симуляции]**

Правило security-инженера: после применения моторный профиль и веса модели живут **только на устройстве**; ни пользователь, ни поддержка, ни приложение не могут «скачать их обратно». Полностью: [RESIDENCY.md](RESIDENCY.md).

* **Нет кода выдачи.** Из протокола убраны `GET bundle` и все «копии»: нет экспорта «для себя», «для другого устройства», «всех слотов»; из манифеста убраны файловые операции `bundle_get` и `bundle_for_card` (остаётся `card_get`, открытая карточка); из клиента убран `getBundle`. Любой запрос профиля или модели получает `ERR RESIDENT` (19).
* **Закрытая поверхность.** `GET_KINDS`, ключи `SET`, действия `ACT`, операции файловых контролов и типы исходящих сообщений заморожены списками (`ctl/residency.py`) и закреплены тестом.
* **Единая дверь исхода.** Каждый ответ проходит `scrub` (схема «запрещено всё, чего нет в списке»): лишний ключ, длинная строка, значение вне словаря или большой ответ не отправляются, счётчик `egress_blocked`. У модели в ответах вместо полного SHA-256 весов короткий `id`.
* **Файл «от самого устройства» отвергается** (`DOBS` и `DOPK`, причина `own_file`): устройство файлов не делает.
* **Сбросы только удаляют.** L1–L4 заменяют ключи и файлы; сохранённая копия шифртекста после сброса бесполезна; `full_return`, отчёт станции и модель восстановления возвращают только метаданные.
* **Доказательство**: профиль и модель с **известными байтами** («канарейки») на устройстве; тестами проверены все вопросы, тысячи фаззинг-запросов, весь «день пилота» с перезапусками и сбросами, диск и логи: ни одного байта наружу. Проба проверяет сама себя: устройство с «get profile» было бы поймано.
* **Цена.** Резервной копии профиля и переноса на запасное устройство нет; замена устройства значит повторную калибровку; потеря раздела данных или secure element значит потерю профиля. Загрузка профиля и модели от доверенного отправителя остаётся (поток только внутрь).
* **Граница.** Не защищает от root на модуле, пока ключи лежат в файле (`FileKeyStore`): нужен secure element (DoD S-7, шаг 5 порядка работ).

## 9. OTA и каналы обновлений

**Статус: оба канала [S/I] в симуляции; загрузчик, flash, secure boot, HSM [A].** Прошивка **исполняется** и может сделать устройство неработоспособным; пакет — **данные человека**, худшее, что от него бывает, — помощь выключена. Поэтому у них разное доверие, разная доставка, разный возврат. Ни ключей, ни «магии» файла, ни сообщений, ни хранилища, ни действий общих нет. Общее одно: кнопка на устройстве и правило «приём ничего не меняет».


### 8.9. Свой путь модели: человек приносит модель сам **[I в симуляции]**

Обратная сторона резидентности: файлы приходят, наружу не выходят. Человек (владелец, доверенный, клиника) готовит ONNX под свои программы и грузит её пакетом `DOPK` через PWA, **без производителя и без магазина** ([MODELS.md](MODELS.md)). «Владелец» это отправитель со своим ключом **вне устройства** (`dataopen update sender init`), которому устройство один раз доверилось кнопкой.

* **Допускается** только: пакет для этого Device Public ID; подпись доверенного отправителя; таксономия интерфейса (`ui-v1`, 8 классов, без людей, поз и «игроков»); граф из белого списка операторов без внешних данных, чужих доменов и подграфов; контракт ABI v1 (вход 640×640, три выхода `[N, классы+4, 640/s, 640/s]`); пределы 16 МиБ, 2000 узлов, 4 GMAC. Проверка **статическая**: граф читается, не запускается.
* **Кнопка:** новый отправитель (`trust:<ID>`) и **каждая** модель (`model:<ID>`); одно нажатие покрывает обе для первой модели нового отправителя.
* **UX:** PWA «глупый» (выбрать файл; слова устройства: принято, отвергнуто с причиной `model_ops`/`model_files`/`model_io`/`model_cost`/`not_ui_model`, нужна новая система, применена); возврат прежней модели; `model.clear` убирает модель слота без кнопки (профиль остаётся); `trust.clear` забывает отправителей (с кнопкой); очистка слота стирает и модель.
* **Резидентность сохраняется:** веса читает ровно один вызов (`ui/resident.py`), он собирает детектор в памяти без файла.
* **Не доказано:** что модель не находит людей (проверяются метки и структура, не поведение; риск R-13); не сделано: демон модуля, NPU/RKNN, изоляция разбора ONNX, измерение на плате.
### 9.1. Два канала

| | A. Система | B. Пакеты |
|---|---|---|
| **Что входит** | Ядро SoM, прошивка моста, BLE-стек, загрузчик, образ восстановления | Профиль, уровни, раскладка, имя слота, веса лёгкой модели UI-детектора |
| **Кто подписывает** | Производитель (ключ вне устройства и репозитория; на устройстве только открытый ключ) | Отправитель: тот, кому человек доверяет (устройство пакетов само не делает) |
| **К чему привязан файл** | Тип железа (`hw_id`) | Конкретное устройство (Device Public ID) |
| **Шифрование** | Нет (публичный файл, нужны целостность и подлинность) | Всегда: X25519 + HKDF + ChaCha20-Poly1305 по частям |
| **Повтор / откат** | Порог анти-отката `min_version` только растёт | `seq` отправителя только растёт; пакет «от самого устройства» отвергается (`own_file`) |
| **Подтверждение** | Кнопка при применении; само не применяется | Кнопка: новый отправитель, чужие веса; иначе проба «Оставить / Вернуть» |
| **Куда кладётся** | Неработающий банк целиком | `pkg/` (ключ диска), один пакет; слот не меняется до применения |
| **Проба** | `MAX_BOOTS = 3`, самоподтверждение при здоровом мосте | Профиль/уровни: проба 20 с; модель: проверка при установке |
| **Возврат** | Автоматически на прежний банк; вручную `fw.rollback` | `profile.prev`, `model.prev`, `pkg.revert`; порога нет |
| **По проводу** | `FW_BEGIN/CHUNK/END`, `FW_REJECTED` | `PKG_BEGIN/CHUNK/END`, `PKG_REJECTED` |
| **Что может пойти не так** | Неработоспособное устройство (поэтому 2 банка, золотой образ, аппаратный bypass мыши) | Помощь выключена, слот очищается; оболочка безопасности и bypass не зависят от пакета |

**Что держит каналы раздельно (каждое правило проверяется тестом):** `signer_a` (файл A проверяется только ключом производителя), `signer_b` (подпись производителя не делает отправителя доверенным), `magic` (каждый канал принимает свою «магию»: DOFW в `PKG_*` и DOPK/DOBS в `FW_*` отвергаются в первом же куске — `wrong_channel`), `transport`, `never_code` (из пакета ничего не исполняется), `storage` (пакет не пишет в банки, обновление системы не пишет в слоты и пакеты), `fw_trial` (пока новая прошивка на пробе, пакеты не применяются, загруженный ждёт).

### 9.2. Канал A: поток обновления системы

1. Человек берёт `.dofw` (сайт производителя, поддержка) → «Ещё» → «Загрузить обновление прошивки».
2. `FW_BEGIN`, `FW_CHUNK`* (≤ 8192 байт, строго по порядку, повторы подтверждаются, обрыв продолжается с места по `GET firmware`/`upload.next`), `FW_END`.
3. Целиком: подпись производителя, `hw_id`, версия ≥ порога анти-отката, не та же, влезает, предыдущее обновление подтверждено. Образ ложится в **неработающий** банк; работающий и помощь не трогаются (проверено на ядре моста).
4. Состояние `staged`. **Само не запускается** (`require_approval`): перезапуск или обрыв питания не применяют.
5. «Применить» (два шага) **и кнопка на устройстве**. Устройство перезапускается; в симуляции мир подменяет шлюз на новый на том же каталоге, связь рвётся, как при перезагрузке; телефон переподключается сам.
6. Проба `trial`: новая версия сама подтверждает себя, когда `fw_confirm_s` секунд непрерывно видит мост (здоров, связь есть, ПК видит мышь, режим не аппаратный обход и не пробный); **аппаратный обход не даёт подтвердить**. Подтверждение поднимает порог анти-отката. Не подтвердилась за `MAX_BOOTS` загрузок → **автоматически возвращается прежний банк**, проваленный помечается плохим.
7. Ручной возврат `fw.rollback` (два шага + кнопка): к другому банку, если он не пуст, не провалил пробу и не ниже порога; кнопка не тратится на невозможное.
8. Без ключа производителя (`vendor_pub` не задан) устройство обновлений не принимает (`unsupported`).

Формат образа `DOFW`: `magic 'DOFW'` (4), `fmt` (1), нули (3, в подписи), `hw_id` (8), `version` (4), `min_version` (4), `payload_len` (4), `sha256` (32), подпись Ed25519 **производителя** над заголовком (64), полезная нагрузка с 124-го байта. Ключ производителя в симуляции тестовый (`DEV_VENDOR_SEED` лежит открыто).

### 9.3. Канал B: поток пакета

1. Человек получает `.dopk` и выбирает его «Ещё» → «Загрузить пакет».
2. `PKG_BEGIN {size}`, `PKG_CHUNK`*, `PKG_END`. **С первым куском** устройство проверяет заголовок и подпись (раздел 8.4); любой отказ закрывает приём, принятое стирается.
3. `PKG_END`: хэш шифртекста, признак «последняя часть», хэш каждой части манифеста, разбор профиля, уровней, раскладки (тем же валидатором, что встроенная), проверка модели. Остаётся `pkg/pending.dopk` и сводка. **Слот не изменился.**
4. «Применить пакет» (два шага). Файл открывается с диска **заново тем же кодом**; кнопка нужна новому отправителю и чужим весам.
5. Применение «вперёд до конца»: метка `pkg/applying` → модель (прежнее поколение сохраняется) → уровни → раскладка → имя → профиль (для нового содержимого при включённой помощи — **проба 20 с**). Обрыв питания посередине: при запуске `applying` обнаруживается и применение **доводится до конца**.
6. Возврат: `profile.restore`, `pkg.revert` (меняет текущую и прежнюю модели местами), отмена ожидающего — `pkg.discard`.
7. Совместимость: в подписанном заголовке `schema` и `min_fw`; пакет, которому нужно больше, чем есть, отвергается из заголовка (`needs_update`). Если система откатилась ниже `min_fw` модели, модель **остаётся**, состояние `needs_system`.

Таблица причин отказа (все ключи `detail` совпадают с текстами приложения; тест сверяет): канал A — `signature`, `hardware`, `rollback`, `same`, `too_large`, `damaged`, `wrong_channel`, `no_trial`, `sequence`, `interrupted`, `unsupported`, `no_previous`; канал B — `wrong_channel`, `damaged`, `bad_signature`, `wrong_device`, `replay`, `needs_update`, `unsupported`, `version`, `too_large`, `sequence`, `tampered`, `truncated`, `hash`, `bad_part`, `not_ui_model`, `bad_model`, `no_pending`, `no_previous`, `unsupported_device`. Полная таблица «когда замечено / что остаётся / что видит человек / что делать»: [UPDATES.md](UPDATES.md) §4 (`dataopen update reasons`).

### 9.4. Правило выпуска: порог анти-отката и золотой образ

Найдено сквозной приёмкой: подъём порога анти-отката первым же обновлением делает **золотой образ устаревшим**; полный возврат (L4) тогда отказывает (`floor`) до траты токена, а самовосстановление не может записать банки. Правило выпуска: **порог после обновления не выше версии золотого образа**. Реализовано функцией `release.policy.check_release(update_raw, golden_raw, vendor_pub, hw_id, floor_now)` и тестом `test_a_release_that_would_outrun_the_golden_image_is_refused`. **Встроить в реальный конвейер выпуска предстоит [A]**; процесс подписанного обновления золотого образа не реализован.

### 9.5. Что не сделано в обновлениях

Загрузчик, secure boot, запись во flash, аппаратный счётчик анти-отката (eFuse/RPMB/secure element) **[A]**; обновление прошивки самого MCU моста (два банка в QSPI) **[A]**; песочница для присланных моделей, лимиты времени и памяти **[A/D]**; каталог официальных моделей, подписанных производителем **[D]**; экспорт моделей в резервную копию, дельта-обновления, очередь нескольких ожидающих пакетов **[D]**.

## 10. Слоты и профили

**Статус: [S].** Человек работает в нескольких контекстах; для каждого нужен свой профиль и уровни. Четыре слота (`SLOT_COUNT = 4`, маска статуса рассчитана на 8) переключаются с телефона или кнопкой на корпусе.

### 10.1. Содержимое и хранение

**В слоте:** профиль (файлы A/B + предыдущий), два уровня, UI-манифест (свой или встроенный), имя (≤ 24 символов), флаг `vetted`, модель (`model.bin`, `model.json`, `model.prev.*`). **Не в слоте:** «помощь включена», активный слот, список доверенных, идентичность, пробное включение.

Ключ слота `HKDF(ключ диска, номер, эпоха)`: ключ соседа и ключ диска чужой слот не открывают. Очистка слота увеличивает эпоху (старый шифртекст мёртв), остальные слоты побайтно целы. Миграция: профиль устройства до слотов при запуске перешифровывается в слот 0 и помечается `vetted`.

### 10.2. Принципы переключения

1. **Смена контекста не включает и не выключает помощь** («помощь включена» — общее состояние устройства, а не слота).
2. **Повышение идёт пробой.** `vetted` слот (содержимое, которое человек уже оставлял в работе) переключается сразу; новое (из файла, калибровки, восстановленное) при включённой помощи и непустом профиле — «Оставить / Вернуть». «Вернуть», истечение или перезапуск посреди пробы возвращают прежний слот. «Оставить» помечает `vetted`.
3. **Клиент остаётся «глупым».** Страница только носит байты.
4. **Путь к соседнему слоту не зависит от того, что принёс слот.** Выбор слота — в неизменной оболочке безопасности, а не в манифесте.
5. **Всё личное стирается заменой ключа.**

Кнопка СЛОТ ходит по кругу **только по занятым слотам**, если их два и больше; иначе по всем четырём (чтобы добраться до пустого и начать калибровку). Отказы (`BUSY`): во время калибровки, во время идущей пробы; номер вне 0..3 (`BAD_VALUE`).

### 10.3. Панель: две кнопки и четыре светодиода (модель `ctl/panel.py`)

| Кнопка | Действие | Что происходит |
|---|---|---|
| **СЛОТ** | короткое (30 мс … 2 с) | следующий слот |
| **ПОДТВЕРДИТЬ** | короткое, идёт проба | «Оставить» |
| | короткое, пробы нет | окно подтверждения на 30 с, одно использование |
| | удержание 3 … 10 с и отпускание | окно сопряжения телефона на 120 с (в шлюзе `pairing.open`; BlueZ-часть **[A]**) |
| | удержание ≥ 10 с | **стереть все личные данные** |
| | удержание ≥ 20 с | **заводской сброс** |
| | отпустить между 2 и 3 с | ничего (так удержание отменяют) |

Контакт короче 30 мс — дребезг. Пока кнопка удерживается, ничего не стёрто (проверено). Светодиоды слотов: активный слот ровно; проба — 2 раза в секунду; калибровка — раз в 2 с; окно подтверждения — все раз в секунду; сопряжение — две быстрые вспышки; удержание ≥ 10 с — все 2,5 раза в секунду; ≥ 20 с — все мерцают 12 раз в секунду; отказ — все 5 раз в секунду 0,6 с. **Пороги 10 и 20 с и «короткое до 2 с» — начальные значения; подбирать с людьми с тремором и ДЦП** (удержание кнопки само может быть трудным действием).

### 10.4. Файл всех слотов

`DOBS` v2 с секцией `6 slot` (номер u8 ‖ длина u32 ‖ вложенные секции `profile`, `tuning`, `manifest`, `meta`). Файл без секции — для **активного слота** получателя; файл со слотами раскладывается **по номерам**, отсутствующие слоты не трогаются; смесь отвергается. Строго проверяется до применения: номер ≥ 4, повтор номера, пустой слот, обрезки, содержимое каждого слота. Принятое в неактивный слот помечается `vetted = false`. Ограничение: четыре собственных UI-манифеста по 10 КБ не влезут в одно сообщение 16 КБ: отправитель шлёт слоты по одному. Файл только **приходит** в устройство; выгрузки нет ([RESIDENCY.md](RESIDENCY.md)).

### 10.5. Матрица сброса (уровни L1–L4)

| Уровень | Название | Как вызывается | Что затрагивает |
|---|---|---|---|
| **L1** | Очистить слот | приложение (два шага + кнопка), `slot.clear` | Активный слот (профиль, уровни, имя, манифест, **модель**); ключ слота заменён; остальные побайтно целы; помощь выключается |
| **L2** | Очистить все профили | приложение, `erase.profile`; удержание CONFIRM 10 с | Все слоты, настройки, список доверенных, ожидающий пакет, **ключ диска**; владелец и телефоны остаются, отправители забыты (нужна кнопка заново) |
| **L3** | Заводской сброс | приложение, `factory.reset`; удержание CONFIRM 20 с | Всё личное + **новые ключи владельца и новый Device Public ID** + забыть телефоны; серийник, DAK, аттестация, прошивка, порог — прежние; файлы для старого номера мертвы |
| **L4** | Полный возврат | только режим восстановления: токен производителя + присутствие | L3 + оба банка SoM и MCU из золотого образа; порог и серийник не сбрасываются |

Банки прошивки не личные и при L1–L3 остаются (проверено). L4 из приложения и кнопками недоступен. Подробности — раздел 12.

### 10.6. Что не сделано

Автоматическое переключение слота по активному окну программы **[D]** (потребует данных UID и политики); плавный переход между слотами (сейчас ступенька параметров; безопасность гарантирует зажим моста, плавность — нет) **[D]**; кнопки и светодиоды на плате (GPIO, дребезг) **[A]**; `vetted` — эвристика симуляции, не оценка качества профиля.

## 11. Latency и критический путь

**Статус: [S]. Ни одной цифры с железа.** Симуляция не вносит джиттер планировщика, прерываний и USB-хоста, поэтому её перцентили — **нижняя оценка**. Подробно: [LATENCY.md](LATENCY.md), `dataopen latency …`.

### 11.1. Три вопроса, которые нельзя складывать

| Группа | Что считаем | Почему отдельно |
|---|---|---|
| **A. Ввод** | Мышь → USB-отчёт в ПК | Задержка **каждого движения**. Ядро считает ASC и TRM синхронно и само добавляет ноль; остальное — сетки опроса USB и **сам фильтр тремора** |
| **B. Сцена** | Объект на кабеле → мост знает цель | Не задерживает указатель: это возраст знания. Положение указателя с тех пор мост возвращает сам. Важно: уложиться в `scene_ttl_ms` (100 мс) и быть заметно меньше окна защиты `T_lo` |
| **C. Политика** | Как быстро помощь вправе действовать | Выбранная плавность: защита до реакции (`T_lo` ≥ 100 мс), нарастание (20–80 мс), торможение не быстрее `slew_per_s`. «Ускорить до нуля» нельзя без потери смысла защиты |

### 11.2. Критический путь

```
 объект нарисован ─► кабель ─► [B1] ROI принята ─► [B2] подготовка (хвост) ─► [B3] очередь кадров ─► [B4] детектор UiNet
                                                                                                  │
   [B6] подтверждение (confirm_hits) ◄─ [B5] трекер ◄─────────────────────────────────────────────┘
        └─► BridgeScenePublisher ─► [B7] SPI-кадр SCENE ─► [B8] link_rx ядра   (t_capture в часах моста)
 мышь ─► отчёт ─► [A3] опрос моста ─► bridge_mouse_in: [A1] ASC ─► [A4] TRM ─► зажим ─► [A3] опрос ПК ─► USB-отчёт
                                                         ▲ select_obj(): цель сдвигается на путь указателя после t_capture
```

### 11.3. Бюджет по сценариям (мс; типично, в скобках диапазон)

Запас считается по возрасту сцены **при использовании** (худший приход + интервал до следующей сцены), потому что TTL моста судит именно его.

| Сценарий | A: ввод | A + TRM | B: сцена в мосту | Возраст при использовании (макс) | Запас до TTL при использовании |
|---|---|---|---|---|---|
| `legacy-fifo`: прежние умолчания, CPU, FIFO(4), 1080p144 | 0,48 (0,0006…1,3) | 21 (7,6…47,5) | **71,8 (61…118)** | 135 | **−35 мс: помощь пропадала** |
| **`v1-default`**: CPU, только свежий кадр, подтверждение за 2 кадра | 0,48 | 21 | **33,6 (22,8…60,1)** | 76 | **24** |
| `cpu-latest`: то же + потоковая подготовка ROI (не реализована) | 0,48 | 21 | 31,8 (22,5…56,5) | 73 | 27 |
| `v1-npu`: цель NPU, свежий кадр, подтверждение за 2 кадра | 0,48 | 21 | 13,8 (10,2…18,8) | 26 | 74 |
| `npu-latest-c1`: вариант, подтверждение за 1 кадр | 0,48 | 21 | 6,84 (3,2…11,9) | 19 | 81 |
| `cpu-60`: умолчания v1 при 1080p60 | 0,48 | 21 | 38,1 (28,1…53,7) | 70 | 30 |
| `npu-4k60`: NPU, свежий кадр, 4K60 | 0,48 | 21 | 24 (19,9…29,4) | 46 | 54 |
| `slow-mouse`: мышь 125 Гц (SLOW) | 3,99 (до 8,3) | 24,5 | 13,8 | 26 | 74 |

Источники по стадиям: B1 `calc` (3,24 мс, до 6,48; физический предел развёртки), B2 `estimate` (0,5 мс), **B3 очередь `calc` (43,9 мс, главный вкладчик прежних умолчаний; при `latest_only` 0)**, B4 `host` (CPU 11 мс p50, 16 мс p95) или цель NPU 3–4 мс (`unmeasured`), B5 `estimate` 0,3 мс, B6 `calc` (`confirm_hits = 2` ≈ 11,3 мс), B7 SPI `unmeasured` (допущено 10 МГц, 0–2 мс), B8 `estimate` 0,5 мс; A1 `estimate` 0,003 мс, A3 `sim` 0,48 мс (максимум 1), **A4 фильтр тремора `sim` 20,5 мс (7,6–46,2)**; C1 6 мс, C2 `T_lo` 100–225 мс, C3 20–80 мс, C4 торможение до ≈ 117 мс (`calc`).

**Вывод по ориентиру «6–8 мс»:** для **входного пути (A) он выполняется** (≤ 1 мс при 1 кГц), но фильтр тремора вносит ощутимое отставание намеренного движения (это цена подавления, а не конвейер). Для **пути сцены (B)** критерий другой: не «мс до помощи», а запас до TTL при использовании и до `T_lo`, и предсказуемое поведение при выходе из запаса. **Находка human-factors** (прежние умолчания: хвост 118 мс при TTL 100, помощь пропадала) закрыта умолчаниями v1 (`latest_only=True`, `max_age_ms=35`, `confirm_hits=2`): worst 60 мс, при использовании 76 мс, запас 24 мс на CPU. Если запас всё же кончается, автомат `SceneHealth` выключает помощь по сцене с гистерезисом (3 поздних подряд → выключено; обратно не раньше 2 с и после 15 свежих ≤ 50 мс), шлёт одну пустую сцену и показывает на пульте `scene.state`: помощь либо вовремя, либо предсказуемо без неё, а не «иногда». Цифры NPU остаются целью.

### 11.4. Что уже компенсируется

* Метка времени кадра = момент, когда **середина ROI была на кабеле**, а не момент готовности (`ts = t_vsync + mid_row + display_latency`).
* **Компенсация сцены в ядре**: сцена 50 мс даёт то же торможение, что свежая (наименьший K 0,36 против 0,36); 90 мс чуть слабее (0,42); 110 мс — не используется (старше TTL).
* TTL сцены считается от захвата, не от приёма.
* Опережение ASC (25 мс + 120 мс·`ov_med`) и окно защиты `T_lo` ≥ 100 мс дают запас относительно человека.
* Мост не задерживает ввод: при превышении бюджета такта — PASSTHRU, а не замедление.
* Трасса `UiService.trace` (`LatencyTrace`); умолчания v1 включены в коде сервиса (`latest_only=True`, `max_age_ms=35`; DoD D-5), автомат деградации и отзыв сцены (`ui/health.py`, `BridgeScenePublisher`); демон, который их соберёт (`scene_service`), ещё не написан (D-1).

### 11.5. Нижние пределы

| Предел | Значение |
|---|---|
| Развёртка (B1), ROI 640×640 готов | 1080p60 — 12,74 мс; 1080p144 — 5,16 мс; 4K60 — 10,37 мс |
| Каскад опросов USB (A3), в среднем / максимум | 125 Гц — 3,99 / 8 мс; 500 Гц — 0,987 / 2; 1000 Гц — 0,479 / 1; 8000 Гц — 0,062 / 0,125 мс |
| Подтверждение цели | не раньше первого обработанного кадра; `confirm_hits = 2` — минимум период кадра сверху |
| Фильтр тремора | не ускоряется без потери подавления: компромисс профиля |

### 11.6. Методика измерения

**Сейчас (симуляция):** `dataopen latency measure hid|chain|scene|pipe` — настоящее C-ядро моста за смоделированной мышью в виртуальном времени (`Rig.report_delay_us`), каскад сеток опроса, плавный бросок через ядро (время достижения 10/25/50/75/90 % пути на входе и выходе), сцена заданного возраста, модель очереди кадров.
**Будущий стенд:** тестовые точки S0 (метка в кадре + фотодиод), L1–L3 (GPIO SoM), L4–L5 (GPIO моста), U1 (анализатор USB на обеих сторонах), M1 (эмулятор мыши), V1 (камера ≥ 1000 кадр/с); не менее нескольких тысяч событий, смотреть p95/p99/максимум; разбор файлов `dataopen latency analyze capture.csv --unit us --limit-ms 12` (код возврата 1 при p99 выше предела или пропусках). Код анализа **работает** и проверен на синтетических данных; снятых данных нет.

### 11.7. Главные риски задержки

1. Очередь FIFO + CPU-детектор (прежние умолчания): хвост B за TTL. Закрыто умолчаниями v1; остаётся риск, что на плате детектор медленнее таблицы (бюджет инференса 19 мс p95 и автомат выключения).
2. Фильтр тремора — главный вкладчик в ощущаемую задержку (20 мс типично, до 46 мс в начале броска); проверять с людьми, не улучшать вслепую.
3. Каскад опросов USB для 125 Гц (до 8 мс).
4. SPI без определённой частоты и DRDY (B7 допущение).
5. Часы: `ClockSync` не подключён к живому циклу, погрешность перевода `t_capture` до RTT/2 входит в ошибку компенсации.
6. Джиттер планировщика в симуляции отсутствует; на плате хвост будет хуже.

## 12. Provisioning, recovery, сбросы

**Статус: логика, форматы и потоки [S]; загрузчик, OTP/eFuse, secure element, HSM, оснастка [A].** Принцип: устройство в поле не должно стать «бомбой замедленного действия»; когда что-то ломается, человек не остаётся без мыши и экрана, а устройство возвращается в рабочее состояние без пайки.

### 12.1. Заводской провижининг (станция из 9 шагов)

Участвуют: устройство (`DeviceAgent`), стенд (`Jig`), HSM (`VendorHsm`), база серийников (`SerialDb`). Команда: `dataopen prov provision`.

| № | Шаг | Что происходит |
|---|---|---|
| 1 | `flash` | Прошить MCU моста (оба банка), SoM (оба банка) и золотой образ; подпись производителя на каждом |
| 2 | `selftest` | Стенд проверяет питание, реле, мышь, Panic, watchdog, пропадание питания, видео, BLE, светодиоды → `DEV_TESTED` |
| 3 | `keygen` | Устройство **само** рождает DAK в secure element и ключи владельца; наружу идут открытые ключи и доказательство владения |
| 4 | `attest` | HSM проверяет доказательство, выдаёт серийник, подписывает аттестацию |
| 5 | `record` | Устройство проверяет аттестацию и пишет запись **один раз** → `PROVISIONED` |
| 6 | `verify` | Станция читает запись, проверяет цепочку производитель → DAK → карточка, повторяет быстрый тест bypass |
| 7 | `lock` | Хэш отчёта в OTP; OTP, слот ключей, отладка и secure boot блокируются (необратимо) → `SHIPPED` |
| 8 | `label` | Наклейка: серийник + QR (карточка рождения с цепочкой) |
| 9 | `release` | HSM отмечает серийник выпущенным |

Серийный номер `DOn-yyww-sssss-c`: цифра SKU, год и неделя, пять цифр порядкового номера, контрольный символ по простому модулю 31 (ловит любую одиночную опечатку; проверено перебором). Любой сбой → **карантин**: плата без наклейки, не попадает в базу выпущенных, выданная аттестация отзывается.

**12 проверок стенда** (допуски из `hw/failsafe.py`): `rails` (±5 %), `secure_element`, `mouse_through_bridge` (20 из 20), `panic_soft`, `panic_long` (≈ 2,9–3,4 с), `panic_loop_hardware` (то же без ведома прошивки), `watchdog_hang` (≤ 130 мс), `mode_switch` (≤ 20 мс), `power_cut_bypass` (≤ 20 мс и мышь работает), `video_direct` (≤ 3 с, EDID не изменён), `ble_visible` (≥ −75 дБм), `indication`. **Проверки мыши, Panic, watchdog, MODE и пропадания питания исполняются на настоящем ядре моста** (`ctl.sim.World`), неисправности внедряются (`--fault relay_stuck|watchdog_dead|panic_stuck|ble_silent…`) и стенд их ловит; видео, BLE, питание, светодиоды — параметрические модели.

### 12.2. Жизненный цикл и неизменяемое

Стадии только вперёд: `BLANK → DEV_TESTED → PROVISIONED → SHIPPED → IN_FIELD → RMA` (RMA → PROVISIONED только по токену производителя). Лог добавляется даже после блокировки OTP.

| Что | Где (целевая архитектура) | Сбрасывается? |
|---|---|---|
| Серийный номер и запись | OTP / заблокированный слот secure element | **Никогда** |
| Хэш ключа производителя | OTP / eFuse | Никогда |
| Порог анти-отката | OTP / eFuse / RPMB (монотонный) | Никогда (только растёт) |
| DAK | secure element, не выходит | Никогда |
| Аттестация | запись устройства + копия у производителя | Никогда |
| Золотой образ | eMMC boot-раздел с защитой записи | vendor-only |
| Ключи владельца (Device Public ID), DAK-сертификат карточки | secure element | L3, L4 |
| Ключ диска | secure element | L2, L3, L4 |
| Профиль, уровни, имя, манифест, модель активного слота | eMMC, ключ слота | L1–L4 |
| Остальные слоты, доверенные, ожидающий пакет | eMMC | L2–L4 |
| Привязки BLE телефонов | стек BlueZ | L3, L4 |
| Образы SoM/MCU, банки A/B | eMMC / QSPI | vendor-only, переустанавливаются при L4 |

### 12.3. Recovery: лестница от никогда не отказывающего слоя

| Слой | Что | Нужен ли компьютер |
|---|---|---|
| **0. Аппаратный bypass** | Мышь и экран напрямую, что бы ни было сломано (без питания, при зависшей прошивке, при мёртвой системе). Единственное, чего слой 0 не покрывает, — залипшие контакты реле | нет |
| **1. MCU моста** | Два банка и загрузчик с пробой; если оба плохи, SoM пишет подписанный образ в ROM-загрузчик MCU по линии BOOT/RESET/UART (ISP) | нет |
| **2. SoM** | Банки A/B с пробой; если оба плохи **или** человек держит **SLOT + CONFIRM при подаче питания ≥ 5 с**, грузится **система восстановления** из золотого образа (подпись, только чтение), светодиод RECOVERY, мышь и экран напрямую; CONFIRM пишет оба банка заново; раздел данных не трогается | нет |
| **3. ROM SoM** (маскром, стереть нельзя) | Если повреждены загрузчик или золотой образ: компьютер на порт питания + утопленная кнопка RECOVERY (скрепка); утилита поддержки пишет загрузчик, золотой образ, банки; данные остаются | да |
| **4. Возврат производителю** | Умерли secure element или eMMC; мышь и экран напрямую; профили теряются | — |

Таблица исходов 14 событий (неудачное обновление, обрыв питания при записи, оба банка плохи, повреждён загрузчик, не читается раздел данных, плохой банк MCU, повреждены SoM и MCU, золотой образ старше порога, потерян телефон, secure element не отвечает, нет блока питания и др.) **вычисляется моделью** `recovery.run` (тест перебирает все сочетания повреждений): для каждого — что видит человек сразу, как вернуть, нужен ли компьютер, что с профилями. `dataopen recover simulate|scenarios`.

**Профили при восстановлении:** живут в разделе данных под ключами secure element; при переустановке образов сохраняются; **профиль и веса не выгружаются никуда** ([RESIDENCY.md](RESIDENCY.md)): при потере раздела данных или смерти secure element резервной копии нет, устройство грузится пустым и человек калибруется заново.

### 12.4. Полный возврат L4 (`service.full_return`)

Только из режима восстановления. Нужны: подписанный токен производителя на **этот серийник** и nonce **этого устройства** (часов нет), плюс присутствие (кнопка). Токен **одноразовый**; неудачная попытка (нет руки, не тот серийник, **золотой образ старше порога**) его не тратит (`floor` проверяется до траты токена); журнал стадий получает `RMA → PROVISIONED → SHIPPED`; порог и серийник не сбрасываются. Команда `dataopen recover full-return`.

### 12.5. Что не сделано

Загрузчик, secure boot, настоящие OTP/eFuse/RPMB/secure element, маскром, оснастка стенда, настоящий HSM, база серийников, подпись отчёта станцией (в OTP только хэш) **[A]**; служебный BLE-сервис режима восстановления и подписанное обновление золотого образа **[A]**; утилита поддержки существует как сценарий в симуляции **[S]**; процесс ключа производителя (ротация, отзыв) назван, не продуман; один производитель в хэше OTP.

`tests/test_acceptance.py` и `tests/acc_helpers.py`. ### 13.4. Что симуляция принципиально не покрывает

Электричество (реле, RC, ток, ESD, целостность HS-сигнала); USB-тайминг ниже микрокадра; поведение конкретных мышей, драйверов ПК, ПО производителя, BIOS/UEFI; реальные мониторы и видеокарты (HDCP, VRR, HDR); радио (MTU, фон, потеря связи); джиттер планировщика Linux, прерываний, USB-хоста; тепло; износ flash; **живые люди**. ### 14.2. Известные пределы поведения (честные цифры)

* **Тремор.** Фильтр вносит отставание намеренного движения: типично **20,5 мс** (7,6–46,2 мс в начале броска), снимает **около 13 %** чистого пути (синтетический пользователь). При очень медленном движении (скорость ниже скорости дрожи) часть движения убирается.
* **Указатель на экране.** UI-детектор находит указатель примерно в 70 % кадров на синтетике; в остальных сцена не публикуется (помощь пропадает). Реальные экраны могут быть хуже.
* **Сцена по умолчанию.** Умолчания v1 включены (`latest_only`, `max_age_ms=35`): на CPU запас до TTL при использовании ≈ 24 мс, и он узкий; при выходе из запаса помощь по сцене предсказуемо выключается. Это симуляция: на плате детектор и планировщик могут быть хуже.
* **Зависание моста.** Мышь пропадает на окно watchdog (100 мс) плюс перенумерацию ПК (принято 300 мс, возможно 0,5–2 с).
* **Мышь 125 Гц** — без помощи (режим SLOW); добавка каскада опросов до 8 мс.
* **Мышь с вендорным движением** (не стандартный относительный X/Y) остаётся на аппаратном bypass.
* **Две мыши** не поддерживаются.
* **Тепло.** Непрерывный UI-детектор в корпус не помещается; SoM ограничен 4,5 Вт.
* **Игры с сырым 3D-вводом.** Указателя нет, сцена не публикуется, помощи нет.
* **Золотой образ.** Подъём порога анти-отката делает его устаревшим (правило выпуска есть, конвейера нет).
* **Резервной копии профиля нет и не будет** (правило резидентности): потеря раздела данных или secure element = потеря профиля; замена устройства = повторная калибровка.
* **Античит.** Сервисы вправе не принимать оборудование, меняющее ввод.

### 14.3. Что нашла сквозная проверка (не видно по отдельным тестам)

1. Помощь выключается намеренно во многих местах (очистка слота, стирание, STOP, bypass от телефона); любой следующий шаг должен включить её заново так, как это делает человек (проба и «Оставить»).
2. Первое же обновление, поднявшее порог, делает золотой образ устаревшим: L4 отказывает (`floor`) до траты токена; самовосстановление тоже.
3. Сцена детектора и шлюз в приёмке попадают в ядро двумя независимыми отправителями; на устройстве мастер SPI один, мультиплексора кадров нет.
4. При зависании моста потери мыши ограничены (`dropped ≤ 110 + перенумерация`), реальное время перенумерации неизвестно.

### 16.3. Правила, которые легко нарушить (найдено по ходу)

1. Всё, что меняет `|out|` в ядре, обязано сохранять `|out| ≤ |in|`, тот же знак и «нулевой ввод → нулевой вывод»; проверять на **трёх** реализациях (float, fixed, C) и сверять C с golden бит в бит.
2. Телефон не присылает параметры; новый тип параметров = новое значение в манифесте + перевод в шлюзе + диапазон в мосту.
3. Любое новое повышение помощи идёт через пробу.
4. Клиент не содержит криптографии (тест по исходникам); хэш и подпись считает устройство.
5. Каналы A и B не делят ничего (пять отдельных тестов-инвариантов); новые действия получают собственные имена.
6. Файл на диске шлюза всегда `DOVT` с именем в AAD; слот — своим ключом.
7. Сцена старше 100 мс от **захвата** не используется; параметры 5 с; связь 0,5 с.
8. Таблицы в `<!-- fp:… -->` и `<!-- hw:… -->` не править руками: `dataopen … docs --write`.
9. Любая новая цифра в документах — с пометкой источника (`calc/sim/host/estimate/unmeasured`).

### E. Глоссарий

* **ASC** — Adaptive Sensitivity Correction, вязкая зона у цели. **TRM** — подавитель дрожи.
* **Bypass (аппаратный)** — мышь и экран напрямую через нормально-замкнутые контакты. **PASSTHRU** — мост работает, X/Y не трогается.
* **Guard** — защита от помощи раньше реакции человека (`T_lo`).
* **DAK** — ключ подлинности устройства, рождается в secure element, не сбрасывается.
* **Device Public ID** — идентификатор владельца, меняется заводским сбросом.
* **Золотой образ** — подписанный образ системы восстановления и банков, только чтение.
* **Анти-откат (floor)** — порог версии, который только растёт.
* **Проба** — применение с автоматическим возвратом через 20 с без «Оставить».
* **Слот** — независимый контекст: профиль, уровни, раскладка, имя, ключ.
* **Манифест** — описание органов управления, которое отдаёт устройство; клиент ничего не знает наперёд.
* **Оболочка безопасности** — неизменяемая часть клиента: статус, «Выключить помощь», «Железный bypass», выбор слота.
* **Канал A / B** — система / пакеты данных человека.
* **Симуляция** — всё, что проверено без железа и без людей.
