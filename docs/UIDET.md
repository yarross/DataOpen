# Assistive UI-детектор: элементы интерфейса и указатель на экране

Источник объектов интереса для ASC и HID-моста, когда accessibility API недоступен или врёт: детектор смотрит на **кадр экрана** (его отдаёт video-путь,
[VIDEO.md](VIDEO.md)) и находит кнопки, значки, поля ввода, пункты меню, переключатели, вкладки, кнопки окна и **сам указатель мыши**. Код: `src/dataopen/ui/`,
CLI: `dataopen ui ...`.

## 0. Честный статус и границы

| Что | Статус |
|---|---|
| Таксономия, жёсткая граница между двумя детекторами, рендерер синтетических экранов, подготовка данных, `UiNet`, loss, декодер, метрики, обучение, ONNX-экспорт, трекер, сцена для ASC и моста, `UiService`, синхронизация часов, симуляция замкнутой петли | **Реализовано, 29 тестов** (`tests/test_ui.py`) |
| Качество на **синтетике** (два обучающих прогона на CPU, раздел 5) | Измерено. Это **нижняя оценка работоспособности конвейера, не обещание для реальных программ** |
| Качество на **реальных скриншотах и играх** | **Не измерено: у меня нет ни одного размеченного реального скриншота.** Формат и команда дообучения есть (раздел 4), прогона нет |
| Весь тракт на целевом SoC (NPU, RKNN, INT8) | Не проверен. ONNX состоит из простых операций; квантизация и RKNN-конвертация не запускались |
| Польза для людей | Не проверена |

**Два мира, развёрнутые жёстко (по просьбе продакт-дизайнера).**

| | Assistive UI-детектор (этот документ) | Pose/people-детектор (ApolloNet-Pose) |
|---|---|---|
| Что находит | только элементы интерфейса и указатель | люди и их ключевые точки в играх |
| Для чего | **единственный** источник объектов для ASC и помощи | исследовательский и аналитический инструмент: BioProfile, статистика моторики, оценка датасета |
| Код | `dataopen.ui`: свои модель, loss, данные, декодер, сервис | `dataopen.detector`, `dataopen.runtime` |
| К цепочке помощи | подключён | **не подключён и не подключается** |

Разделение не на словах. Классы UI-таксономии фиксированы (`ui/taxonomy.py`), и `require_ui_layout` отклоняет **любую** модель, у которой есть ключевые точки или хотя бы один класс вне таксономии.
Её вызывают `UiSceneBuilder`, экспортёр ONNX и `OrtUiDetector` (который к тому же отказывается от файла без `ui_layout` в метаданных). Тесты: pose-раскладка (`player_ct`, `player_t`, 12 точек) отвергается во всех трёх местах.
Это защита от ошибки и от «случайной» склейки, а не от человека, который переобучит модель и обойдёт проверку: сам факт, что границы такие, есть решение проекта, и оно записано здесь и в ASSIST.md.
Мост (`BRIDGE.md`) принимает от модуля только `SCENE`-кадры с координатами относительно указателя и ничего не знает о том, откуда они.

**Что из этого следует для игр.** В играх с «сырым» вводом в 3D-мире указателя на экране нет (есть прицел, а он не наш объект): сцена не публикуется, мост работает без объектов, помощи нет. Помощь появляется там, где есть указатель и интерфейс:
меню игры, инвентарь, лаунчеры, настройки, браузеры, Canvas/WebGL-страницы, старые программы.

## 1. Классы v1 (минимальный набор для старта)

| id | Класс | Что внутри |
|---|---|---|
| 0 | `button` | кнопки, кнопки панелей, крупные нажимаемые плитки |
| 1 | `icon` | значки с подписью и без (ярлыки рабочего стола, значки инструментов) |
| 2 | `text_field` | поля ввода, поиск, адресная строка |
| 3 | `menu_item` | пункты меню-бара, строки выпадающих списков и контекстных меню |
| 4 | `toggle` | чекбоксы, радиокнопки, переключатели (вместе с подписью) |
| 5 | `tab` | заголовки вкладок |
| 6 | `window_control` | свернуть, развернуть, закрыть (самые мелкие и самые важные цели для людей с тремором) |
| 7 | `cursor` | указатель (не цель: нужен, чтобы знать, где указатель) |

Дальше по потребности: ползунки и полосы прокрутки, ссылки в тексте (нужен OCR-подобный признак), раскрывающиеся списки как целое, состояние элемента (недоступен, выбран), вариации указателя (рука, I-образный).
Сейчас обучен и проверен только указатель-стрелка с «горячей точкой» в левом верхнем углу рамки.

## 2. Модель: `UiNet`

Малая безъякорная сеть, **не** pose-сеть: у той `n_kpt=0` не поддерживается (голова, loss, C-постпроцессор и пакет результата завязаны на 12 точек), и общий код был бы как раз связью, которую мы разрываем.

* Вход 640×640 RGB (letterbox video-пути), uint8 NHWC внутри ONNX. Основа: свёртки + BatchNorm + ReLU (BN сворачивается при экспорте), три масштаба (шаги 8, 16, 32), лёгкая нисходящая шея.
  0.48 M параметров, ≈ 1.0 GMAC на 640 (по счёту, принятому в этом документе; счётчик устройства даёт 2.02, см. раздел о задержке), ONNX 1.9 МБ, операции только `Conv, Relu, Add, Resize, Concat` (+ `Cast, Transpose, Mul`). Декодирование (exp, sigmoid, NMS по классам) на хосте.
* На ячейку: логиты 8 классов и расстояния до сторон бокса (l, t, r, b) в долях шага (exp).
* Назначение (FCOS-подобное): бокс идёт на тот масштаб, который ему подходит по длинной стороне (< 40 px: шаг 8, 24–120: 16, ≥ 80: 32, с перекрытием); позитивы — ячейки внутри бокса возле его центра; **крошечные боксы (указатель)
  получают позитивы в окрестности 3×3 ячеек**, иначе одной ячейки мало. Loss: focal BCE по классам (**вес класса `cursor` ×3**: указатель крошечный, а всё остальное от него зависит) + GIoU.
* Скорость на хосте: ONNX Runtime CPU, 4 потока, 640×640, прогон + декодирование: p50 11 мс, p95 16 мс. Цифры для NPU не измерялись.

## 3. Данные: синтетика

`ui/synth.py` рисует экраны: окно приложения (заголовок, меню, панель значков, вкладки, форма), диалог, игровое меню (крупные кнопки, значки в углу), рабочий стол (значки с подписями, панель задач, контекстное меню), страницу настроек, страницу с выпадающими меню.
Размеры 1280×720, 1920×1080, 2560×1440, масштаб интерфейса 0.75 до 1.8 (DPI), фоны плоские, градиентные, «шумовые» (как сцена игры), с узором. Рисуются и **трудные негативы**, которые не размечаются: рамка с подписью, пилюля-«чип», баннер, прогресс, абзац текста.

* **Семейства тем.** Обучающие: светлая, тёмная, высококонтрастная, цветная, неоновая «игровая». **Отложенные** (в обучении не участвуют): ретро с объёмными кнопками и «стеклянная». Метрика на отложенных темах показывает, сколько умения переживает незнакомый внешний вид.
* **Тот же путь, что в проде.** Экран готовится через C-ядро video-пути (area-даунскейл, letterbox 114), включая ROI-кропы (треть выборок смотрит на область экрана в крупном масштабе, как делает video-путь), метки пересчитываются той же `Geometry`. Нет разрыва «как обучали» против «как эксплуатируют».
* Фотометрические аугментации (яркость, контраст, насыщенность, шум, размытие, JPEG); геометрию не портим (зеркало перевернуло бы указатель и текст).
* Ограничения синтетики: текст только латиницей (встроенный шрифт), нет настоящих иконографий, нет анимаций и состояний «наведено/недоступно» кроме простых, нет реального антиалиасинга ОС. Это объясняет, почему синтетика не заменяет реальных скриншотов.

`dataopen ui synth --out DIR -n 8 --boxes [--heldout]` рисует примеры с метками.

## 4. Дообучение на реальных скриншотах (то, что нужно сделать, чтобы это стало рабочим)

Формат: папка с `*.png|jpg` и рядом одноимённые `*.txt` в формате YOLO (`class cx cy w h`, нормировано к размеру скриншота), плюс `classes.txt` с именами классов из таксономии (**любой другой список классов отвергается**).
Скриншоты проходят ту же подготовку, что и всё остальное.

```
dataopen ui train --out runs/ui_ft --resume runs/ui/best.pt --real PATH/TO/SCREENSHOTS --real-share 0.3 --steps 1500 --lr 1e-3
dataopen ui eval  --ckpt runs/ui_ft/best.pt --real PATH/TO/HELD_OUT_SCREENSHOTS
```

Рекомендации по разметке: бокс элемента **с подписью** для значков и переключателей (кликабельная область); для кнопки и поля сам прямоугольник; пункт меню целой строкой; указатель по рамке стрелки (горячая точка в левом верхнем углу);
не размечать то, что только выглядит интерактивным (статические рамки, баннеры, неактивные элементы). Чем разнообразнее программы и темы, тем лучше; отложенный набор нужно брать из **других программ**, чем обучающий.
Это единственный способ узнать, работает ли детектор в реальной жизни, и я не могу сделать этот шаг без данных.

## 5. Результаты на синтетике (CPU, 4 ядра, `dataopen ui eval`, 200 экранов каждого вида)

Обучение: шаг 1: 2500 шагов, батч 16, окно 512, ≈ 51 мин; шаг 2: дообучение 1500 шагов с позитивами 3×3 и весом указателя ×3, ≈ 35 мин. Итоговая модель шага 2:

| | Обучающие темы | Отложенные темы (ретро, стекло) |
|---|---|---|
| mAP50, все 8 классов | 0.78 | 0.76 |
| доля найденных целей (conf ≥ 0.05, без порога) | 0.91 | 0.90 |
| AP50: button / icon / text_field / menu_item | 0.96 / 0.93 / 0.90 / 0.61 | 0.93 / 0.92 / 0.79 / 0.62 |
| AP50: toggle / tab / window_control / cursor | 0.82 / 0.84 / 0.79 / 0.35 | 0.77 / 0.92 / 0.83 / 0.31 |
| найдено по размеру стороны (в px входа): < 16 / 16–32 / 32–64 / 64–128 / ≥ 128 | 0.80 / 0.97 / 0.93 / 0.93 / 0.81 | 0.84 / 0.98 / 0.92 / 0.81 / 0.84 |

**Указатель: узкое место.** AP50 по боксу указателя низкий (0.35 / 0.31), потому что у бокса 6×10 px при одной ошибке в пиксель IoU рушится. Для ASC важно другое: найдена ли **горячая точка** (левый верхний угол) в пределах 6 px входа (≈ 18 px экрана 1080p):

| Указатель | До шага 2 (conf ≥ 0.4) | После шага 2, conf ≥ 0.2 / 0.3 / 0.4 (обучающие) | после шага 2, conf ≥ 0.2 / 0.3 / 0.4 (отложенные) |
|---|---|---|---|
| найден в пределах 6 px | 0.42 | 0.75 / 0.73 / 0.70 | 0.68 / 0.67 / 0.63 |
| медианная ошибка, px входа | 1.9 | 1.9 / 1.8 / 1.8 | 2.6 / 2.4 / 2.2 |
| ложный указатель на экранах, где его нет | 1 из 18 | 7 / 2 / 0 из 23 | 9 / 4 / 1 из 32 |

Это всё ещё **мало**: примерно в 30% кадров указатель не найден, и в эти кадры сцена не публикуется (помощи нет). Это безопасное направление отказа, но помощь будет пропадать.

**Цена шага 2.** Тот же шаг увеличил число ложных элементов: при пороге цели 0.5 стало 2.3 на экран (было 0.7), при 0.6 около 1.1 (было 0.4), при 0.7 около 0.5 (было 0.2); найдено при 0.6 около 0.76 против 0.75.
Поэтому порог цели в `SceneConfig.conf_target` по умолчанию **0.6**, порог указателя **0.4**. Выбор «сильнее искать указатель против меньше ложных элементов» это явный компромисс, его нужно переиграть на реальных данных.
Варианты улучшить указатель: более высокое разрешение входа в окрестности указателя (ROI), отдельная голова шага 4, трекинг указателя с оценкой по счётам моста (ниже), больше шагов.

## 6. Как это встраивается в цепочку ASC → HID-мост

```
 кадр экрана (video-путь, 640×640 + Geometry + ts)
   → UiService (последний кадр, буфер всегда возвращается; ошибка детектора = нет снимка = нет сцены)
   → OrtUiDetector / TorchUiDetector (классы проверены require_ui_layout)
   → UiSceneBuilder: пересчёт в пиксели экрана (Geometry.to_screen) → трекер → указатель → цели
   → ObjectOfInterest (float ASC)   или   SceneObject (BridgeLink SCENE → мост)
```

* **Трекер:** жадное сопоставление по IoU внутри класса, стабильные `id`, сглаживание бокса (вес нового 0.5), цель считается целью после **2 кадров** (одноразовые ложные срабатывания не доходят до ASC), трек живёт 6 пропущенных кадров.
* **«Когда появился»** нужен pre-reaction guard ASC: то, что было на экране с самого начала наблюдения (первые 5 кадров), имеет `t_appear = None`; то, что возникло позже (выпавшее меню, всплывшее окно), получает время захвата. Тест `..._appearance_time_...`.
  Если человек начал двигаться раньше, чем мог отреагировать на новый элемент, ASC не помогает.
* **Объект для ASC:** точка бокса, **ближайшая к указателю**, и радиус `0.35 × меньшая сторона` (в пределах 4 до 60 px). Широкое поле «достигнуто» у своего края, а не у центра; указатель внутри бокса даёт расстояние 0 (удерживающая лунка).
* **Указатель** это сам указатель с экрана (его рисует ОС в сигнал), его горячая точка левый верхний угол рамки. **Сцена задаётся относительно указателя на момент захвата:** `rel = точка_цели − указатель`, и мост сам вычитает дальнейшее движение (`cum_out`), поэтому абсолютная
  погрешность положения указателя не накапливается, а задержка анализа компенсируется (BRIDGE.md, раздел 6). Нет указателя в кадре: сцена не публикуется.
* **Время захвата в часах моста:** `ClockSync` (`bridge/clocksync.py`) по обменам `TSYNC` (формула NTP, выбирается обмен с наименьшим round trip, погрешность ≈ половина RTT). Тест восстанавливает смещение до погрешности.
* **Допущение, которое нужно проверить на железе:** связь «счёты мыши → пиксели» линейна (`px_per_count`). При включённом ускорении указателя ОС она нелинейна: нужно либо выключить ускорение, либо оценивать коэффициент по движению указателя в кадрах (не сделано).

**Замкнутая петля с заглушкой детектора** (`dataopen ui scene-sim`: человек → ASC → мост; сцена идёт через трекер и настоящие кадры `SCENE`, детектор заменён моделью ошибок: дрожание боксов 1.5 px, 5% пропусков, ложные срабатывания, задержка и частота кадров; 20 прогонов):

| | перелёты (доля) | время захвата | дрожь удержания |
|---|---|---|---|
| `overshooter`, без помощи | 1.00 | 346 мс | 5.4 px |
| `overshooter`, идеальная сцена | 0.40 | 208 мс | 7.0 px |
| `overshooter`, сцена детектора 144 к/с, +8 мс | 0.35 | 208 мс | 6.4 px |
| `overshooter`, сцена детектора 60 к/с, +20 мс | 0.35 | 208 мс | 6.7 px |
| `overshooter`, сцена детектора 30 к/с, +40 мс | 0.35 | 208 мс | 6.5 px |
| `tremor`, без помощи | 1.00 | 518 мс | 24.7 px |
| `tremor`, идеальная сцена | 0.30 | 728 мс | 4.2 px |
| `tremor`, сцена детектора 144 / 60 / 30 к/с | 0.30 / 0.40 / 0.35 | 773 / 825 / 777 мс | 6.0 / 10.1 / 10.6 px |

Для персонажа с дрожью сцена детектора заметно хуже идеальной по дрожи удержания (4.2 → 6–10 px): помощь у цели зависит от точности и частоты сцены. Это на заглушке; с реальной моделью цифры будут другими.
Сквозной тест `test_frames_to_service_to_scene_frames_to_the_real_bridge_core_brake_the_approach`: кадры → `UiService` → `BridgeScenePublisher` → кадры BridgeLink → настоящее ядро моста тормозит подход к кнопке.

**Задержка сцены.** Раньше `UiService` брал самый старый кадр из очереди в 4 слота: при детекторе 11 мс против кадра 6.9 мс картинка к моменту взятия была стара в среднем на ~41 мс, и худший случай пути сцены выходил за `scene_ttl_ms` моста (100 мс; тогда помощи нет). Теперь по умолчанию `UiService(latest_only=True, max_age_ms=35)`, а при выходе из бюджета помощь по сцене предсказуемо выключается (`ui/policy.py`, `ui/health.py`); подробности и числа: [docs/LATENCY.md](LATENCY.md) (разделы 3.2–3.4).

**Число MAC.** Здесь указано «≈ 1.0 GMAC»; собственный статический счётчик устройства (`updates/models.py`, свёртки по выведенным формам) даёт для экспортированной `UiNet` **2.02 GMAC**. Расхождение не объяснено (разный способ счёта, возможно, учёт умножения и сложения); оценка времени пользовательской модели ведётся по счётчику устройства и калибруется на `UiNet` (11/16 мс CPU).

## 7. Чего здесь нет

* Реальных скриншотов, реальных игр, реального прогона качества; квантизации INT8 и RKNN; замеров на NPU.
* Указателей кроме стрелки, текста не на латинице, ссылок, ползунков, состояний элементов, OCR.
* Оценки скорости указателя по кадрам и калибровки `px_per_count` при ускорении мыши.
* Весов в репозитории: обучение воспроизводится двумя командами (≈ 1.5 часа на 4 ядрах CPU), результат зависит от данных; сначала нужны реальные скриншоты. Если нужен готовый файл весов для экспериментов, его легко выложить.
* Склейки pose/people-детектора с цепочкой помощи: нет и не будет.
