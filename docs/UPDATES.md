# Два канала обновлений: система и пакеты для слотов

Сначала профили, уровни, раскладки и веса лёгких моделей жили слишком близко к системной прошивке: оба можно было «обновить файлом». Это разные вещи. Прошивка **исполняется** и может сделать устройство неработоспособным; пакет это **данные человека**, он персонален, и худшее, что от него бывает, помощь, которая выключена. У них разное доверие, разный риск, разная доставка, разный возврат. Здесь они разведены на два канала, которые не делят ни ключей, ни формата файла, ни сообщений на проводе, ни хранилища.

Всё проверено **только на симуляции** (настоящее C-ядро моста, шлюз, клиент в Node и в Chromium), см. раздел 0.

## 0. Честный статус и границы

| Что | Статус |
|---|---|
| Канал A (система): формат `DOFW`, два банка, проба, самоподтверждение, анти-откат, кнопка при применении | **уже было** ([SLOTS.md](SLOTS.md) раздел 8, [SECURITY.md](SECURITY.md) раздел 6); здесь добавлены защита от «чужого» файла в этом канале (`wrong_channel`) и правила разделения |
| Канал B (пакеты): формат `DOPK`, приём по частям с проверкой заголовка до загрузки остального, раздел `pkg/`, применение с roll-forward, веса модели в слоте, возврат прежней модели | **новое, реализовано в симуляции, проверено тестами** (формат, потоки, все отказы, настоящее ядро моста, клиент) |
| Малые файлы `DOBS` (профиль, уровни, имя, раскладка до 16 КБ) | остаются как были; это тот же канал B, малый формат |
| Проверка весов модели: формат ONNX, список операторов, отсутствие внешних данных и пользовательских доменов, метки интерфейсной таксономии | реализовано (нужен пакет `onnx`: без него устройство **не принимает** веса) |
| Качество присланной модели | **не проверяется**: проверяется, что это допустимый вид модели, не что она хороша (`dataopen ui eval`) |
| Загрузчик, secure boot, подпись образов на плате, настоящий HSM производителя | **только задел** (как раньше) |
| Выполнение присланной модели в песочнице на SoM, ограничение по времени и памяти | **не сделано**: проверяется структура графа, исполнение отдельно |
| Каталог официальных моделей (подпись производителя, открытая раздача) | **не сделано**: сейчас пакет всегда для одного устройства |
| Резервная копия моделей наружу (экспорт `DOPK` для себя) | **не сделано**: профили и уровни экспортируются как раньше (`DOBS`) |
| Испытания с людьми, клиническая оценка | **не проводились** |

## 1. Два канала

<!-- fp:channels -->
| канал | что входит | кто подписывает | как доставляется | риск |
| --- | --- | --- | --- | --- |
| **A. Система** | ядро (SoM), прошивка моста, BLE-стек, загрузчик, образ восстановления | производитель: ключ вне устройства и вне репозитория, в HSM; на устройстве только открытый ключ | открыто: сайт, поддержка, магазин; через телефон или утилиту; все устройства одного типа (`hw_id`): один и тот же файл | подпись одного ключа даёт код на всех устройствах: ключ хранится вне сети; файл с известной дырой нельзя вернуть (анти-откат) |
| **B. Пакеты** | профиль, уровни помощи, UI-манифест, имя слота, веса лёгкой модели интерфейсного детектора | отправитель: сам владелец (копия «для себя») или тот, кому человек доверяет; ключ Ed25519 отправителя | через владельца: телефон (PWA), почта, облако; сам файл безопасно хранить где угодно; одно устройство: Device Public ID получателя внутри ключа шифрования и внутри подписанного заголовка | подмена получателя, повтор, чужая модель, подмена по частям, «усечённый» файл; веса модели не код, но влияют на то, что считается целью |
<!-- /fp:channels -->

Политика, строка за строкой:

<!-- fp:policy -->
|  | A. Система | B. Пакеты |
| --- | --- | --- |
| **кому доверяет устройство** | открытый ключ производителя (OTP / secure element) | карточка отправителя в списке доверенных (первый раз кнопкой); ключ производителя тут не принимается |
| **к чему привязан файл** | тип железа (`hw_id`), не устройство | ключи владельца (Device Public ID); после заводского сброса файл для старого номера не откроется |
| **шифрование** | нет: файл публичный, нужны целостность и подлинность | всегда: X25519 + HKDF + ChaCha20-Poly1305 по частям, у каждого устройства свой ключ |
| **повтор и откат версии** | порог анти-отката (`min_version`) только растёт; та же версия отвергается | `seq` отправителя только растёт (повтор отвергается); свои копии можно ставить заново |
| **подтверждение человеком** | кнопка на устройстве при применении; применяется не сама | кнопка: первый раз от нового отправителя, каждый раз для весов модели от чужого; иначе проба «Оставить / Вернуть» |
| **куда кладётся** | неработающий банк целиком; работающий не трогается | каталог устройства `pkg/`, зашифрован ключом диска; один пакет за раз; слот не меняется до применения |
| **проба после применения** | пробная загрузка: `MAX_BOOTS` попыток, новая версия сама подтверждает себя; аппаратный обход не даёт подтвердить | для профиля и уровней: проба 20 с; для модели: проверка при установке и проба, прежняя модель хранится |
| **возврат** | автоматически на прежний банк; вручную `fw.rollback` (кнопка); не ниже порога анти-отката | прежнее поколение хранится в слоте (`profile.prev`, `model.prev`); `pkg.revert`; порога нет |
| **по проводу** | `FW_BEGIN/CHUNK/END`, ошибка `FW_REJECTED` | `PKG_BEGIN/CHUNK/END`, ошибка `PKG_REJECTED` |
| **что может пойти не так** | может сделать устройство неработоспособным (поэтому два банка, золотой образ и аппаратный обход мыши) | не может сломать устройство: это данные; худший итог: помощь выключена, слот очищается (оболочка безопасности и обход от пакета не зависят) |
<!-- /fp:policy -->

Что держит каналы раздельно (каждое правило проверяется тестом):

<!-- fp:invariants -->
| правило | что гарантируется |
| --- | --- |
| `signer_a` | файл канала A проверяется только по ключу производителя; подпись любого отправителя не годится |
| `signer_b` | пакет канала B проверяется по ключу его отправителя; подпись производителя не делает пакет доверенным |
| `magic` | каждый канал принимает только свою «магию» файла: DOFW в PKG_* и DOPK/DOBS в FW_* отвергаются в первом же куске |
| `transport` | у каналов разные типы сообщений и разные коды ошибок; один не может быть выдан за другой |
| `never_code` | из пакета канала B ничего не исполняется: ни скрипт, ни код модели, ни операторы вне списка |
| `storage` | пакет канала B не пишет в банки прошивки; обновление канала A не пишет в слоты и пакеты |
| `fw_trial` | пока новая прошивка на пробе, пакеты не применяются (она ещё не доказала, что читает их); загруженный пакет при этом ждёт |
<!-- /fp:invariants -->

Что принципиально общего **нет**: ключи (производитель против отправителя), «магия» файла (`DOFW` / `DOPK`, малый `DOBS`), сообщения (`FW_*` / `PKG_*`), коды ошибок (`FW_REJECTED` / `PKG_REJECTED`), хранилище (банки `fw/` против `pkg/` и слотов), действия (`fw.apply` / `pkg.apply`). Общее одно: кнопка на устройстве (одно нажатие, одно использование, 30 с) и правило «приём ничего не меняет».

## 2. Форматы

### 2.1. Канал A: образ системы `DOFW`

Не изменился (подробности в [SECURITY.md](SECURITY.md) раздел 6). Файл публичный и одинаковый для всех устройств типа; подписан **производителем**.

<!-- fp:format_a -->
| поле | байт | смысл |
| --- | --- | --- |
| `magic` | 4 (0…3) | 'DOFW' |
| `fmt` | 1 (4…4) | формат, 1 |
| `(пусто)` | 3 (5…7) | нули, входят в подпись |
| `hw_id` | 8 (8…15) | тип железа |
| `version` | 4 (16…19) | версия образа |
| `min_version` | 4 (20…23) | порог анти-отката: ниже уже не принимается |
| `payload_len` | 4 (24…27) | длина образа |
| `sha256` | 32 (28…59) | SHA-256 образа |
| `signature` | 64 (60…123) | Ed25519 ПРОИЗВОДИТЕЛЯ над заголовком |
| `payload` | {payload_len} (с 124) | образ без шифрования: файл публичный |
<!-- /fp:format_a -->

Что нового: первые четыре байта первого куска сверяются с `DOFW` ещё до накопления файла. Пакет, отправленный как обновление системы, отвергается сразу (`wrong_channel`), банк не трогается.

### 2.2. Канал B: пакет `DOPK` v1

Запечатан для **одного** устройства, подписан **отправителем**, сделан так, чтобы его можно было принимать по частям. Набор примитивов тот же, что у `DOBS` ([SECURITY.md](SECURITY.md) раздел 3): X25519, HKDF-SHA256, ChaCha20-Poly1305, Ed25519 из пакета `cryptography`; свои примитивы не придуманы, отличаются только метки, поэтому ключ одного формата не открывает другой.

<!-- fp:format_b -->
| поле | байт | смысл |
| --- | --- | --- |
| `magic` | 4 (0…3) | 'DOPK' |
| `ver` | 1 (4…4) | формат, 1 |
| `suite` | 1 (5…5) | набор примитивов, 1 |
| `flags` | 2 (6…7) | бит 0: «для себя» (отправитель = получатель) |
| `pkg_id` | 16 (8…23) | случайный номер пакета (входит в ключ) |
| `recipient_fp` | 8 (24…31) | короткий отпечаток получателя: Device Public ID |
| `sender_fp` | 8 (32…39) | короткий отпечаток отправителя |
| `seq` | 8 (40…47) | порядковый номер отправителя, только растёт |
| `schema` | 2 (48…49) | схема пакета, которую нужно понимать |
| `kinds` | 2 (50…51) | что внутри (битовая маска: профиль, уровни, раскладка, имя, модель) |
| `min_fw` | 4 (52…55) | версия системы, не ниже которой пакет читается |
| `sender_ed` | 32 (56…87) | открытый ключ подписи отправителя |
| `sender_x` | 32 (88…119) | открытый ключ обмена отправителя |
| `eph_x` | 32 (120…151) | одноразовый открытый ключ обмена |
| `nonce_base` | 12 (152…163) | основа nonce частей |
| `chunk_size` | 4 (164…167) | байт открытого текста в одной части |
| `ct_len` | 8 (168…175) | длина шифртекста |
| `ct_sha256` | 32 (176…207) | SHA-256 всего шифртекста |
| `signature` | 64 (208…271) | Ed25519 отправителя над `'DOPK-v1-sig' ‖ заголовок` |
| `ciphertext` | {ct_len} (с 272) | части по `chunk_size` + 16 байт метки; метка части связана с её номером и признаком «последняя» |
<!-- /fp:format_b -->

Открытый текст: `u32 длина_манифеста ‖ манифест (JSON: слот, части: тип, размер, SHA-256, описание) ‖ байты частей по порядку манифеста`. Он режется на части по `chunk_size` байт, **каждая часть** шифруется отдельно: nonce = `nonce_base ⊕ номер`, связанные данные = `SHA-256(заголовок без хэша шифртекста) ‖ номер ‖ признак «последняя»`.

**Подпись стоит до данных.** Заголовок называет получателя, отправителя, порядковый номер, схему, нужную версию системы, виды содержимого и (через `ct_sha256`) каждый байт шифртекста. Устройство проверяет всё это по первым 272 байтам: подделка, файл для другого устройства, повтор, пакет, которому нужна более новая система, слишком большой пакет отвергаются **до** того, как будет передан хоть мегабайт. Остальное проверяется дважды: по частям (метка части заодно ловит перестановку, пропуск и обрезку через номер и признак «последняя») и целиком (`ct_sha256`).

Что может нести пакет:

<!-- fp:parts -->
| часть | что это | где лежит | подтверждение | возврат |
| --- | --- | --- | --- | --- |
| `profile` | моторный профиль (то же кодирование, что в `DOBS`) | в слоте, под ключом слота | кнопка для нового отправителя; проба «Оставить / Вернуть» | `profile.prev`, `ACT profile.restore` |
| `tuning` | два уровня: сила помощи и подавление дрожи | в слоте | то же | проба |
| `ui_manifest` | раскладка экранов слота (проверяется тем же валидатором, что и встроенная) | в слоте | то же | прежняя раскладка не хранится: слот можно очистить |
| `meta` | имя слота (до 24 символов) | в слоте | то же | — |
| `model` | веса лёгкой модели интерфейсного детектора (ONNX) и её карточка | в слоте: `model.bin`, `model.json` под ключом слота | кнопка каждый раз, если не своя копия | `model.prev.*`, `ACT pkg.revert` (меняет местами) |
<!-- /fp:parts -->

Содержимое частей `profile`, `tuning`, `ui_manifest`, `meta` кодируется и разбирается **той же функцией**, что и в `DOBS` (`ctl/seal.py`), поэтому профиль и уровни значат одно и то же в обоих форматах. Слот назначения указан в манифесте (`slot` = 0…3) или не указан (активный слот приёмника).

### 2.3. Веса модели как часть пакета

Веса это **данные, не код**. Устройство проверяет (`updates/models.py`), прежде чем оставить их:

1. карточка модели в манифесте (формат `onnx`, таксономия `ui-v1`, список классов, размер входа 640, набор операторов, версия, размер, SHA-256) совпадает с байтами;
2. список классов входит в интерфейсную таксономию, указатель это отдельный класс, ключевых точек нет: модель позы или людей **отвергается** (`not_ui_model`) тем же правилом, что в `UiSceneBuilder`;
3. граф ONNX разобран без запуска: только простые операторы, которые пишет `dataopen ui export` (`Conv`, `Relu`, `Add`, `Resize`, `Concat`, `Constant`, `Cast`, `Transpose`, `Mul`, `Identity`), ни одного пользовательского домена операторов, ни одного подграфа, ни одного внешнего файла с данными, набор операторов не выше 20, один вход;
4. собственная метка модели `ui_layout` совпадает с карточкой;
5. размер не больше 16 МиБ.

### 2.4. Совместимость пакета и системы

В подписанном заголовке: `schema` (какую схему пакета нужно понимать; у этой системы 1) и `min_fw` (не ниже какой версии системы пакет читается). Если пакету нужно больше, чем есть, он отвергается из заголовка: `needs_update` («сначала обновите систему»). Если после установки модели система откатилась ниже `min_fw`, модель **остаётся на устройстве**, а состояние `model.state` становится `needs_system`: ничего не удаляется, при обновлении системы модель снова работает.

## 3. Потоки

### 3.1. Канал A: обновление системы

1. Человек берёт файл `.dofw` (сайт производителя, поддержка) и выбирает его на странице «Ещё» → «Загрузить обновление прошивки».
2. `FW_BEGIN`, `FW_CHUNK`*, `FW_END`; куски по порядку, повторы подтверждаются, обрыв продолжается с места обрыва.
3. Целиком: подпись производителя, `hw_id`, порог анти-отката, «та же версия», размер, предыдущее обновление уже подтверждено. Образ ложится в **неработающий** банк; работающий и помощь не трогаются.
4. Состояние `staged`. Само не запускается (перезапуск или обрыв питания не применяют).
5. «Применить обновление» (два шага) и **кнопка на устройстве**; устройство перезапускается; телефон подключается заново сам.
6. Проба: новая версия сама подтверждает себя, когда `fw_confirm_s` секунд непрерывно видит мост; аппаратный обход не даёт подтвердить. Не подтвердилась за `MAX_BOOTS` загрузок: возвращается прежний банк.
7. Возврат вручную: «Вернуть прежнюю версию» (два шага и кнопка), не ниже порога анти-отката.

### 3.2. Канал B: пакет для слотов

1. Человек получает файл `.dopk` от себя (копия) или от того, кому доверяет, и выбирает его на странице «Ещё» → «Загрузить пакет».
2. `PKG_BEGIN {size}`, `PKG_CHUNK`* (смещение + данные), `PKG_END`. **С первым куском**, содержащим заголовок и подпись, устройство проверяет: «магию», версию и набор примитивов, подпись, получателя, повтор, схему и версию системы, виды содержимого, размеры. Любой отказ закрывает приём, принятое стирается. Остальные куски расшифровываются и проверяются по мере прихода; куски пишутся в `pkg/incoming.part`.
3. `PKG_END`: хэш всего шифртекста, обязательный признак «последняя часть», хэш каждой части манифеста, разбор профиля, уровней и раскладки (тем же валидатором, что и встроенная), проверка модели (раздел 2.3). Файл остаётся как `pkg/pending.dopk` (запечатан для ключей этого устройства и подписан отправителем) и краткая сводка (под ключом диска). Ответ: что внутри, от кого, для какого слота, нужна ли кнопка.
4. Состояние `pending`; **слот не изменился**. Новая загрузка не стирает ожидающий пакет, пока новый не пройдёт все проверки.
5. «Применить пакет» (два шага). Устройство открывает файл с диска **заново тем же кодом** (изменённый на диске файл ловится как изменённый на проводе), сверяет порядковый номер отправителя и определяет, нужна ли кнопка:
   * отправитель ещё не известен: кнопка (`trust:<ID>`), после этого он в списке доверенных;
   * в пакете веса модели, а он не от самого владельца: кнопка (`model:<ID>`), **каждый раз**;
   * копия «для себя» и пакет без весов от известного отправителя: кнопка не нужна.
6. Применение идёт «вперёд до конца»: сначала метка `pkg/applying`, затем модель (отдельный файл, прежнее поколение сохраняется), затем уровни, раскладка, имя и профиль (через те же пути, что и у `DOBS`: для нового содержимого при включённой помощи это **проба «Оставить / Вернуть»**, 20 секунд). Потом файл и метка удаляются. Обрыв питания посередине: при запуске `applying` обнаруживается и применение **доводится до конца** (кнопка уже потрачена).
7. Возврат: профиль `ACT profile.restore` (как раньше), модель `ACT pkg.revert` (меняет текущую и прежнюю местами, повторный вызов возвращает обратно). Уровни и раскладка возвращаются пробой.
8. Отменить ожидающий пакет: `ACT pkg.discard` (ничего не стирает, кроме самого пакета).

### 3.3. Что видит человек

| Шаг | Система | Пакет |
|---|---|---|
| где | «Ещё» → блок прошивки | «Ещё» → блок пакета и модели |
| загрузить | «Загрузить обновление прошивки», проценты | «Загрузить пакет», проценты; при отказе заголовка сообщение приходит с первым куском |
| что показывает устройство | «Обновление»: «Загружено, ждёт применения» | «Пакет для слотов»: «Проверен, ждёт применения»; «Пакет от»; сообщение: «ничего не изменилось» |
| применить | «Применить обновление» (два шага + кнопка) | «Применить пакет» (два шага; кнопка, если нужна: сообщение называет, для чего и от кого) |
| пробный период | новая версия проверяет себя сама | «Оставить / Вернуть» для профиля и уровней |
| вернуть | «Вернуть прежнюю версию» | «Вернуть прежний профиль», «Вернуть прежнюю модель» |
| передумать | не нужно: до применения ничего не работает | «Отменить пакет» |

Страница **не содержит криптографии**: она только носит байты (тест по исходникам проходит без исключений). Хэш, подпись, шифрование и разбор считает устройство.

### 4.3. Особые случаи

* **Обрыв связи.** Приём возобновляется с места обрыва: телефон спрашивает `GET firmware` / `GET packages`, берёт `upload.next` и продолжает. Принятый кусок, подтверждение которого потерялось, подтверждается ещё раз и не применяется дважды; пропуск куска (`sequence`) не закрывает приём. Приём, к которому никто не прикасался 60 секунд, или перезапуск шлюза **сбрасывают** недоставленное; законченный ожидающий пакет **переживает** перезапуск.
* **Обрыв питания.** Канал A: пустой второй банк, работающий не тронут. Канал B при приёме: ничего не применено; при применении: довершение при запуске (раздел 3.2, пункт 6).
* **Неверная подпись** отправителя: `bad_signature` в самом начале. **Чужой производитель**: подпись производителя не делает отправителя доверенным, а подпись отправителя не годится для системы (проверяется тестами в обе стороны).
* **Пакет «не для этого устройства»:** получатель назван в подписанном заголовке и входит в ключ; после заводского сброса (новый номер владельца) файлы для старого номера не открываются.
* **Новая система на пробе:** пакеты не применяются (`BUSY`, `fw_trial`), загруженный ждёт; кнопка не тратится.
* **Калибровка идёт:** `BUSY`, `calibrating`.
* **Повтор:** тот же порядковый номер (или меньше) от того же отправителя отвергается (`replay`); свои копии можно ставить заново.

## 5. Как это стыкуется с остальным

| С чем | Как |
|---|---|
| **Два банка прошивки** ([SLOTS.md](SLOTS.md) раздел 8) | Канал A как был. Банки пишет только он; пакет их не трогает (тест сравнивает байты `fw/` до и после). Пока новая версия на пробе, пакеты не применяются: она ещё не доказала, что читает хранимое. |
| **Слоты** ([SLOTS.md](SLOTS.md)) | Пакет адресован слоту по номеру. Модель лежит в каталоге слота под **ключом слота** (`model.bin`, `model.json`, прежнее поколение `model.prev.*`): очистка слота стирает её вместе с профилем. Обновление системы слоты не трогает (тест сравнивает байты). |
| **Защищённые файлы `DOBS`** ([SECURITY.md](SECURITY.md) раздел 3) | `DOBS` остаётся малым форматом для профиля, уровней, имени и раскладки (до 16 КБ в одном сообщении). `DOPK` несёт то же содержимое тем же кодированием, плюс веса, и принимается по частям. Список доверенных отправителей и счётчик повтора общие. |
| **PWA** ([PWA.md](PWA.md)) | Манифест устройства получил операцию файла `pkg_put`, действия `pkg.apply`, `pkg.discard`, `pkg.revert`, состояния `pkg.*`, `model.*`. Клиент по-прежнему «глупый»: тип сообщений `PKG_*` и коды ошибок сгенерированы из `ctl/protocol.py` (эталонные векторы пересозданы). |
| **Провижининг** ([PROVISIONING.md](PROVISIONING.md)) | Заводской образ и золотой образ это канал A (подпись производителя, `hw_id`). Ожидающий пакет и модели входят в карту хранения и матрицу сброса: L1 (очистка слота) стирает модель слота и оставляет ожидающий пакет; L2, L3 и L4 стирают всё; серийник, DAK, аттестация и порог анти-отката не затрагиваются ни одним уровнем. |
| **Восстановление** | Откат на золотой образ или прежний банк раздел данных не трогает: пакеты и модели остаются. Если система стала старше `min_fw` модели, модель помечается `needs_system` и не удаляется. |
| **Аппаратный обход и оболочка безопасности** | От пакета не зависят: слот, раскладка и модель не могут убрать «Выключить помощь», обход или выбор слота (правила остались: выбор слота лежит вне манифеста). |

## 6. Команды

```
dataopen update channels | policy | invariants | parts | format-a | format-b | reasons [--channel A|B]
dataopen update build-package --to card.docard --sender-dir DIR --out file.dopk [--slot K] [--tuning S,T] [--name N] [--model m.onnx] [--min-fw N]
dataopen update inspect file.dopk                          # заголовок, ничего не проверяется и не расшифровывается
dataopen update verify file.dopk --device-dir DIR          # все проверки устройства ключами моделируемого устройства
dataopen update check-model m.onnx                         # структурная проверка модели
dataopen update docs --check | --write                     # актуальность этого документа
```

## 7. Что сознательно не сделано

* Исполнение присланной модели в песочнице, лимиты времени и памяти на SoM: проверяется граф, а не поведение.
* Каталог официальных моделей, подписанных производителем и раздаваемых открыто (другая политика: не привязан к устройству, нужна подпись производителя и свой порог версии). Сейчас пакет всегда для одного устройства.
* Экспорт моделей в резервную копию (`DOBS` для них мал), сжатие и дельта-обновления.
* Ограничение размера по свободному месту и очередь нескольких ожидающих пакетов: сейчас один.
* Стойкость к отказу диска: в симуляции файлы пишутся временным файлом и переименовываются; настоящая запись во flash, износ, RPMB и счётчики это задел.
* Сроки годности: часов у устройства нет, поэтому ничто здесь не «протухает по времени»; повтор отсекается порядковыми номерами.
* Испытания с людьми: что показывать, когда и как формулировать, нужно проверять с теми, для кого это сделано.
